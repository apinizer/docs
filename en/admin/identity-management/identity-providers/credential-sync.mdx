---
title: "Credential Synchronization"
description: "You can synchronize users from LDAP/Active Directory, Database, API, and OIDC (Keycloak) identity providers into Apinizer credentials with a scheduled job, and monitor synchronization status and history from a single screen."
---

:::info

Credential Synchronization automatically turns users from [Database Provider](/en/admin/identity-management/identity-providers/database-provider), [LDAP Active Directory](/en/admin/identity-management/identity-providers/ldap-active-directory), [API Authentication Provider](/en/admin/identity-management/identity-providers/api-authentication-provider), and [OIDC Provider](/en/admin/identity-management/identity-providers/oidc-provider) (Keycloak only) sources into [Credential](/en/admin/identity-management/credentials) records, either on a schedule or on manual trigger. This keeps credentials centrally up to date from the external source instead of being created manually for each provider.

:::

## Sync Profile

These common fields live in a **Sync Profile** section of each provider's edit screen: a separate tab for Database Provider, API Authentication Provider, and OIDC Provider (**Synchronization** for OIDC); for LDAP Active Directory, a **Synchronization** card with a **Configure** button that opens them in a drawer — see [LDAP Active Directory](/en/admin/identity-management/identity-providers/ldap-active-directory#synchronization).

<img
  src="/images/yonetici/credential-sync/credential-sync-profil.png"
  alt="Credential Synchronization Profile"
  width="1000"
  height="468"
/>

| Field | Description |
|------|----------|
| Enable Synchronization | When enabled, credentials are synchronized from this source according to the configured schedule. When disabled, neither the scheduled nor the manual synchronization runs. |
| Cron Expression | A Quartz cron expression that determines how often synchronization runs (e.g. `0 0 2 * * ?`). It is optional. If left empty, synchronization can only be triggered manually from the [Synchronization](#synchronization-status-and-history) screen. While the field is empty it shows a grey hint text, which is not a value. |
| Deactivation Mode | The action applied to credentials whose corresponding user is no longer present in the source on the last run:<br/>• **Disable** *(recoverable)* — the credential is disabled but its record is kept. This is the default.<br/>• **Delete** *(irreversible)* — the credential is permanently deleted.<br/>• **None** *(keep as is)* — no action is taken; drift is accepted. |

Provider-specific additional fields are described below.

### LDAP Active Directory

| Field | Description |
|------|----------|
| Base DN (from the connection) | Read-only. Synchronization reads users and groups under the Base DN of the selected LDAP connection. To narrow the search, fill in **User Base DN Attribute** or **Group Base DN Attribute** in the object class definitions. |

:::note

LDAP synchronization synchronizes not only users but also the organization tree the users belong to. The parent of an organization comes from the directory tree: an OU or group that sits under another OU or group in its DN is placed under it. Active Directory cannot place a group under another group, so a group that is a member of another group is placed under that group. An organization has one parent: when a group is a member of several groups, the group with the longest DN becomes its parent. The OIDC (Keycloak) source can also synchronize the group tree in addition to users when **Synchronize Groups** is enabled. The remaining sources (Database, API) synchronize users only. On the organization screens, the code of an organization that comes from LDAP is shown as `<provider name>: <group DN>`. The stored code does not change; hover over the code to see the full value.

:::

### Database Provider

| Field | Description |
|------|----------|
| User List Query | A parameterless SELECT statement that returns the users to synchronize. The returned columns must use the following aliases: `username` (required), `email`, `full_name`. Example: `select login as username, mail as email, display_name as full_name from users` |

### API Authentication Provider

| Field | Description |
|------|----------|
| User List URL | The endpoint that returns the list of users to synchronize. |
| HTTP Method | The HTTP method used when calling the user list endpoint. |
| Timeout | The request is terminated after this many seconds. |
| Request Body | An optional request body sent to the user list endpoint (for POST/PUT). |
| Request Headers | Optional HTTP headers sent with the user list request (e.g. Authorization). |
| Users Array JSON Path | The JSON Path expression to the user array in the response. Default: `$` |
| Username JSON Path | The JSON Path expression to the username within a user item. Required. |
| Email JSON Path | The JSON Path expression to the email within a user item. |
| Full Name JSON Path | The JSON Path expression to the full name within a user item. |

### OIDC Provider (Keycloak)

Available only when the provider's Vendor is Keycloak — see [OIDC Provider](/en/admin/identity-management/identity-providers/oidc-provider#synchronization-tab) for the full field reference.

| Field | Description |
|------|----------|
| Realm | The Keycloak realm to synchronize from. |
| Admin API Base URL | The base URL of the Keycloak Admin REST API. |
| Sync Client ID | The service-account client used to call the Admin API. Requires, at minimum, the `view-users` and `query-groups` realm-management roles — see [Keycloak Service Account Roles](/en/admin/identity-management/identity-providers/oidc-provider#keycloak-service-account-roles). |
| Sync Page Size | The page size used when paging through Keycloak's user list. Default: 250. |
| Synchronize Groups | When enabled, the realm's group tree is also synchronized as Credential organizations. |
| Role Sync Source | Realm Roles, Client Roles, or Groups — which Keycloak role assignment becomes the synchronized user's roles. |

:::note

Unlike the other three sources, users synchronized from Keycloak are **passwordless** — the password stays with Keycloak, and authentication is verified through the [OIDC Authentication](/en/develop/policies/oidc-authentication) policy's token validation, not through a stored password. See [Password Model and Username Contract](/en/admin/identity-management/identity-providers/oidc-provider#password-model-and-username-contract).

:::

## Synchronization Status and History

The screen opened from **Identity &gt; Providers &gt; Synchronization** lists LDAP, Database, API, and OIDC sources in separate tabs. Each row shows:

  src="/images/yonetici/credential-sync/credential-sync-izleme.png"
  alt="Credential Synchronization status and history"
  width="1000"
  height="245"
/>

| Field | Description |
|------|----------|
| Name | The name of the identity provider, with its description under it. A source whose synchronization is off shows a **Sync disabled** badge. |
| Schedule | The job status as a badge (Scheduled, Running, Paused, Blocked, Complete, or Error) and the cron expression under it. A source with synchronization on but no cron expression shows a **Manual only** badge. |
| Last Synchronized | The completion time of the last run. |
| Result | The result of the last run as a badge: **Succeeded**, **Warning**, or **Failed**. Hover over the badge to see the reason. While a run of the source is queued or running, this cell shows the running badge instead. |
| Upserted, Deactivated, Skipped, Errors | The record counts processed on the last run. A zero is shown in grey. A non-zero **Deactivated** count is an orange badge. A non-zero **Errors** count is a red badge. |

### Starting a Synchronization

Each row has a **Synchronize…** button. It starts a synchronization without waiting for the schedule. The start has two steps: a dialog where you select the scope, and a second confirmation.

:::warning

The **Synchronize…** button is disabled for a source whose synchronization is off (the Enable Synchronization field is off). It is also disabled while a run of that source is queued or running. Hover over the button to see the reason.

:::

:::tip

A **Full** or **Users only** run can deactivate consumers. If you are not sure about the result, first run a dry run on the edit screen of the provider: **Directory Preview &gt; Full scan (dry run)** for LDAP, **Source Preview** with **Dry run** for Database and API, **Preview Directory** for OIDC.

:::

1. Click **Synchronize…** on the row of the source. The synchronization dialog opens.
2. Check the connection block at the top of the dialog. It shows the name and the description of the source, and where the source is read from:
   - LDAP: the connection, the server address, the security (LDAPS or StartTLS), the base DN, the bind DN, the user base DN, the group base DN, and the membership mode.
   - Database: the connection, the JDBC URL, and the database user.
   - API: the user list URL, the HTTP method, and the organization list URL (when it is set).
   - OIDC: the issuer URL, the realm, the admin API base URL, the client ID, and the group synchronization setting.

   The block never shows a password or a secret. If you cannot view connections, some lines are missing and the dialog tells you so.
3. Select the scope under **What should be synchronized?**. LDAP and OIDC sources have three scopes:
   - **Full** (Recommended): users, groups/organizations and their parents are read. Then the records that left the source are handled.
   - **Users only**: consumers are created or updated. The organization tree does not change.
   - **Groups only**: only the organization tree is updated. Consumers do not change.

   Database and API sources support only full synchronization. For these sources, the dialog shows a note instead of the scopes.
4. Read the **Last run** and **Expected duration** lines. The expected duration comes from an earlier run of the source, preferably a run with the same scope. If there is no earlier run, the expected duration is **unknown**.
5. Read the information note. It changes with the scope:
   - **Full** and **Users only**: at the end of the run, consumers that are no longer in the source are deactivated or deleted, according to the deactivation mode of the source.
   - **Groups only**: at the end of the run, organizations that are no longer in the source are handled. Consumers do not change.
6. Click **Start synchronization**. A second confirmation opens. It shows the scope, the source, what the run changes, and the expected duration.
7. Click **Yes, start** to start the run. To go back to the dialog without starting a run, click **No, go back**.

While a run is queued or running, the **Result** cell of its row shows a badge such as **Running · Users only** or **Queued · Full**. The line under the badge shows the phase (**Reading the source** or **Applying the changes**) and the number of users processed so far. The page refreshes this information itself; the phase and the count change about every 15 seconds. When the run ends, the row shows the new result.

:::note

The rows learn about a running synchronization from the first page of the **Synchronization History** table below. If you move that table to a later page, the running badge is not shown until you go back to the first page.

:::

:::tip

A **Synchronize Now** button is also on the detail screen of a synchronized [credential](/en/admin/identity-management/credentials#synchronization) or [organization](/en/admin/identity-management/organizations#synchronization), for users with identity management permission. It starts a full synchronization of the entire source provider of the record, not only that one record.

:::

### Run History

Beyond the last-run snapshot in the table above, Apinizer keeps a permanent record of every synchronization run. A **Synchronization History** card appears at the bottom of two screens:

- The **Identity &gt; Providers &gt; Synchronization** screen described above — the card here lists runs from **every** source in the current project, with a **Source** column identifying which provider each row belongs to.
- Each provider's own view screen (LDAP Active Directory, Database Provider, API Authentication Provider, OIDC Provider) — the same card, scoped to **that source only**, without the Source column.

Both surfaces show the same columns, paged from the server (10 / 20 / 50 rows per page):

| Column | Description |
|------|----------|
| Source | The provider's name and type. Shown only on the project-wide Synchronization screen. |
| Started | The run's start time. |
| Duration | How long the run took. |
| Trigger | A **Scheduled** or **Manual** badge. For a manual run, the username of the administrator who started it is shown under the badge. |
| Scope | The scope of the run as a badge: **Full**, **Users only**, **Groups only**, or **Reconcile apply**. |
| Result | The result as a badge: **Success**, **Warning**, or **Failed** — see below. A run that has not ended shows **Queued** or **Running**. |
| Upserted, Deactivated, Skipped, Errors | The record counts processed by this run. A zero is shown in grey. A non-zero **Deactivated** count is an orange badge. A non-zero **Errors** count is a red badge. |
| Issues | The number of user-level records (warnings and errors) of the run, as a badge such as **3 issues**. Click the badge to open the issues panel. |
| Reason | A translated explanation of the result. |

Every run is recorded — including a run that failed outright and a run that was rejected during pre-checks before synchronization could even start (for example, a missing connection or a required field left empty). The run an administrator is looking for is often the one that didn't work.

:::note

A **Warning** result means the run finished without error, but the source returned **zero users**. To keep a transient source outage from causing a mass deactivation, this run's deactivation/reconciliation step is skipped entirely — no credential is upserted, deactivated, or skipped-and-counted for it. Check the source's user filter, base DN, or query settings.

:::

The source name recorded in history is a **snapshot** taken at the time the run executed — if the provider is later renamed or deleted, its history rows keep the name they had when the run happened.

#### Issues of a Run

Click the **N issues** badge in the **Issues** column. The issues panel opens on the right side of the screen and covers at least half of it. The table stays in place behind the panel.

The panel contains:

- **Header**: the source name, the start time, the duration, and the result, scope, and trigger badges of the run.
- **Summary boxes**: Upserted, Deactivated, Warnings, and Errors.
- **Reason**: the explanation of the run result, as an information note.
- **Severity filter**: **All**, **Warning**, or **Error**, each with its record count.
- **Records**: one card per record, with the severity badge, the time, the user, and the reason.

The panel shows the first 50 records of the run. The **Warnings** and **Errors** boxes and the filter counts cover these records. If the run wrote more records, the panel shows how many of the total are on screen. If the server kept only part of the records, a warning tells you so.

#### Retention

History records are **not deleted automatically**. An administrator can turn on automatic cleanup for the **Identity Synchronization History** entry on the [Application Log Cleanup Tasks](/en/admin/audit-compliance/application-log-cleanup-tasks) screen; while it stays off (the default), no history record is ever removed regardless of age.

#### Audit Attribution

When a synchronization run changes a credential, the resulting entry in [Audit Records](/en/admin/audit-compliance/audit-records) shows its Principal as `sync:<SOURCE_TYPE>:<source name>` (for example `sync:LDAP:corp-ad` or `sync:OIDC:keycloak-prod`) instead of the generic `SYSTEM` — so a synchronization-driven change can be told apart from one made by a person, and traced back to the source that made it. The administrator who manually triggered the run is not part of this value; that name appears in the **Trigger** column of the Run History table instead.

## Behavior and Safety Notes

:::info

- If a manually created (non-sync-managed) credential's username also exists in the source, synchronization does **not** overwrite that record; an administrator must resolve the conflict.
- If a credential is already managed by another source (for example LDAP), a different source (for example Database) does not take it over.
- If the same username already exists in another project, synchronization does not create a new credential with that username in a different project.
- If the user list cannot be fetched from the source (connection error, etc.) or the source returns zero users, the deactivation step for that run is skipped so that a transient source outage cannot cause a mass deactivation.

:::
