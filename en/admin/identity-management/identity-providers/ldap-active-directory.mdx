## List

Directories that Apinizer uses to authenticate API calls and to synchronize consumers are listed on this screen. Use the search box to filter by name, and the two filters next to it to narrow the list further.

| Filter | Description |
| --- | --- |
| Status | All statuses, Enabled, or Disabled. Reflects the provider's Enable Synchronization setting. Hover over the column header for the same explanation. |
| Directory Type | All directory types, Active Directory, OpenLDAP, or Other. Comes from the Directory Type of the provider's connection pool. |

The table shows the following columns.

| Column | Description |
| --- | --- |
| Name | The provider's name and description. |
| Directory Type | A badge with the Directory Type of the connection pool. Empty when you cannot view the connection, or the pool no longer exists. |
| Server | The server address of the connection. |
| Base DN | The Base DN of the connection. |
| Status | An Enabled or Disabled badge for the provider's synchronization setting. |
| Project | Only in admin (global) scope. The name of the project the provider belongs to. |

Each row has a single **⋮** menu, in this order: **Open**, **Duplicate** (if you can manage identity providers), **Delete** (same permission), **Move to Global** (same permission, for a provider that is not already global), and **Export** (if you can export/import identity data).

Click **+ New** at the top of the screen to create a provider. Click **Import** to bring one in from an [export package](/en/admin/secrets-management/export-import).

### Configuring a Section

1. Click **Configure** on the card of the section. A panel opens on the right.
2. Change the fields.
3. Click **Save**. **Cancel** discards your changes.
4. Check the list of changes in the **Review Changes** dialog.
5. Confirm the dialog. The provider is saved and deployed to every environment where it is used.

If you close the dialog without confirming, nothing is saved.

### New Provider

**+ New** opens a page that holds all cards in one form. The top of the page has **Test**, **Directory explorer** and **Save** buttons. **Test** and **Directory explorer** work with the values on the form, including values you have not saved yet.

The Users, Groups, OUs and Synchronization sections appear on the form as a summary. **Configure** opens a section in a panel. **Apply** in the panel writes your change into the form. **Save** saves the provider.

With Advanced authentication, **Save** stays disabled while there is no group definition and OU synchronization is off. Define the groups, or turn on the OUs section.

### Synchronization history

The table is the same as the one on the project-wide Synchronization screen, without the Source column. - Click an **N issues** badge to open the issues panel of that run.
- While one of the listed runs is queued or running, the card reloads itself every few seconds.
- Click **Open Synchronization screen** to see the provider's full run history.

### Users

The card shows a summary of the User Object Class Definition. **Configure** opens the definition in a panel. This section is used with Advanced authentication only.

| Field | Description |
| --- | --- |
| User Object Class Names | The class name(s) used to filter users. Separate more than one with a comma. Example: `person,inetOrgPerson` |
| User Base DN Attribute | Used instead of the connection's Base DN when searching and loading users, if set. Example: `cn=users,dc=ad,dc=example,dc=com` |
| Custom Filter Attribute | An additional filter used together with the connection's filter when fetching users. Example: `(&(objectCategory=Person)(sAMAccountName=*))` |
| Search Scope | The level at which the search runs under the base DN. |
| Attribute mapping: Login Name Attribute | The attribute holding the user's login name. Example: `uid` |
| Attribute mapping: First Name Attribute | The attribute holding the user's first name. Example: `givenName` |
| Attribute mapping: Last Name Attribute | The attribute holding the user's last name. Example: `sn` |
| Attribute mapping: Full Name Attribute | The attribute holding the user's full name. Example: `cn` |
| Attribute mapping: E-mail Attribute | The attribute holding the user's e-mail address. Example: `mail` |
| Attribute mapping: Membership Attribute | The attribute holding the user's group memberships. Example: `isMemberOf` |
| Unique ID Attribute | The attribute that holds the user's permanent identity. Options: `objectGUID` (Active Directory) and `entryUUID` (OpenLDAP, 389 Directory Server / FreeIPA). When a user is renamed or moved, the same consumer record is updated. If the field is empty, users are matched by username. If you change it, records are matched again by username in the next sync. |
| Attributes To Fetch | Extra attributes read for the user in addition to authentication. See [below](#attributes-to-fetch). |
| Account State Attribute | The attribute that tells whether the account is switched off in the directory. Example: `userAccountControl` on Active Directory, `pwdAccountLockedTime` on OpenLDAP, `nsAccountLock` on 389 Directory Server / FreeIPA. If you leave it empty, the account state is not read, and synchronization never deactivates a consumer because of it. |
| Account State Format | How to read the value of that attribute. Picking the wrong format does not raise an error. Every locked account silently shows as active. Make sure the format matches your directory. |

:::note Disabled directory accounts

An account switched off in the directory is switched off in Apinizer too, once synchronization reads it. When the account is switched on again in the directory, synchronization switches it back on automatically. An account you switched off yourself in Apinizer is never touched by synchronization.

:::

#### Attributes To Fetch

When authentication is performed with LDAP, these attributes are read for the user in addition to authentication, if present:

- If the provider is used to generate a JWT, the attributes and their values (excluding null ones) are added to the JWT as claims.
- If the provider is used with plaintext, basic, or digest authorization, the attributes and their values are added to the message context as custom variables. The key is prefixed by `#clientLDAPAttribute#.`. For example, a `mail` attribute becomes the key `#clientLDAPAttribute#mail`.

A binary attribute is returned as text. Active Directory `objectGUID` comes in GUID form, `objectSid` in `S-1-5-21-...` form, and any other binary attribute as Base64.

### Groups

The card shows a summary of the Group Object Class Definition. **Configure** opens the definition in a panel. This section is used with Advanced authentication only.

:::warning

When the **Enabled** switch is off, synchronization does not read groups and keeps the existing group organizations. Sign-in still reads the user's groups. If you turn the switch off, users linked only to a group organization lose that link at the next sync.

:::

| Field | Description |
| --- | --- |
| Enabled | Whether synchronization reads groups. When on, each group is opened as an Apinizer organization. |
| Group Object Class Name | The class name used to filter groups. Example: `groupOfUniqueNames` |
| Group Base DN Attribute | Used instead of the connection's Base DN when searching and loading groups, if set. |
| Custom Filter Attribute | An additional filter used together with the connection's filter when fetching groups. |
| Search Scope | The level at which the search runs under the base DN. |
| Attribute mapping: Group Name Attribute | The attribute holding the group's name. |
| Attribute mapping: Member Attribute | The attribute holding the group's members. The value must match the group object class: `member` for `groupOfNames` and Active Directory `group`, `uniqueMember` for `groupOfUniqueNames`, `memberUid` for `posixGroup`. With a mismatched value, every group is read as empty and no user is linked to an organization. **Configuration issues** in the Test panel reports this as **LDAP-I14**. Active Directory returns the members of a group with more than 1500 members in parts (`member;range=`). Apinizer reads all parts. |
| How is membership determined? | Selects how a user's group membership is resolved: the current behavior (default), automatic detection (recommended), from the user's own membership attribute, from the group's member list, from the organizational unit the user is placed under, or both the OU and every membership list. If you are not sure, leave it as is or choose automatic detection. This choice only affects how memberships are read. Nothing changes in your directory. |
| Member Strategy | The strategy used to find a group's members, USER DN or USER LOGIN. Not shown when membership is determined automatically or from the organizational unit tree. The format of each member value is then detected on its own. |
| Unique ID Attribute | The attribute that holds the group's permanent identity. Options: `objectGUID` (Active Directory) and `entryUUID` (OpenLDAP, 389 Directory Server / FreeIPA). When a group is renamed or moved, the same organization record stays with its limits and members. If the field is empty, groups are matched by DN. |
| Attributes To Fetch | Extra attributes read from each group. |

### OUs

The OUs section appears for Advanced authentication only. It is a separate card next to Groups. Synchronization opens each OU as an Apinizer organization. A user belongs to the OU its entry sits under. The OU fields have no membership attribute.

:::warning

When the **Enabled** switch is off, synchronization does not read OUs and keeps the existing OU organizations. If you turn the switch off, users linked only to an OU organization lose that link at the next sync.

:::

| Field | Description |
| --- | --- |
| Enabled | Whether synchronization reads OUs. If there is no OU definition, the card tells you to turn the switch on to read OUs with the default values, or to select **Configure**. |
| OU Class Name | The object class of the OU entries. Example: `organizationalUnit` |
| OU Base DN | The directory node the OU search starts from. If empty, the connection's Base DN is used. |
| Custom Filter Attribute | An additional filter used together with the connection's filter when fetching OUs. |
| Search Scope | The level at which the search runs under the base DN. |
| OU Name Attribute | The attribute that holds the OU name. It becomes the organization name. Example: `ou` |
| Unique ID Attribute | The attribute that holds the OU's permanent identity. Options: `objectGUID` (Active Directory) and `entryUUID` (OpenLDAP, 389 Directory Server / FreeIPA). When an OU is renamed or moved, the same organization record stays with its limits and members. If the field is empty, OUs are matched by DN. |

In a new provider, the **Groups** and **OUs** switches both start on. In an existing provider, **Groups** stays on and **OUs** stays off.

### Synchronization

The card shows a summary of the synchronization profile: Enable Synchronization, Schedule, Deactivation Mode, Scope: users, Scope: groups / organizations, Scope Exit Policy, Deactivation thresholds and the Without stable identity guard. **Configure** opens the profile in a panel:

| Field | Description |
| --- | --- |
| Enable Synchronization | See [Provider Synchronization](/en/admin/identity-management/identity-providers/credential-sync#sync-profile). |
| Base DN (from the connection) | Read-only. See [Provider Synchronization](/en/admin/identity-management/identity-providers/credential-sync#ldap-active-directory). |
| Cron Expression | See [Provider Synchronization](/en/admin/identity-management/identity-providers/credential-sync#sync-profile). Leave it blank to allow only manual synchronization. |
| Deactivation Mode | See [Provider Synchronization](/en/admin/identity-management/identity-providers/credential-sync#sync-profile). |

Below these, a **Synchronization Scope** section narrows which users and which groups/organizations this provider synchronizes. For each, choose the matched field (such as Username or Path), the pattern type (Glob or Regular Expression), and the patterns to include or exclude. A record outside the scope is not treated as removed from the source. The **Reconciliation Safety Net** below it decides what happens to that record:

| Field | Description |
| --- | --- |
| Scope Exit Policy | Applied to a record that still exists in the source but no longer matches the scope: Leave as is, Disable, or Tombstone. |
| Deactivation Threshold (%) / Deactivation Threshold (records) | When the records that reconciliation would deactivate exceed either the percentage or the count, reconciliation pauses for approval instead of running. The default is 20%. 0 turns a threshold off. |
| Do not deactivate or delete when the source returns no stable external identity | Without a stable external identity, the only key is the username, so a user renamed in the source looks removed. While this is off, the current behavior is kept and the run only records a warning. |

This scope and safety-net editor is shared by all four provider types (LDAP, Database, API, OIDC).

:::note

This page has no control to start a synchronization run. Open the [Synchronization screen](/en/admin/identity-management/identity-providers/credential-sync#starting-a-synchronization) to start one.

:::

### Support Bundle

You can download a **Support bundle** from the source row on the [Provider Synchronization](/en/admin/identity-management/identity-providers/credential-sync) screen. It is an anonymized diagnostic archive of this LDAP source. Directory names, user names and e-mail addresses are replaced by hashes. The password never enters the bundle. ## Test Panel

A single **Test** panel covers the connection, the directory read, one user's sign-in and membership, and the synchronization preview. On a saved provider, open it from the **⋮** menu. On the new provider page, open it with the **Test** button at the top.

The panel uses the values on screen. Nothing is saved. On a saved provider's page these are the saved values. On the new provider page these are the values currently on the form.

The panel has four groups. With Advanced authentication all four groups appear. With Simple authentication only **Connection** and **Try with a user** appear.

The panel resolves connection variables (`${variable}`) with their API Manager environment values. This is the only environment the panel can use, so no environment selector appears. If a variable has no value in the API Manager environment, the test says so.

### Connection and Read

The **Run connection and read** button in the **Connection** group (**Run connection test** with Simple authentication) runs the steps in order. Each step reports its own result on its own row. So you can see exactly where the connection breaks.

When a step fails, the steps that depend on it get the result **Not run: a preceding step failed, so this step could not be measured.** Earlier successful steps stay as they are. The search of a section that is switched off is not run either. For example, with the Groups section off, the Group Search row says **Not run: the Groups section is off.**

Click a row to open its explanation, suggestion and a copyable technical detail.

Steps of the **Connection** group:

| Step | What it checks |
| --- | --- |
| Configuration Check | Consistency of the form fields: address format, TLS options, required fields |
| Server Connection | Whether the LDAP server can be reached over the network |
| Secure Connection (TLS) | The LDAPS/StartTLS handshake. Not needed when the connection is configured without TLS |
| Service Account Sign-in | Signing in with the service account configured on the connection |
| Directory Information | The directory type and tree roots the server reports about itself |
| Schema Check | Whether the configured object classes and attribute names exist in the directory schema |
| Paged Search Support | Whether the server can return large result sets page by page |

Steps of the **Read** group (Advanced authentication only):

| Step | What it checks |
| --- | --- |
| Base DN Read | Whether the root the searches start from is readable |
| User Search | Whether the configured user filter returns at least one record |
| Group Search | Whether the configured group filter returns at least one record |
| OU Search | Whether the configured OU filter returns at least one OU |
| Identity Attribute | Whether the Unique ID Attribute is filled and unique in the sampled records. Not run when no attribute is selected |
| Attribute Permissions | Whether the service account can see all of the requested attributes |
| Membership Resolution | Whether the sampled users resolve to an organization under the configured membership mode. Not run when the OU search returned no OU |

The **Read** group has two more buttons:

| Button | Description |
| --- | --- |
| Configuration issues | Reads a small part of the directory and opens the **Directory Preview** window. The window has **Users**, **Groups**, **Membership** and **Issues** tabs. The **Issues** tab lists known configuration issues. See [Issues](#issues). |
| Sample users and groups | Reads a few users and groups with the values on screen. It shows at most 10 users for each user object class, at most 5 groups for each group object class and at most 10 users of each group. |

### Try with a User

Enter a **User name**. Optionally enter a masked **Password**. Click **Run**.

- Without a password, the panel only searches for the user.
- With a password, the panel also tries to sign in. The password is never stored or displayed.
- With Simple authentication the password is required. The panel only tries the sign-in. The result shows as **Sign-in succeeded** or **Sign-in failed**.

With Advanced authentication, the panel shows these items step by step:

- The search filter that found the user, and the raw attributes read from the user entry (as far as the service account can see them)
- The membership from the user entry, from the group member lists and from the organizational unit tree. Each one appears as its own step with its filter and result
- The result used: which source counts, and the organization it produces
- What would happen if this user signed in to the management console: the project teams the user joins and the system rights the user gets
- What would happen if this user called an API: whether a matching consumer exists, its organization and its active limit assignments
- The account status, when an Account State Attribute is configured

The **Show in explorer** link next to the user's DN opens the user in the [Directory explorer](#directory-explorer). The **Detailed view** button opens the same membership check in a dialog, together with the user's details. The details block shows **Login Name**, **Full Name**, **First Name**, **Last Name** and **E-Mail**, and a name badge next to each group's distinguished name.

### Sync Preview

The **Sync preview** group appears only with Advanced authentication. **Start dry run** scans the whole directory with paging and shows what synchronization would change. It writes no record. A large directory can take a few minutes.

The panel first summarizes how many users, groups and OUs were read. The counts below it are:

| Count | Description |
| --- | --- |
| Would be created | Consumers the synchronization would create. |
| Would be updated | Consumers the synchronization would update. |
| Would be deactivated | Consumers the synchronization would deactivate. |
| New organizations (group) | New organizations that would come from groups. |
| New organizations (OU) | New organizations that would come from OUs. |
| Organizations to update | Existing organizations that would be updated. |
| Out-of-scope groups | Groups the scope filter would leave out. |
| Would stay without an organization | Users that no organization would be linked to. |
| Username used by another provider | The same username already belongs to a consumer that another identity provider syncs in this project. The sync does not take these records over. This happens when two domains have the same username. The first five usernames are listed. |
| Username of a manually added consumer | A consumer with the same username was added by hand in this project. The sync does not overwrite it. Remove or rename it to let the sync manage that user. |

If the scan could not be completed, the list is partial. The deactivation count is not estimated then and is reported as zero.

**Open the full report** shows the detailed report of the scan in the **Directory Preview** window.

## Directory Explorer

The **Directory explorer** lets you browse the directory read-only. Nothing is saved or written. On a saved provider, open it from the **⋮** menu. On the new provider page, open it with the **Directory explorer** button at the top. On a saved provider the explorer uses the saved values. On the new provider page it uses the values on the form. You need the permission to manage identity providers.

The explorer has a tree on the left and an attribute panel on the right.

- **Tree**: The tree starts at the Base DN of the connection. Opening a node reads one level. If a level has more entries than shown, **Show more** loads the next page.
- **Attribute panel**: When you select an entry on the left, the panel shows:
  - The DN with a copy button
  - The entry type: User, Group, Organizational unit, Container, Domain or Other
  - The Apinizer counterpart: the **Consumer** or **Organization** name, or **Not in Apinizer**
  - An attribute table with **Attribute** and **Value** columns. **All values** opens the values of a multi-valued attribute.
  - The identity attribute row is highlighted and carries the **Identity attribute** label. If no identity attribute is selected for the entry type, the panel says so.
  - Binary attributes appear as text: `objectGUID` and `objectSid` in text form, others as their size.
  - Password attributes are masked. Their values are not shown.
  - A warning appears for an entry outside the sync scope.
- **Search**: Type a name or an LDAP filter in the search box. A name is searched in `cn`, `ou`, `uid`, `sAMAccountName`, `displayName` and `mail`. Text that starts with `(` is sent as an LDAP filter. Example: `(mail=*@example.com)`. The search runs under the Base DN of the connection.
- **Filter**: The list has three options.

| Filter | Description |
| --- | --- |
| All entries | Every entry in the directory. |
| Only the sync scope | The entries the sync reads with the current settings. |
| Users without an organization | Users that cannot be linked to any organization. Search is off with this filter. If the directory cannot be read in full, users of the groups or OUs not read may show here without an organization. |

## Issues

You may see the following codes in the **Configuration issues** list of the Test panel and in the **Detailed view** dialog:

| Code | Meaning | What to do |
|------|---------|------------|
| I01 | None of the users read carry the configured membership attribute. | On Active Directory this attribute is usually `memberOf`. If your directory does not publish group membership on the user entry at all, switch **How is membership determined?** to a mode that uses group member lists or the organizational unit tree. |
| I02 | Group member values are in a different format than the configured strategy expects, so the reverse lookup can never match. | Switch **How is membership determined?** to automatic detection. The format of each member value is then detected on its own. |
| I03 | Some of the groups read are organizational units and carry no member list. | In this layout a user belongs to the organizational unit it is placed under. **Apply** moves the group definition to the OUs section: OUs on, Groups off. |
| I04 | None of the member values match any of the users read. | The user search root and the groups are probably looking at different parts of the tree, or the user name attribute does not match the format used in the member values. Check the Base DN and the attribute mapping. |
| I05 | The group search returned no records for the configured object class. | Check the group object class and the group search root. If your directory is organized by organizational units, select **Apply** to turn on the OUs section. This issue is not listed when the Groups section is off. |
| I06 | The server does not support paged search results. | Synchronization can only read the first page, so some users will be missing and records will not be reconciled correctly. Enable paged results on the directory server. |
| I07 | The login name attribute is empty on some of the users read. | The user name is taken from this attribute. On Active Directory it is usually `sAMAccountName`. Check the Login Name Attribute field. |
| I08 | The directory returned a referral during the search. | Some records may live on another server and are not read. Consider pointing the connection at a server that holds the whole tree. |
| I09 | On Active Directory the primary group of a user is not listed on the user entry. | This is normal, and no action is needed. A user that appears to be missing from a group such as Domain Users is affected by this. |
| I10 | A member value points to another group (nested group). | Nested groups are detected but not resolved. Members of the inner group are not treated as members of the outer one. |
| I11 | No Unique ID Attribute is selected. The suggested attribute for this directory is shown: `objectGUID` on Active Directory, `entryUUID` on OpenLDAP and 389 Directory Server / FreeIPA. Without it, a renamed or moved record is treated as a new one. | Open the **Configure** panel of the section. Select the suggested attribute in the **Unique ID Attribute** field. The Users, Groups and OUs sections each have their own field. |
| I12 | Configured attributes are not defined in the directory schema. | The server silently ignores an attribute it does not know. Check the spelling and whether the attribute belongs to a different directory product. |
| I13 | Requested attributes came back empty on every user read. | The service account is probably not allowed to see them. Check the access rights of the account used to connect. |
| I14 | None of the groups read has a member in the configured Member Attribute, although the group object class normally keeps its members in a different attribute. Every group looks empty, so no user is linked to an organization. | Set **Member Attribute** to the value the group object class uses: `member` for `groupOfNames` and Active Directory `group`, `uniqueMember` for `groupOfUniqueNames`, `memberUid` for `posixGroup`. On the new provider page, the **Apply** button writes it for you. |

Each issue has a suggestion. On the new provider page, some issues have an **Apply** button. The button writes the suggestion to the form. Review it and save. On a saved provider's page, a note replaces **Apply**. It tells you to open the **Configure** panel of the section to apply the suggested value.

## Synchronization Scope

The **Matched Field** options for filtering which records are synchronized have worked examples:

| Matched Field | Example |
|---|---|
| Username | `svc-*` |
| E-mail | `*@example.com` |
| Path (DN / group path) | `/Groups/*`. The DN is read right to left, written as `/Eng/Dev`, and `dc=` components are dropped |
| Name | `developers` |

A **Try a pattern** box evaluates a sample value against the current patterns. It saves nothing and does not query the directory.

Group and organization scope filters are enforced during synchronization. A group excluded by the filter is not created as an organization. An existing organization that falls out of scope is not deleted or deactivated. It is left untouched. A plain literal pattern (no `*` or `?`) is not rejected during synchronization.

## Synchronization Behaviors

- A consumer that synchronization previously deactivated, and that later reappears in the source, is automatically re-enabled. A consumer you deactivated by hand is never touched by synchronization.
- When a user belongs to more than one in-scope group or OU, only one organization is linked: the deepest one. See [How the Organization Link Is Determined](/en/admin/identity-management/identity-providers/credential-sync#how-the-organization-link-is-determined) for the full winner rule and the exceptions to the every-run rewrite.
- A group or OU whose name contains characters such as `,` `+` `;` `"` `\` or a leading `#` is synchronized as well.
- If the source directory carries two entries with the same login name, the second one is skipped and recorded as an issue. The first one is kept.
- If an organization with the same distinguished name already exists as a manually created record, synchronization does not create a duplicate organization. It links users to the existing one and records an issue. The organization stays under manual management until you hand it over.
- If the synchronization schedule cannot be registered, for example because of an invalid cron expression, the error is shown immediately when you save. It does not fail silently on the next scheduled run.
- A run that fails, or in which users could not be attached to an organization, produces an issue you can review from **View issues**.

If two different LDAP sources contain the same directory entry (the same DN), synchronization from one source does not update the other source's organization record. Each source's organization record belongs to that source alone. A group present in both directories is kept and reconciled separately per source.

:::note Paged results

During synchronization Apinizer reads the directory page by page using the LDAP **PagedResults** control (500 entries per page). If the directory server does not support that control, or does not allow it to be used, only the first page can be read. The run is then reported as **Warning**. As a safety measure, no consumer is deactivated or deleted. The records that were read are upserted normally. The same safety measure applies when even a single record read from the directory cannot be converted: the run counts as incomplete and deactivation/deletion is skipped. For a full synchronization, enable paged result support on the directory server or raise its server-side size limit.

Even when the directory server appears to support paged results, the same safety measure applies if paging stalls or repeats. The run is still treated as incomplete and deactivation/deletion is still skipped.

A directory that **refuses** the search is reported differently. If the configured base DN does not exist, or the bind account may not search under it, the run ends as **Failed** with a reason naming that base DN. Both are settings an administrator can correct, so they are kept distinct from a server that simply refuses paging.

:::

## Multiple Domains

If you synchronize more than one Active Directory domain into the same project, create one LDAP provider for each domain. In the user object class definition, use `userPrincipalName` as the **Login Name Attribute**. The same `sAMAccountName` can exist in two domains. `userPrincipalName` also contains the domain name.

If two providers produce the same username, the second provider skips that record during synchronization. To see this without running a synchronization, check the **Username used by another provider** count in [Sync Preview](#sync-preview).

## Why Was an API Request Rejected?

When an API consumer cannot be verified through this source, the detailed record of the request shows the reason for the authentication failure: sign-in failed, user not found, required role missing, or directory unreachable. When the directory cannot be reached at all, the request is rejected with a separate error that says the service is unavailable at that moment. It is not rejected as if the username or password were wrong. See [API Traffic Tab](/en/develop/monitoring-analysis/api-traffic#authentication-failure-reason).

## Troubleshooting

### Users and groups come in, but the user-to-organization/group link is empty

1. Open the **Test** panel. Enter the affected user name in **Try with a user** and click **Run**. It shows which of the three membership sources found a match and which did not.
2. In the **Read** group, open **Configuration issues** and look for I01, I02, I03 and I04. Each one describes a variant of this problem with its own fix.
3. Check **How is membership determined?** in the group definition. On Active Directory, the usual choice is the mode that reads the membership attribute (`memberOf`). When groups are organizational units, choose **Our groups are OUs; a user belongs to the OU it is in**.
4. Turn on **Diagnostic Mode** on the connection to log every search made. Read the log while you reproduce the problem.
5. If the problem needs support, download a **Support bundle** from the Synchronization screen.

## Backward Compatibility

Existing providers keep working as before. **How is membership determined?** stays at **Current behaviour (default)** for them, and organization assignments do not change. The new membership modes apply only when you choose one yourself.

- The **Groups** switch stays on in existing providers. The **OUs** switch stays off. The first synchronization after the upgrade does not open a new OU organization.
- For a provider whose group class is `organizationalUnit` and whose membership comes from the organizational unit tree (DN scope only), the group definition is copied to the OUs section. OUs turn on and Groups turn off. The group definition stays in place for sign-in.
- If the **Attributes To Fetch** list of a user or group class holds `objectGUID` or `entryUUID`, the upgrade writes that value into the **Unique ID Attribute** field. The list stays as it is. If the list holds neither attribute, the field stays empty.
- During a rolling upgrade where the API Manager is upgraded before the gateway workers, the workers keep resolving membership the old way until they are redeployed.
