:::info Where to Find It

The **API Client Migration** screen is reached from **Admin → Identity & Security → Credential Management → API Client Migration**. It is the operator view of the inventory and migration mechanism described in [Credentials — Legacy Records: Inventory and Migration](/en/admin/identity-management/credentials#legacy-records-inventory-and-migration); this page only describes the screen itself — see that page for what inventory and migration cover and do not cover.

:::

## Scope Selection

The project selector at the top of the screen determines which project the scan covers. The **All projects (installation-wide, system administrator only)** option removes the project filter entirely and scans every legacy record in the installation; it is available only to users with system administrator permission.

## Inventory Table

For every legacy record in the selected scope, the table shows:

| Column | Description |
|------|----------|
| Credential | The legacy record's username (and display name, if any). |
| Application | The portal application the record is linked to (if any). |
| Decision | One of three values below — see [Decision Values](#decision-values). |
| Labels | Evidence badges showing that the record behaves like a client, or that something blocks its migration. These labels are not mutually exclusive; more than one can appear on the same row. |
| Targets | The number of targets that make up the record's access axis. |
| Migrated | Marked when an API client derived from this record already exists. |

Hovering the badge in the **Decision** column shows more detail as a tooltip: the reason for a **Blocked** decision, or the migration notes on a **Migrate** or **Consumer only** row (a skipped access rule, a Consumer-owned fallback, a username collision this record won).

### Decision Values {#decision-values}

| Decision | Meaning |
|-------|--------|
| **Migrate** | The record is converted to an API client in the apply step. A target whose access rule cannot be resolved (for example, an API Proxy that no longer exists) no longer stops this: that one rule is skipped and reported in the tooltip, while the rest of the record is still carried over. When the record's owning application cannot be settled either, the client is derived Consumer-owned instead — labeled **Ambiguous owner**. A record reached through an HTTP Digest or an mTLS policy is migrated the same way and carries an informational label (**Reached via HTTP Digest**, **Reached via mTLS**); a Digest-reached record is served from the migrated generation's encrypted platform copy. |
| **Consumer only** | The record stays a Consumer; no API client is derived for it, because a client would have nothing of its own to authenticate with. This covers a record verified against an external identity source (LDAP, a database, an API), a record matched by an identity provider claim (labeled **IdP-matched identity**), a record with no usable stored secret, and every record but the oldest sharing a username with another record (labeled **Client id collision**). This is not a warning — the record keeps working exactly as it did before. |
| **Blocked** | The record has no username, so there is no identifier to carry over. This is the one case that stops a record's migration outright. |

"Permanent legacy" and "Out of scope" are no longer produced by a new scan; they may still appear in a report generated by an earlier version.

## Dry-Run and Apply

The toolbar at the top of the screen has **Refresh** and **Dry-Run** buttons.

**Dry-Run** reports what a real run would do without writing anything. The report opens in a dialog with three parts:

1. **Summary counters** — the number of records scanned, the number of API clients that would be created, how many fall into each decision, how many access grants and restriction rows would be written, and how the client id registry would change.
2. **Per-credential outcome table** — for each row: username, outcome (Migrated / Already migrated / Skipped — blocked / Skipped — consumer only / Planned / Failed), reason, and the number of management keys and restriction rows that would be created.
3. **Per-application grant table** — how many grants would be created for each portal application, how many already exist, and which credentials contributed or were skipped.

The same dialog is also used to trigger the real conversion, with the **Apply** button, offered only from inside a dry-run's report; the button is shown only while the report has not yet been applied and the user has identity management manage permission. Pressing **Apply** opens a confirmation naming the scope the conversion will be applied to — once confirmed, typed API clients, grants and restriction rows are written; there is no separate apply screen and no way to apply without first reading a dry-run of the same scope. **This action cannot be undone.** A notification is shown when the apply completes, and the inventory table refreshes itself, so rows already converted show as migrated immediately.

:::warning

If the inventory changed between the dry-run and the apply — for example, a record was migrated manually, or a new legacy record was added — re-run **Dry-Run** before applying to see the current report.

:::

## Secret Carry-Over {#secret-carry-over}

This step is not on this screen yet in this version — it is run directly against the API described below — but it is the natural next step after Apply above, since a client the migration creates starts out in Draft with no secret of its own at all, exactly like one created by hand.

For every such client, the legacy credential's password is read once and stored as that client's first secret: the same client id and the same password the customer already uses keep authenticating, now through the new client as well, without a forced reset and without the customer noticing anything. The legacy credential itself is never modified, and every token issued before or after this step keeps working until it expires on its own — this step never revokes anything.

The run is controlled by three separate, opt-in switches:

1. **Dry run** (the default) classifies every candidate and writes nothing.
2. **Apply** actually creates a secret for each eligible client. On its own this changes nothing at runtime: the client stays in Draft, the legacy credential keeps answering exactly as before, and the two paths simply exist side by side.
3. **Activate** — a separate choice, meaningful only together with Apply — additionally moves to Active every Draft client whose secret was just carried, or that already had one. This is the one switch that makes a client start being verified through the new path instead of the old one, so it can be turned on for a single project first and extended once that project looks right.

```
POST /api/api-clients/migration/secrets/carry-over?projectId=<project>&apply=false|true&activate=false|true
```

Each candidate client comes back with one of eleven outcomes:

| Outcome | Meaning |
|---------|---------|
| Would carry | Dry run only: a secret would be created from the legacy password. |
| Carried | A secret was created from the legacy password and deployed; the legacy credential is unchanged. |
| Carried as-is | The stored password was not a ciphertext of this installation's key — it was stored as plain text, or sealed under a different installation's key — so it was carried across exactly as stored, byte for byte, since that is what the legacy runtime itself expected. Rotating the client's secret afterward is recommended. |
| Carried as variable reference | The legacy password was a variable or expression reference (a value starting with `${` or `#{`) rather than a literal value; the reference itself is carried over as a "secret reference" generation, and the gateway resolves it on every request, exactly as it resolved it on the legacy password field. An unresolvable reference verifies nothing — the variable's name is never accepted as the secret itself. |
| Already has material | The client already has a secret of its own; running again changes nothing. |
| Source missing | The legacy credential this client was created from no longer exists. |
| Skipped — external identity source | The legacy credential authenticates through LDAP, a database, an API, or an external identity provider rather than a locally stored password — there is no password to carry. |
| Skipped — blank secret | The legacy credential has no password stored, or it is empty once read. |
| Skipped — revoked | The client has been revoked and takes no new material. |
| Failed — decrypt | The stored password looked like a ciphertext of this installation's key but decrypted to nothing — a corrupt value; nothing is carried for this row. |
| Failed — issue | The secret could not be created — for example a concurrent change to the same client — and nothing was written for this row. |

"Skipped — reference not supported" is no longer produced: a variable or expression password is now carried over as **Carried as variable reference** instead of being left on the legacy path.

:::note

A carried-over secret is always stored in [Encrypted mode](/en/admin/identity-management/credentials#secret-storage-mode), so it stays revealable even on an installation with no recovery key configured — a platform-encrypted copy is kept regardless. A recovery key, when configured, additionally seals a recovery envelope; its absence no longer makes a carried-over secret one-way. This does not apply to a **Carried as variable reference** row: there is no local secret material to recover — the value is resolved by the gateway at request time — so its recovery state simply reads unavailable.

:::

None of this is disruptive by itself. The legacy credential is left exactly as it was, every token already issued is untouched, and nothing is revoked. Running Apply without Activate carries the secret ahead of time with zero effect on live traffic; Activate is the only switch that changes what a live request actually does, and it can be limited to one project at a time before being extended further.

See [API Client Secret Migration](/api-reference/credentials#api-client-secret-migration) for the full parameter and response reference.

## New Consumers Are Migrated at Creation

A Consumer created after this version — from this screen, from the portal, through APIops, or by CSV import — that authenticates with a locally stored password rather than through an external identity source goes through the same three steps automatically, at the moment it is created: it is classified, its API client is derived, and the legacy password is carried over and the client activated. No operator action is needed; the derived client shows up on the Consumer's own **API Clients** tab right away.

A Consumer the inventory would decide **Consumer only** — one authenticating through LDAP, a database, an API, or matched by an identity provider claim — is left exactly as created; nothing is derived for it, since this is the normal outcome for that kind of record, not a failure. If any one of the three steps fails for a Consumer that should have been migrated, the Consumer keeps working exactly as it did before this feature existed, and the installation-wide conversion that runs automatically the next time the Manager starts completes it — see [Automatic Migration at Upgrade](#automatic-migration-at-upgrade) below. Records written by directory or database synchronization are not part of this at all — they carry an external identity source by construction, so nothing is derived for them either way.

## Automatic Migration at Upgrade {#automatic-migration-at-upgrade}

:::info No operator action needed

The steps below run **automatically, in order, once** the first time the Manager starts on this version — before it starts accepting requests. No screen, button, or manual step triggers them.

:::

Each step is **fault-tolerant per record** (one broken record does not stop the step), **idempotent** (a second run adds zero new rows), and never pushes synchronously to the gateway: it writes dispatch rows that workers pick up on their next cold start or through the minutely sweeper, rather than pushing to every worker inline. Every step writes one run row — tag, status (`RUNNING`/`COMPLETED`/`FAILED`), counters, a residual count, and notes — to the `api_client_migration_run` collection, and, for every record that did not converge, a row to `api_client_migration_row` (subject type, subject id, outcome, reason). Together these two collections are the migration's **ledger**.

| Step | What it does |
|---|---|
| **Identity** | For every legacy Consumer in the installation, makes the same inventory decision described in [Decision Values](#decision-values) above, derives its API client twin, carries over its secret, and activates it — installation-wide, the same conversion this screen runs by hand for one scope at a time. Residual (retryable): `FAILED`, `FAILED_ISSUE`. Recorded in the ledger, but not residual: `SKIPPED_BLOCKED` (blank username), `FAILED_DECRYPT`, `SOURCE_MISSING`. |
| **Access flag** | Records, for audit only, that the access axis (typed grant/restriction/registry) was already written by the Identity step above, and that a Consumer-owned or **Consumer only** record's access authority stays exactly where it always was — its legacy [API Proxy ACL](/en/admin/identity-management/api-proxy-acl)/[API Proxy Group ACL](/en/admin/identity-management/api-proxy-group-acl) rows. This step writes nothing else. |
| **Limits** | Converts legacy Request Rate limits into typed Limit Plans and assignments — see [Legacy Limits Migrated at Upgrade](/en/ai-gateway/limit-plans#legacy-limits-migrated-at-upgrade) for the full conversion. A Consumer's enabled AI token budget is converted the same way, into its own typed **AI Token Budget** assignment, carried onto its migrated API client when it has one; see [AI Budgets](/en/ai-gateway/limit-plans#ai-budgets). |
| **Portal** | Re-derives every portal application's grants from its approved subscriptions and backfills the matching subscription plan assignments. |
| **Consumer key stamp** | Generates a unique `consumerKey` for every Consumer that does not already have one — earlier synchronization writers never stamped it. |
| **Verification and daily reconcile** | Rolls the residual of every step above into one run row, then makes sure a **daily job (03:45)**, `LimitMigrationReconcileJob`, exists in the [admin job catalog](/en/admin/scheduled-jobs) — the job is recreated automatically at every boot if it is ever missing, not installed only once by this changeset. It re-runs the same idempotent steps for as long as any residual or failed step remains in the ledger; once fully converged, this is a single indexed read per day. If this step itself cannot reach the scheduler at boot, it records a `FAILED` run row instead of installing the job directly — the job catalog's own boot-time recreation still brings the job up, and its next nightly run retries whatever steps are still outstanding. |
| **Legacy password cleanup** | Deferred, not immediate: **7 days** after the Identity step converges (configurable with `-Dapinizer.migration.legacyPasswordUnsetGraceDays=N`), the daily reconcile job above unsets the `password` field on every legacy Consumer whose twin is **Active** and carries its own secret material (Local Secret or Secret Reference), so no second copy of the secret is left behind. Environment-detail passwords and `username` are left in place. A Consumer whose secret carry-over failed, or whose twin is still in Draft, keeps its password — the legacy path keeps answering for it. The wait exists so an older-version gateway pod restarting inside that window can still find the password it needs to verify a migrated Consumer — every gateway must be upgraded to this version within the window; see [Apinizer Version Upgrade](/en/upgrade/apinizer-version-upgrade). Until the window elapses, the ledger shows this step with a residual of 1 and a `deferred` note — this is expected, not a failure. |

Legacy quota and throttling counters do **not** carry over — every typed Request Rate counter restarts from zero. A migrated **AI Token Budget** assignment is the one exception: it is counted under the same counter its legacy budget already used, so in-window AI consumption carries over rather than restarting. This migration has no rollback: the MongoDB backup you take before upgrading (see [Apinizer Version Upgrade](/en/upgrade/apinizer-version-upgrade)) is the only way back.

## Permissions

- **View**: Identity management view permission is enough to view the inventory.
- **Dry-run and apply**: Both require identity management **manage** permission — a dry-run is authorized as the write it could become, even though it writes nothing, so the **Dry-Run** button is not available on view-only access.
- **Installation-wide scan**: When the project filter is removed and **All projects** is selected, both viewing and running a dry-run or apply require system administrator permission.
- **Secret Carry-Over**: Same rule as the row above — identity management **manage** permission, and an installation-wide run additionally requires system administrator permission.
