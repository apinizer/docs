## Logging Categories

Apinizer's logging mechanism is primarily divided into two main categories:

<CardGroup cols={2}>
    <Card title="Traffic Logs" icon="network-wired">
        Contains all API traffic information passing through Apinizer and is recorded by default in <strong>Elasticsearch</strong>.
    </Card>
    <Card title="System Logs" icon="server">
        Records system-related operations and events. These are stored by default in the <strong>MongoDB</strong> database.
    </Card>
</CardGroup>

## System Log Subcategories

System Logs are divided into five subcategories. Four of these can be sent to an external product via Syslog:

<Tabs>
    <TabItem value="logs-that-can-be-sent-via-syslog" label="Logs That Can Be Sent via Syslog">
        <ul>
            <li><strong>Audit Log (System Operations)</strong>: Logs related to changes and operations made in the Apinizer management application. Optionally also covers write requests to the Management Console/APIs and rejected requests; see <a href="/en/admin/audit-compliance/audit-records">Audit Records</a>.</li>
            <li><strong>Token Log</strong>: Contains logs related to token acquisition when Apinizer is used as a token provider.</li>
            <li><strong>Application Log</strong>: Software logs of Apinizer applications/modules. By default, kept at error (Error) level, and users can change the level as needed.</li>
            <li><strong>Login Audit</strong>: Successful and failed sign-in attempts, sign-outs, and project token refresh events; see <a href="/en/admin/audit-compliance/login-records">Login Records</a>. Forwarded through its own, separate connector configuration rather than the Audit/Token/Application Log settings above — see <a href="/en/admin/system-settings/login-log-connector-configuration">Login Log Connector Configuration</a>.</li>
        </ul>
    </TabItem>

    <TabItem value="logs-not-sent-via-syslog" label="Logs Not Sent via Syslog">
        <ul>
            <li><strong>Test Console Audit</strong>: Audit logs related to the use of the Test Console in the Apinizer management application interface. Not sent to external syslog products.</li>
        </ul>
    </TabItem>
</Tabs>

## Frequently Asked Questions


    <Accordion title="What are the challenges when sending logs to a SIEM product like QRadar?">
        Parameters in JSON format logs need to be parsed by writing a parser and stored accordingly. Therefore, it is necessary to work together with people who manage/use the Apinizer product or are familiar with web services to determine important fields for the organization together.

        In some cases, the length of log records that can be received at once can also be a problem. In such cases, when opening syslog integration, it can be configured to send only up to a certain number of characters in the body field.
    </Accordion>

    <Accordion title="Do System Audit logs coming via Syslog cover User Audit logs?">
        No, <strong>System Audit logs</strong> and <strong>User Audit logs</strong> have different content and are configured separately:

        <ul>
            <li><strong>System Audit Logs</strong>: "Who did what on which page" - general logs related to changes made on the system. Sent via the Audit Log connector described on this page.</li>
            <li><strong>Login Audit Logs</strong>: Successful and failed sign-in attempts, sign-outs, and token refresh events. Sent via their own, separate connector configuration; see <a href="/en/admin/system-settings/login-log-connector-configuration">Login Log Connector Configuration</a>.</li>
            <li><strong>Test Console Usage Audits</strong>: Not currently sent to external applications.</li>
        </ul>
    </Accordion>

    <Accordion title="Can Login Audit logs be forwarded to a Graylog connector?">
        Not currently — forwarding Login Audit logs through a Graylog connector fails. Syslog, Kafka, Webhook, Elasticsearch, and database connectors work as expected for Login Audit logs; use one of those until this is resolved.
    </Accordion>

    <Accordion title="What fields do Manager Request and Access Denied audit events add?">
        When the Audit Log setting described in <a href="/en/admin/audit-compliance/audit-records">Audit Records</a> is turned on, write requests to the Management Console/APIs are captured as <strong>Manager Request</strong> events, and every rejected request is captured as an <strong>Access Denied</strong> event. Both are additive to the existing Audit Log structure: the fields already documented in <a href="/en/operations/administrator-guides/system-logs-syslog-transfer">Transferring System Logs to Syslog</a> are unchanged, and every audit event forwarded via Syslog now also carries:

        <ul>
            <li><strong>eventType</strong>: Always present — <code>ENTITY</code> for the changes already documented, or <code>MANAGER_REQUEST</code> / <code>ACCESS_DENIED</code> for these two.</li>
            <li><strong>outcome</strong>: Always present — <code>SUCCESS</code>, <code>FAILURE</code>, or <code>DENIED</code>.</li>
            <li><strong>source</strong>: Always present — <code>MANAGER</code>, <code>APIOPS</code>, <code>PORTAL</code>, or <code>SYSTEM</code>.</li>
            <li><strong>clientIp</strong>, <strong>userAgent</strong>, <strong>correlationId</strong>: Present only when known for the request.</li>
        </ul>

        Example of a Manager Request event:

        ```text
        2026-09-02T08:14:22.101Z apinizer_demo Apinizer_demo {"id":"690b1a2c3d4e5f6789abcdef","principal":"admin","auditEventDate":"2026-09-02T08:14:22.101Z","state":"CREATED","objectId":"7c9e6679-7425-40de-944b-e07fc1f90ae7","objectName":"POST /api/apiproxy","referenceObjectJson":"{\"httpMethod\":\"POST\",\"path\":\"/api/apiproxy\",\"status\":200,\"durationMs\":184}","className":"MANAGER_REQUEST","eventType":"MANAGER_REQUEST","outcome":"SUCCESS","clientIp":"10.24.5.101","userAgent":"Mozilla/5.0 (Windows NT 10.0; Win64; x64)","correlationId":"7c9e6679-7425-40de-944b-e07fc1f90ae7","source":"MANAGER"}
        ```

        Example of an Access Denied event:

        ```text
        2026-09-02T08:16:47.552Z apinizer_demo Apinizer_demo {"id":"690b1a3d4e5f6789abcdef01","principal":"jdoe","auditEventDate":"2026-09-02T08:16:47.552Z","state":"CREATED","objectId":"/api/apiproxy/68493bb680f5de2a3c29c609","objectName":"403 DELETE /api/apiproxy/68493bb680f5de2a3c29c609","referenceObjectJson":"{\"path\":\"/api/apiproxy/68493bb680f5de2a3c29c609\",\"method\":\"DELETE\",\"problemTitle\":\"Forbidden\",\"exceptionClass\":\"com.apinizer.manager.errors.ExceptionTranslator$MapBasedProblem\"}","className":"ACCESS_DENIED","eventType":"ACCESS_DENIED","outcome":"DENIED","clientIp":"10.24.5.212","userAgent":"Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7)","source":"MANAGER"}
        ```

        In the Access Denied example, <strong>problemTitle</strong> and <strong>exceptionClass</strong> describe the rejection response itself, not the caller's request — they never contain data the caller sent.

        A database connector configured for the Audit Log only writes the original set of columns shown in <a href="/en/operations/administrator-guides/system-logs-syslog-transfer">Transferring System Logs to Syslog</a>; the additional fields above are only available through JSON-based connectors (Syslog, Kafka, Webhook, Elasticsearch).
    </Accordion>
