## Log Record Regions

Message information coming to and going from API Proxies defined on Apinizer is logged in Elasticsearch database according to message elements (header, parameter, body).

These log record regions:

<CardGroup cols={2}>
  <Card title="Request from Client" icon="arrow-right">
    Request information coming from client to API Proxy
  </Card>
  <Card title="Request to Target" icon="arrow-right">
    Request information sent from API Proxy to Backend API
  </Card>
  <Card title="Response from Target" icon="arrow-left">
    Response information given from Backend API to API Proxy
  </Card>
  <Card title="Response to Client" icon="arrow-left">
    Response information sent from API Proxy to client
  </Card>
</CardGroup>

By default, logging of fields in all message regions of the project is active. Logged fields can be restricted based on need or log server resource consumption.

Log settings are managed on a project and environment (environment) basis through this screen.

:::info

For production environment, it is recommended to disable logging of elements belonging to the following regions.

- From API Proxy to Backend API (Request to Target)
- From Backend API to API Proxy (Response from Target)

If an API Proxy is running in production environment, it means that all policy settings and tests in the API Proxy are completed and no more development will be done.

Therefore, to prevent excessive growth of data in the database, it is recommended not to write header, parameter, and body data in these two regions.

:::

:::warning

Even if all logging fields are closed, if an error occurs in the request, all log fields are recorded to detect the error. This feature can be opened and closed in general settings.

:::

:::warning

Due to variable data sizes and data formats, file parts of formdata requests are never logged. Only other metadata fields are logged.

:::

:::warning

Since WebSocket and gRPC requests are stored as data coming to Apinizer and data going out from Apinizer, there are only 2 regions in these types of API Proxies.

:::

On this screen you can manage [API Proxy](/en/concepts/core-concepts/what-is-api-proxy)-based traffic log settings. When [connectors](/en/concepts/core-concepts/connector) are defined on the [environment](/en/concepts/core-concepts/what-is-environment), you can control whether each proxy sends traffic records to those targets.

### What the list shows

Each row is one API Proxy on one environment with one connector. The list shows the values that are in effect, not only the values you saved.

| Column | Description |
|------|----------|
| API Proxy | Name of the API Proxy. |
| Environment | Name of the environment. The line below it shows the deployment state of the API Proxy on that environment: **Deployed**, **Redeploy required** or **Not deployed**. |
| Connector | Name and type of the connector. If the connector is not on, the line below it shows why: **Off**, **Disabled in environment** or **Off · not configured**. |
| Request from Client, Request to Target, Response from Target, Response to Client | What is written for each message region: Parameter, Header, Body, or a dash if nothing is written. The environment restriction and the retention profile are already applied. The tooltip tells when the environment narrowed the value. Under the retention profile **No persist** the cell shows **Not stored (retention)**. |
| Disabled fields | The log content groups that are turned off: **Request details**, **Client address**, **Metrics**, **Response status**. The tooltip shows which screens read these fields. Method overrides are not counted here. |
| Method Overrides | Number of method overrides. |
| Project | Project of the API Proxy. Shown in the admin project only. |

Saved log settings are sent to the gateway immediately. A redeploy is not required, so the deployment state has no action on this screen.

Use the filter bar above the list to narrow it. **API Proxy**, **Environment**, **Proxy deployment** and **Disabled fields** are always shown (and **Project** in the admin project). **Add filter** offers more, such as **Connector state**, **Body logged**, **Method Overrides**, **Override environment restrictions**, **Retention** and the attributes of the API Proxy. **Excel** downloads the filtered list: one row for each API Proxy, environment and connector, with the deployment state, the connector state, the four message regions, the disabled fields, the retention profile and the method override count. If the list is longer than the export limit, the file tells you that it is cut.

### Applying to many API Proxies

You can change the log settings of many API Proxies in one step. Users who may change log settings see the checkboxes and the buttons.

1. In the filter bar, select one environment. In the admin project, select one project as well. Log settings are applied to one environment and one project at a time. Until then the buttons are passive and a tooltip tells you what to select.
2. Tick the rows you want. The checkbox in the column header (**Select all on this page**) ticks every row on the page. The bar above the list shows the number of selected rows and **Clear selection**.
3. Select **Apply to selected**. To apply to every API Proxy that the filters list, on all pages, select **Apply to filtered results**. This button is also offered when nothing is ticked.
4. In the **Apply log settings** dialog, select the connector. Tick **Change** for each field you want to change and set its **New value**. The fields are grouped as **Connector** (on or off), **Content** (Parameter, Header and Body of each message region), **Body size limit** and **Field groups** (HTTP Request Details, Client Address, Performance Metrics, Response Status Info, Routing Address, Policy Execution Times).
5. Check the **Preview** and select **Apply**.

Only the fields you tick are changed. Other fields, method overrides and empty (default) values keep their state. **Override environment restrictions**, **Privacy**, **Method overrides** and the retention profile are not changed here. Edit them on each API Proxy.

The settings are sent in groups of 50 API Proxies. The dialog shows the progress, and **Cancel** stops the groups that are not sent yet. When the run ends, the dialog lists the result for each API Proxy:

| Result | Meaning |
|------|----------|
| Saved and sent | The settings are saved and the gateways received them. |
| Saved; gateway update incomplete | The settings are saved, but not all gateways were updated. The gateways that were not updated are shown next to the result. |
| Saved, gateway not reached | The settings are saved, but the gateway could not be reached. |
| Not saved: reason | The settings are not saved. The reason is one of: the API Proxy was not found or you may not change its log settings; the environment is not available to the project of the API Proxy; method overrides exist without proxy-level log settings (edit this API Proxy individually); the settings could not be saved. |

An API Proxy that is not deployed on the environment is saved too. The settings apply when you deploy it.

### Edit dialog (Edit API Traffic Proxy Log Settings)

Opening **Edit** on a row shows a dialog with a **CONNECTORS** menu on the left (Logback, Webhook, Kafka, RabbitMQ, database, Syslog, Elasticsearch, and so on). Selecting an item loads that target’s configuration on the right. At the top you choose the environment and use **Save and Deploy**; on each connector card, **Active for this environment** turns sending on or off for the selected environment. The colored status dot next to a connector reflects its configuration state at a glance. Use **Method Overrides** for method-level overrides.

In **Method Overrides**, methods are listed with the HTTP verb in front of the path, for example `GET /pet/{petId}`, so endpoints that share a path but differ by verb can be told apart. Methods that have no HTTP verb, such as SOAP operations, are listed by name only.

For the selected connector, the **Log content** section lets you toggle high-level groups such as HTTP request details, client address, performance metrics, and response status; these groups are independent. The four message regions follow the flow of a request and are numbered in that order: **1** Request from Client, **2** Request to Target, **3** Response from Target, **4** Response to Client. In each region you configure Parameter, Header, and Body (and **Partial size** where available). **Routing Address** is in region 2, because the gateway writes it when it sends the request to the backend. At the bottom, **Privacy** toggles privacy processing for this flow.

## Connectors Added Later {#connectors-added-later}

A connector that has no entry in the log settings of an API Proxy does not receive traffic logs. In the Traffic Log Settings list its state is **Not configured**. This is the case for a connector that you add to the environment after you saved the log settings of the proxy.

To start logging to a new connector, open the log settings of the API Proxy, select the connector, turn on **Active for this environment** and select **Save and Deploy**.

- **Upgrade:** On upgrade, Apinizer adds an explicit entry for every connector that already exists in the environment, for each API Proxy that has log settings. These connectors keep logging as before. An API Proxy with no connector entries logged nothing before the upgrade and logs nothing after it.
- **Upgrade order:** Upgrade the Manager first. Wait until the Manager log shows the line `Migration 202610-007030: completed`. Then restart the Gateway Engine instances. A Gateway Engine that starts before the migration finishes treats connectors without an entry as off.
- **Unreadable connector:** If the upgrade cannot read a connector or an environment, it writes a WARN line to the Manager log and skips it. The completion line is also a WARN and shows the number of skipped items. Turn on **Active for this environment** for a skipped connector to log to it.

:::warning

When you update log settings with APIops, the connector settings you send replace the stored connector settings. A connector you do not list in a partial update has no entry afterwards, so it stops logging. Always send every connector you want to keep logging to. The same applies to method overrides.

:::

## Log Settings Fields

The main fields used in log settings are summarized below.

| Field | Description |
|------|----------|
| Active for this environment | Turns sending traffic logs to this log target on or off for the selected environment. |
| HTTP request details | Controls inclusion of HTTP method, URI, port, caller identity, and related request metadata in the log. When it is off, the client address fields are removed as well. |
| Client address | Controls the client IP, the forwarded-for address, the remote host and port, and the location derived from the IP. It can only narrow HTTP request details: when it is off and HTTP request details is on, the HTTP method, URI, and caller identity are still written. A record that has no explicit value follows HTTP request details. When it is turned off explicitly, the address is not written for failed or blocked requests either. |
| Performance metrics | Controls whether duration, message size, cache-related metrics, and similar values are written to the log. |
| Response status info | Controls inclusion of HTTP status code, error type, and related fields in the log. |
| Routing address | Controls whether routing or destination address information is written to the log. |
| Header | For each message region, controls whether header information is logged. |
| Body | For each message region, controls whether body content is logged. |
| Parameter | For each message region, controls whether parameter information is logged. |
| Partial size | For each message region, controls whether long text fields are truncated or size-limited when logged. |
| Policy execution times | Adds the order, type and duration (in milliseconds) of every policy that ran on the request. Off by default; see below. |
| Privacy | Controls whether environment-level privacy rules apply to log data sent through this connector. |

When **HTTP request details** is off, the caller's username and the caller's attribution are removed from the traffic log of that connector: the typed client attribution ids (`ack`, `cot`, `coi`, `coo`) and the subscription ids (`subi`, `subp`, `subpl`, `subo`). The AI tenant credential (`aivk`) is still written. Usage reports and AI alarms that count by these ids do not see that connector's traffic; quota and limit enforcement is not affected.

## Policy Execution Times

When a request is slower than expected, the usual next question is *which policy consumed the time*.
Answering it used to require enabling **Trace** on the API Proxy, which records the full before/after
body, headers and parameters of every policy — too heavy to leave on in production.

**Policy execution times** answers the same question without capturing any payload. When the option is
enabled, each traffic log record carries a compact list of the policies that ran on that request:

| Value | Meaning |
|------|----------|
| Order | Execution order. The value also encodes the pipeline region: `0-9999` request, `10000-19999` response, `20000` and above error. The API Traffic detail screen shows the region and the position within it. |
| Policy type | The policy type, for example `jwt-auth` or `content-filter`. The policy *name* is deliberately not stored — it is usually an auto-generated identifier and carries no meaning on screen. |
| Duration | How long the policy took, in milliseconds. |

Records that come from the end of a streaming response, policies skipped because their condition was
not met, and a truncation marker (when a request runs an unusually large number of policies) are shown
with a small badge next to the policy type.

The measurement itself is not new work: the gateway already computes each policy's duration on every
request and discards it when Trace is off. Enabling this option only keeps the value.

### Turning it on

The option lives with the other log content flags and is set **per log target**, so you can write the
timings to Elasticsearch while leaving them out of a relational database target. Method-level overrides
apply as well.

**Redeploy the API Proxy after changing it** — traffic log settings reach the gateway with the proxy
deployment.

### Where the data is written

| Target | Representation |
|------|----------|
| Elasticsearch | The `pxt` field, as a `nested` object array. `nested` keeps the type and the duration correlated, so a query such as "requests where policy X took longer than 100 ms" returns the right rows. |
| MongoDB | A sub-document array. |
| Relational database (SQL/JDBC) | The `policy_exec_times` column, as a single capped CSV: `order:type:duration`, pipe-separated. |
| Graylog | The same CSV as the relational target. |

:::note
The option is off by default. On the Elasticsearch side a `nested` field indexes every list item as a
separate internal document, so a record with 10-20 policies increases the document count of that index
accordingly. Enable it on the targets where you actually need the data.
:::

:::info Existing Elasticsearch indices
The new field is added to the index template and the index is rolled over automatically during the
upgrade. Because traffic logs are written to a data stream, the field is only available on backing
indices created after the rollover; older records stay as they are.
:::

:::info SQL/JDBC log target
If you write traffic logs to a relational database, the `policy_exec_times` column must be added once
per environment database. See the [2026.09.1 — Log Table ALTER Scripts](/en/release-notes/2026-09-1-log-table-alter)
page; new installations already have the column via the
[Apinizer Log Table Creation Commands](/en/operations/administrator-guides/apinizer-log-table-creation-commands)
script.
:::
