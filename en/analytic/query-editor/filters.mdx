:::note Queries and Filters are now one

Earlier versions had two lists: Queries and Filters. There is now one list, **Filters**. On upgrade, each saved Query became a Filter with its conditions. Each earlier Filter also became a Filter: its API Proxy list and result types became conditions, and its date range became the time range. A Filter whose name already existed in the same project got the suffix " (filter)". A Query that held several test filters gave one Filter for its first test filter and one more Filter named "Query name · Filter name" for each other test filter.

:::

## Where a Filter Is Used

A Filter works on API traffic. It reads the traffic log of the gateway.

- **Traffic**: **Select filter** copies a Filter into the search. **Save** saves the search as a Filter. See [Traffic](/en/analytic/api-traffic).
- **Report Generator**: The report types that read the traffic log take a Filter in the **Filter** step. See [Report Generator](/en/analytic/analytics-reports/report-generator).
- **Anomaly Detector**: A detector has a **Filter: calls you watch** and an optional **Base filter: all calls that count**. See [Anomaly Detector](/en/monitor/anomaly-detector).
- **API Proxy trace**: The **Trace** tab can trace only the requests that match a Filter. See [Tracing](/en/analytic/tracing).
- **APIops**: A Filter can run by name. See [Run Saved Query on Traffic Log](/api-reference/reports/search-saved-query).

Report types that do not read the traffic log do not use a Filter. They have their own **Period** and **API Proxies** fields. Alerts keep their own traffic filter.

## Filter List

The list shows the name, description, conditions, API Proxy, time range, visibility, owner and where the Filter is used. In Administration mode it also shows the project. The **API Proxy** column shows **All Proxies** when the Filter names no API Proxy.

The filter bar of the list has **Name**, **Visibility**, **Used in** and, in Administration mode, **Project**. **Owner** and **Description** are under **Add filter**. The filters apply when you click **Search** or press Enter. **Clear filters** and the eraser button reset them. Use the Excel button to download the list. When a row limit cuts the file, a message tells how many Filters were downloaded.

### Actions on the List

Open the row menu (three dots) of a Filter to see its actions. The **With this filter** item opens a submenu that lets you use the Filter in other places.

| Action | What it does | When it is shown |
| --- | --- | --- |
| **Open in Traffic** | Opens the Traffic screen with the conditions of this Filter applied. | Always. |
| **Use in Trace** | Asks you to choose an API proxy, then opens the **Trace** tab of that proxy with this Filter selected. The trace starts when you press **Start**. | You can manage analytics and you can view API proxies or AI development. |
| **Create Report** | Opens the new Report Generator screen with this Filter selected. | You can manage analytics and your license includes advanced analytics. |
| **Create Anomaly Detector** | Opens the new Anomaly Detector screen with this Filter selected. | You can manage monitoring and your license includes monitoring. |

Other row menu items are **Edit**, **Duplicate**, **Delete**, **Move to Global** and **Export**. **Edit**, **Duplicate** and **Delete** need the permission to manage analytics. **Export** needs the permission to export and import project assets.

## Filter Page

The **General** tab of the page has the settings of the Filter and the bar that holds its conditions.

| Field | Description |
| --- | --- |
| **Name** | Unique name of the Filter. |
| **Visibility** | **Project**: everyone with access to the project sees the Filter. **Personal**: only you see it. |
| **Description** | Optional description. |
| **Projects** | Administration mode only. The projects whose traffic the Filter reads. An empty list means all projects. |
| **Time range** | Optional. A relative range such as "Last 7 days". When set, the screens that open the Filter use this range. Without it, the screen that uses the Filter decides the time. |

### The Bar

The **Filter** block of the page shows the bar. It works like the bar of [Traffic](/en/analytic/api-traffic#filtering).

- The **API** / **AI** switch chooses the fields the bar offers. It is not a separate setting: it follows the fields that the Filter uses. When you switch it, the conditions of the other half are removed.
- The proxy selector follows the half. The API half has **API Proxy**. The AI half has **LLM Gateway**, **MCP Gateway** and **A2A Gateway**. Each one lists only its own type. In Administration mode, **Project** comes first.
- Quick filters are always in the bar. **Edit quick filters** chooses them. They are saved in your profile and are the same on Traffic and on the Filter page.
- **More filters** adds any other field. The fields are in groups and have a search box.
- **Advanced** opens a condition tree below the bar for **OR** and **NOT** groups. A badge on the button shows that the tree has conditions.
- The conditions of the bar and the **Advanced** conditions work together (AND).

### Try it

Select an environment in the header of the **Filter** block and click **Search**. The Filter runs on that environment. It reads the **Time range** of the Filter. When the Filter has no time range, it reads the last 24 hours. The result table appears below. **Columns** chooses the fields of the table. The Excel button exports the result. **Open in Traffic** opens the Traffic screen with the Filter.

### Actions on the Page

The **⋯** menu of the bar has these items:

- **Save filter as new…**: Saves a copy under a new name. It is shown for a saved Filter.
- **Open in Traffic**: Opens the Traffic screen with the Filter.
- **Copy as cURL**: Copies the Filter as a request to the traffic API. Choose bash, Windows CMD or PowerShell.

Save the Filter with **Save** in the header of the page.

## Where a Filter Is Used (Used in)

A report, anomaly detector or trace that uses a saved Filter holds a linked copy of it. The list shows how many places use each Filter in the **Used in** column. Select the number to open the **Used in** tab of the Filter. This link needs the permission to manage analytics.

The **Used in** tab lists each place with its type, name and whether the copy is **Linked** or a **Local copy**. A linked copy follows the saved Filter.

- To find Filters by usage, use the **Used in** filter of the list and choose **Used** or **Not used**.
- When you save a Filter that is used somewhere, a dialog shows the places. Saving overwrites the linked copies with the new conditions. A trace that is running keeps the conditions it started with and takes the new ones at its next start.
- Some anomaly detector rate conditions divide by the result of a Filter. The dialog warns you that changing the Filter changes the rate they measure.
- When you delete a Filter that is used somewhere, the dialog shows the places. Reports and anomaly detectors keep their copy of the conditions, but it is no longer linked. A trace that uses the deleted Filter cannot start until you choose another Filter or all traffic.

## Conditions

The bar and the **Advanced** tree use the same conditions. Each field offers the operators that fit its type. For example, a number field has the comparison operators and "is between". See [Traffic](/en/analytic/api-traffic) for the fields and operators.

The fields include API Proxy name, client IP, HTTP method, status code, duration, size and **API Proxy Type** (REST, SOAP, gRPC, WebSocket, AI, MCP, A2A). Fields for WebSocket and gRPC calls are **WebSocket Message Type**, **gRPC Call Type**, **Message Direction**, **gRPC Service** and **gRPC Method**. **HTTP Method** lists only HTTP methods.

### Keyword Criterion — Message Region and Part

A **Keyword** condition searches one part of one message region. Choose the region first, then the part.

| Region | Header | Parameter | Body |
| --- | --- | --- | --- |
| 1. Request from Client | ✓ | ✓ | ✓ |
| 2. Request to Backend API | ✓ | ✓ | ✓ |
| 3. Response from Backend API | ✓ | — | ✓ |
| 4. Response to Client | ✓ | — | ✓ |

- **Header** and **Parameter** parts require the header/parameter name; the operator is applied to its value. Responses carry no query parameters. The name field is mandatory for these two parts: leaving it empty shows a required-field warning under the field and the search does not run.
- **Body** parts search the full text of that region's body (case-insensitive; values with punctuation such as `ABC-123` are matched as a phrase, `*`/`?` give explicit wildcard patterns).
- **Header** and **Parameter** values are matched case-insensitively on Elasticsearch 7.10 and later. On Elasticsearch 7.0–7.9 only the lowercase form of the stored value matches, because those versions do not support the case-insensitive option; Apinizer retries the search without it automatically, so the Filter still runs.
- The same condition is used by the API Proxy **trace** filter: a request is traced when its live messages satisfy the criteria. A region that does not exist for a request (for example the backend request of a blocked call) never matches.

:::tip

To see the routing target in the **Try it** table, select the route address field in **Columns**.

:::

### More Fields

A Filter can use the **More fields** criterion. A Filter that uses it cannot be used as a trace filter. After an import, conditions that hold a consumer, an API client, an organization, an API product or a provider are listed in the import report. Select these values again. See [Traffic](/en/analytic/api-traffic) for the fields.

## Time Range of a Filter

A new Filter keeps only a relative time range, such as "Last 7 days". An absolute range of an earlier Filter stays as it is. In Traffic, **Save** stores the time range only when you tick **Save the time range with the filter**. The base filter of an anomaly detector needs a rolling range.
