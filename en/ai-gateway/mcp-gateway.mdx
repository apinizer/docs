## Overview

**MCP (Model Context Protocol)** is the standard AI agents use to discover and call external tools. In Apinizer, MCP is a **first-class API proxy type** — you create an MCP proxy the same way you'd create a REST, SOAP, or AI proxy, and configure its behavior on a dedicated routing tab. An MCP proxy works in one of two directions:

- **Expose Tools** — publishes your existing API proxy operations as MCP tools that any MCP-compatible client can discover and call
- **Passthrough** — forwards MCP calls through to an external MCP server, applying tool filtering and output masking along the way

:::info
**Coming from an older release?** MCP used to be configured on a separate "Inbound Server" screen with its own authentication settings, reachable at a dedicated path. That model has been replaced entirely — see [Migrating from the Previous Model](#migrating-from-the-previous-model). New to the MCP protocol itself? See [AI Fundamentals](/en/concepts/core-concepts/ai-fundamentals) for a primer.
:::

## Quick Start

<Steps>
  <Step title="Create an MCP Proxy">
    Create a new **MCP Proxy** the same way you'd create any other API proxy: give it a name and a single client-facing path.
  </Step>

  <Step title="Choose a Routing Mode">
    Open the proxy's **MCP Routing** tab and pick **Expose Tools** or **Passthrough**.
  </Step>

  <Step title="Configure the Mode">
    For Expose Tools, select which of your API proxy operations should be published as tools. For Passthrough, pick an outbound MCP connection and, optionally, restrict which of its discovered tools are allowed through.
  </Step>

  <Step title="Add Authentication">
    Attach any of Apinizer's regular authentication policies (API Key, JWT, OAuth2, ...) to the proxy — the same way you would on any other proxy type.
  </Step>

  <Step title="Save and Deploy">
    Deploy the proxy. Its client path becomes the single endpoint MCP clients connect to, for both discovery and tool calls.
  </Step>

  <Step title="Connect a Client">
    Point an MCP-compatible client at the proxy's path — it discovers the manifest and tool catalog through the standard handshake, then calls tools over that same path.
  </Step>
</Steps>

## Modes

### Expose Tools

Publishes selected operations from your existing API proxies as MCP tools. Each exposed tool maps to one API proxy operation, can override the tool's auto-generated input schema, and can optionally require a specific scope — enforced only when the caller authenticated through OAuth2 and ignored for every other authentication type. A caller missing the required scope is denied that particular tool while the rest of the catalog behaves normally.

### Passthrough

Forwards MCP calls to an external MCP server through a stored, encrypted **outbound MCP connection** — the same connection object described below.

<CardGroup cols={2}>
  <Card title="Automatic Tool Discovery" icon="search">
    Once the outbound connection is saved, Apinizer fetches its tool catalog automatically.
  </Card>
  <Card title="Tool Allow-List" icon="shield-check">
    Leave the allow-list empty to pass every discovered tool through, or select specific tools to restrict what's reachable through this proxy.
  </Card>
  <Card title="Health Probe" icon="activity">
    The connection is probed periodically and reports **Healthy**, **Down**, or **Unknown** status with its last response time.
  </Card>
  <Card title="Egress Protection" icon="shield">
    Discovery and tool calls can't reach cloud-metadata endpoints, loopback, or link-local addresses — see [Security and Governance](#security-and-governance).
  </Card>
</CardGroup>

Both modes' tool results pass through the same output filtering used elsewhere in the gateway: a deny-pattern match blocks the whole response (not just the matched portion), and PII masking covers the platform's built-in personal-data types.

### Outbound MCP Connections

An outbound MCP connection is a stored, encrypted reference to an external MCP server, with its tool catalog fetched and cached automatically. It's the shared backend behind two different things:

- A **Passthrough** MCP proxy forwards every call it receives straight to one.
- The **MCP Tool Call** / **MCP Tool Invoke** policies let a model call one as part of any AI proxy's own [tool-call loop](/en/ai-gateway/routing-and-failover#tool-call-loop-agentic-requests) — no MCP proxy required for that path at all.

Both consumers share the same connection health, discovery, and governance settings described in [Security and Governance](#security-and-governance).

## Protocol Versions

An MCP proxy negotiates one of three protocol behaviors, set per proxy and applied on the next redeploy:

| Version | Behavior |
|---|---|
| `2024-11-05` | Legacy HTTP+SSE transport — a `GET` to the proxy's SSE sub-path opens a bounded push channel. |
| `2025-06-18` | Streamable HTTP — the default for new proxies. Responses carry an `MCP-Protocol-Version` header confirming the negotiated version. |
| `2026-07-28` | Stateless mode — no `initialize` handshake is required before calling tools. |

If a connecting client requests a version Apinizer doesn't recognize during `initialize`, the proxy falls back to the nearest earlier version it does support and logs a warning, rather than rejecting the request outright.

The discovery manifest is published, unauthenticated, at the proxy's client path plus `/.well-known/mcp/manifest.json` — required so a client can see what's on offer before it has credentials to authenticate. The manifest is a best-effort discovery aid: it advertises a generic "authentication required" hint whenever the proxy has any request policy attached, but the actual scheme enforced is whatever policy chain you've configured (see [Authentication](#authentication)).

## Multi-Target Aggregation

A Passthrough proxy isn't limited to a single backend: alongside its primary outbound MCP connection, aggregate up to **10** additional ones behind one client-facing endpoint (11 in total). Their tool catalogs are merged into a single list; if two backends expose a tool with the same name, the collision is resolved deterministically by prefixing the tool name with its source connection (`connectionName__toolName`). If one backend is slow or unreachable, the others still respond — a single failing target doesn't take down the whole catalog.

## Security and Governance

### Authentication

Authentication for an MCP proxy is whatever policy chain you attach to it — API Key, JWT, OAuth2, Basic, and so on — the same policies every other proxy type uses. There's no separate per-server auth-mode selector anymore; the proxy's own policy chain runs before a request ever reaches MCP handling. The one deliberate exception is the discovery manifest itself, which stays reachable without authentication.

### Identity-Based Access Control

Optionally, restrict tool visibility by the caller's credential, role, or organization — in **Passthrough** mode only; Expose Tools mode never evaluates this list, and instead relies solely on each tool's own required-scope check (see [Expose Tools](#expose-tools)). Each rule allows or denies specific tool names for the principal it matches; once at least one rule is configured, a caller not covered by any rule sees nothing in the Passthrough tool list (default-deny) and can't call any tool either. This is set on the proxy's MCP routing configuration — today through the Management REST API rather than a Manager UI screen:

```json
{
  "identityAcl": [
    {
      "principalType": "ROLE",
      "principalName": "partner-readonly",
      "allow": ["search", "fetch"],
      "deny": []
    }
  ]
}
```

### Argument Constraints

Attach validation rules to a tool's arguments — a required field, a maximum string length, an allowed value list, or a regular expression — matched with dot-notation against the argument object (for example `user.email`). A malformed rule is skipped rather than blocking all traffic through the tool. Regular-expression rules run under a hard ceiling (a 4096-character input cap and a 200ms evaluation deadline) so a crafted value can't turn a rule into a denial-of-service vector.

```json
{
  "argumentConstraints": [
    {
      "toolName": "search",
      "rules": [
        { "argumentPath": "query", "ruleType": "MAX_LENGTH", "value": "500" },
        { "argumentPath": "region", "ruleType": "ENUM", "value": "eu,us,apac" }
      ]
    }
  ]
}
```

### Call Quotas

Cap how often a tool can be called per minute, hour, or day — scoped per tool, per calling credential, or both combined. A call that would exceed the quota is rejected before it dispatches; an unauthorized or argument-invalid call never consumes a unit.

```json
{
  "callQuota": { "scope": "PER_CREDENTIAL", "period": "HOUR", "limit": 1000 }
}
```

### Catalog Drift Protection

Each outbound MCP connection remembers a fingerprint of its tool catalog captured at the moment it was last approved (an explicit discovery/re-parse). A periodic health check compares the live catalog against that fingerprint; when they diverge, the connection either just logs and surfaces the drift (the default) or blocks every tool call through it until an operator re-approves the new catalog. This guards against a backend server silently changing what a tool does, or what it expects, underneath an already-approved integration.

### Token Passthrough

By default, Apinizer never forwards a caller's own token to a backend MCP server — the connection's own configured credential is always used instead. You can opt in per connection: the caller's bearer token is relayed as-is, optionally restricted to an allow-list of accepted JWT audiences, with the connection's own credential resolution skipped once a forward succeeds. This is off everywhere by default — an operator has to enable it deliberately.

### Egress Protection

:::danger
Outbound MCP calls — discovery, tool calls, and health probes — can never reach cloud-metadata endpoints, loopback, link-local, multicast, or carrier-grade-NAT addresses, regardless of configuration. A connection can optionally be allowed to reach other private-network ranges (for example an in-cluster MCP server), but that opt-in never lifts the addresses above.
:::

This same protection is shared with [A2A Gateway](/en/ai-gateway/a2a-gateway) outbound connections.

## Logging and Analytics

Every MCP call — discovery, a tool invocation, and (for Passthrough) each fan-out to a backend connection — is recorded in your traffic logs with the call direction, the connection or tool identifier, and the request's correlation ID, so a single agent turn can be followed end to end. These calls also appear in [trace groups](/en/ai-gateway/tracing-and-replay) alongside the rest of a request's chain, and roll up into your usage [reports](/en/ai-gateway/reports).

## Migrating from the Previous Model

- The separate MCP "Inbound Server" screen is gone; MCP is now configured directly on an MCP proxy's **MCP Routing** tab.
- Per-server authentication mode (None / API Key / OAuth2) no longer exists — authentication is whatever policy chain you attach to the proxy, the same as any other proxy type.
- The old dedicated inbound path is gone; clients must be repointed at the MCP proxy's own client path.
- Existing inbound server definitions aren't carried forward automatically — recreate your exposed tool list as an MCP proxy.
- Outbound MCP connections, their tool discovery, and the MCP Tool Call / MCP Tool Invoke policies are unchanged.
