A plan created while the module was licensed still shows its own type when opened later; the type of an existing plan is read-only in any case.

## Concepts

A **limit plan** is a reusable description of a limit. It says *what* is limited (APIs, endpoints, AI proxies, models, providers), *how much*, and *what happens when the limit is reached*. A plan does nothing until it is **deployed**, and it only limits the callers in its **target audience**.

| Concept | Meaning |
|---------|---------|
| **Limit Plan** | A named, reusable set of limits. Defined once, used by any number of identities. When a deployed plan is updated and redeployed, everyone on it gets the new values automatically. |
| **Target Audience** | The callers the plan limits: identities you select on the plan page, callers that match a condition, and identities that pick the plan on their own **Limits** tab. |
| **Deployment** | The step that sends the plan to the gateways. A plan that is not deployed limits nothing. |
| **Limits tab** | The tab on an organization, consumer, application or API client where you add a plan to that identity and see which plans apply to it. |

### Plan Types

A plan has one of two types, chosen when the plan is created. The type cannot be changed afterwards.

**AI Token Limit** — token limits per minute/hour/day/month, USD budgets per minute/hour/day/month, alert thresholds and a hard cap, and an action for when the budget is reached. A budget can cover all AI traffic of an identity (the **General Limit**) or one AI proxy, model or provider.

**API Request Count** — the limit body is a **list of windows**; each window defines:

| Field | Meaning | Default |
|---|---|---|
| **Requests** | The number of requests permitted in the window (a positive integer). | — |
| **Interval** | The unit of time the window is measured in: 1 Second, 1 Minute, 1 Hour, 1 Day, or 1 Month. | — |
| **Period Length** | How many intervals make up one window — for example, a 5-minute window is a Period Length of 5 on a 1 Minute interval. | 1 |
| **Window Type** | **Fixed (calendar aligned)** resets the counter on a calendar boundary, for example at the start of each minute; **Sliding** measures the trailing period from each request. | Fixed |
| **Counting Mode** | **All requests** counts every request, accepted or rejected, toward the window — this slows down an abusive client; **Accepted only** counts only requests that reach the backend — the right choice for a commercial quota. | All requests |

A limit needs **at least one window**. The same Interval/Period Length combination cannot be defined twice in the same limit — the screen warns before you can save. "100 requests per second and 10,000 per day" is **one** limit with **two** windows: exceeding any one of them blocks the request. An hour, day or month window answers with a quota error; a second or minute window answers with a throttling error.

## The Limit Plans Screen

Reached from **AI Gateway → Limit Plans**. The plan list is on the left; the selected plan opens on the right. The list can be filtered by type and by free-text search, and the toolbar offers **Bulk assignment**, **Import** and **Create**. A plan with saved changes that are not yet on the gateways is marked **Waiting for Redeploy**.

When nothing matches, the screen shows one of two messages:

| Situation | What you see |
|---|---|
| No plan exists in this scope | "No limit plans defined yet." |
| A filter matches nothing | "No limit plan matches this filter.", a line naming how many plans exist in this scope, and a **Clear filters** button that resets the free-text search and the type filter together |

### Plan Scope: Project or Platform

Every plan belongs to either one project's own catalog or the installation-wide **Platform** catalog. A system administrator switches between **Project** and **Platform** with a scope control above the list; a project member without system-admin rights sees only their own project's scope.

- **Project-scope** plans are created, edited, and added to identities the same way regardless of scope.
- **Platform-scope** plans are visible to every project — a project member sees them read-only, badged **Platform**, and can reference them when adding a plan to an identity — but only a system administrator can create, edit, deploy, or retire one.

A [Subscription Plan on a portal API Product](/en/api-portal/api-product#limit-profiles) can only reference a **deployed, platform-scope** plan of the matching type — this is what makes the Platform catalog the shared source of ceilings a commercial plan sells.

### Administration Mode: Every Project in One List {#administration-mode}

A system administrator also reaches the plans from **Administration → Identity Management → Limit Plans**. This view does not belong to any one project: it lists **every project's plans and the Platform catalog together**, with a **Project** column that names the owner of each row, so a plan can be found and corrected without first switching into the project that owns it.

- A **scope filter** above the list narrows it to **All projects**, **Platform**, or one project. Plans stay project-scoped — the filter only decides what is shown; it never moves a plan between projects.
- **Creating** a plan requires a concrete scope: pick **Platform** or a project in the filter first (the screen says "Pick a project or Platform in the scope filter to create a plan there."), and the new plan is born into that scope.
- **Editing** a row opens the same plan page as in project mode, badged with the owning project (or **Platform**). Deploying, retiring and deleting work exactly as they do there.
- **Bulk assignment** stays a project-mode action: it works on the active project's identities.

### Profiles Owned by a Subscription Plan {#profiles-owned-by-a-subscription-plan}

When a portal subscription plan carries a rate limit or a quota, the system generates an **API Request Count** profile for that plan and updates and deploys it whenever the plan's numbers change. These profiles live in the Platform catalog too, but they do not behave like ordinary plans:

- They are **hidden from the list by default**. Turn on **Show subscription plan profiles** above the list to see them; the row is badged **Subscription plan** and names the plan that owns it.
- They **cannot be edited or deleted.** The only way to change these limits is the rate-limit and quota fields on the owning [subscription plan](/en/api-portal/api-product#limit-profiles). The screen says: "This limit profile is managed by the subscription plan".
- They are **not offered** when you add a plan to an identity — the owning plan rewrites them from its own numbers, so binding another identity to one would silently change that identity's ceiling.
- If the subscription plan is deleted — or its rate limit and quota are both cleared — its profile is **released**, not removed: it stays deployed, keeps applying to the identities that already use it, and becomes an ordinary catalog plan that you can edit, undeploy or add to identities. Its description is rewritten to name the plan it came from and the date it was released.
- The profile's internal key includes the owning API Product's name as well as the plan's, so two products that each have a plan named, for instance, "Standard" get two distinct profiles instead of colliding on the same one. Profiles generated before this change keep their existing key.
- On an installation upgraded from an earlier version, profiles that this mechanism had already generated but had not yet marked as owned are found and stamped with their owning plan automatically; any plan that had ended up bound to another plan's profile because of that gap is moved back to its own. This runs once during the upgrade and needs no action.

### Creating a Plan {#creating-a-plan}

**Create** opens the **New Limit Plan** dialog:

- **Name** and **Description** — for example "Partner Limits", and who the plan is for.
- **What to Limit** — the plan type: **API Request Count** ("Request limits per API and endpoint.") or **AI Token Limit** ("Token and USD limits per AI proxy, model and provider."). The type cannot be changed later.

**Create and Continue** creates the plan and opens its page, where you add the limits and the target audience. A new plan is **not deployed** and limits nothing until you deploy it.

A plan has one name. The Turkish label shown in the portal and in reports is that same name. A plan that already had a distinct Turkish name keeps it until the plan is saved again.

**Duplicate** copies the plan's limits into a new plan. The **Target Audience** is not copied.

## The Plan Page

The plan page has six tabs:

| Tab | What it holds |
|---|---|
| **Definition** | General information, the general limit or budget, the limits per target, what happens when a limit is reached, and advanced settings. |
| **Target Audience** | The callers the plan limits. |
| **API/Endpoint Limits** (API Request Count) or **AI Limits** (AI Token Limit) | The limits per API, endpoint, API group, AI proxy, model or provider. |
| **Conditions** | A request condition that decides which requests the plan counts. |
| **Error Message Customization** | The messages returned when a limit is exceeded or the target audience rejects a caller. |
| **Revision History** | The deployed versions of the plan. |

Each card has its own **Configure** button that opens a side drawer. A **How to Read** button opens a short guide.

### General Limit and Targeted Limits {#target-what-the-ceiling-narrows-to}

A plan can hold two kinds of limit, and a request is counted against every limit that covers it:

- **General Limit** (API Request Count) or **General Limit** (AI Token Limit) — optional. The total of all requests, or all AI calls, of each identity that has the plan. Example for API Request Count: 1,000 requests a minute and 100,000 a day, both applying together. Example for AI Token Limit: 200,000 tokens a day and 50 USD a month.
- **API and Endpoint Limits** (API Request Count) — a separate limit for one API, endpoint or API group. Each row is counted on its own.
- **AI Proxy, Model and Provider Limits** (AI Token Limit) — a separate limit for one AI proxy, model or provider. Each row is counted on its own. Choose the **Target Type** (AI Proxy, Model or Provider), then the target.

A call or request is counted in the general limit **and** in every row that covers it. The first limit that fills stops the request. For example, a general limit of 600/min and a Payments API `POST /payments` limit of 60/min mean that a consumer cannot send more than 60 payment requests a minute, and all its requests together cannot pass 600.

**Scope of a row.** For an API row you pick the project, the API or API group, an **Environment** and the endpoints: **All endpoints of the API** (one counter for every endpoint), **Select endpoints** (each selected endpoint has its own counter), or **Select an endpoint** (only that endpoint). A group limit counts the total of the requests to the group. The API list also includes AI proxies, so you can limit the request count of an AI proxy in an API Request Count plan (its token and USD use is limited in an AI Token Limit plan). An API row can also show an **API total (all endpoints)**.

**Values per environment.** Each target holds one value per environment. The **All environments** value is the default. An environment-specific value **replaces** the default in that environment; the two are not added. If a target has no default, it has no limit in the environments that are not listed.

The screen warns when a row can never fill because a lower limit that covers it fills first.

### When a Limit Is Reached

The **When a Limit Is Reached** card sets what happens to a request that hits a limit:

| Plan type | Option | Meaning |
|---|---|---|
| Both | **Reject the request** | The caller gets HTTP 429. This is the right choice in most cases. |
| API Request Count | **Let it pass, only count** | The request passes. The overrun shows only in reports. |
| AI Token Limit | **Let it pass, only alert** | The call passes and an alert is raised. |
| AI Token Limit | **Switch to a cheaper model** | When the budget is reached, calls go to the chosen **Model to Switch To**, which is required. |
| AI Token Limit | **Fail over** | When the budget is reached, the backup provider is used. If the routing has no backup provider, the request is rejected with HTTP 429. It is not sent to the over-budget primary. |

**Let it pass, only count** exists for the case where the plan backs a **billed** overage rather than a hard stop — see [Referenced by a Portal Subscription Plan](#referenced-by-a-portal-subscription-plan) below.

### Advanced Settings {#cache-posture-and-custom-error-message}

The defaults are enough in most cases.

| Setting | Meaning | Plan type |
|---|---|---|
| **Alert Thresholds (%)** | An alert is raised at these percentages of the limit. Values from 1 to 99, ascending. The default is 50, 80 and 90. | AI Token Limit |
| **Hard Cap (%)** | From 1 to 100. At this percentage of the limit, the action in **When a Limit Is Reached** starts. The default, 100, means when the limit is full. | AI Token Limit |
| **Valid From** / **Valid Until** | Optional validity window of the plan. Leave **Valid Until** empty for no end date. | Both |
| **If the Counter Store Is Unreachable** | **Reject the request** or **Let the request pass** when the counter service cannot be reached. | Both |
| **Connection Timeout (s)** | Maximum time to wait when connecting to the counter service. | Both |
| **Remaining Limit in Response Headers** | Show the remaining limit in response headers (`RateLimit-Remaining`, `RateLimit-Limit`, `RateLimit-Reset`, `X-RateLimit-Type`). An **API Request Count** plan also adds `X-RateLimit-Identity`. When the plan does not set it, the setting of the assignment that adds the plan to the identity applies. | Both |

On an AI Token Limit plan, the headers show the limit with the smallest share left on this request. Token limits and call-count limits show in the headers. USD limits do not, because they are not a count of tokens or calls. When a limit is full, `RateLimit-Remaining` is 0 on the 429 response. `RateLimit-Reset` is the number of seconds until the window ends; on a monthly window it can be longer than one day. The AI proxy protection of the Token Rate Limit policy does not add these headers. The headers come on single responses, streamed (SSE) responses and binary (audio, image) responses.

:::note Known limitation
When one request has both an **API Request Count** plan and an **AI Token Limit** plan that show these headers, the response keeps the values of the **AI Token Limit** plan. The headers do not select the stricter of the two plans. The unit of the number in the headers depends on the limit: tokens for a token limit, calls for a call-count limit.
:::

In the **Add Limit** and **Edit Limit** drawers, **Hard Cap (%)** and **Alert Thresholds (%)** sit in their own **Thresholds** group. They apply to token limits and USD limits alike. The USD group stays named **Budget (USD)**, because those fields are real money budgets. It has four fields in the same order as the token row: **USD/Minute**, **USD/Hour**, **USD/Day** and **USD/Month**. **USD/Minute** accepts up to 4 decimals (for example 0.0025); the other USD fields accept 2 decimals. A limit chip shows the value as, for example, "0.5 USD / min".

The plan's own **If the Counter Store Is Unreachable** and **Connection Timeout (s)** settings win over the cache settings of the assignment (**Action on cache connection error** and **Cache connection timeout (seconds)**). The [Token Rate Limit policy](/en/ai-gateway/token-quotas#when-the-counter-store-is-unreachable) has its own **Fail Open on Cache Error** setting for the AI Proxy Limit. It does not apply to plans.

The plan's custom error messages are set on the **Error Message Customization** tab. For an AI Token Limit plan this includes the message returned when the counter store cannot be reached and the plan rejects (HTTP 503, ERR-307).

### Conditions and Error Messages

The **Conditions** tab holds a request condition. The plan counts and blocks only the requests that meet the condition; other requests are not limited by this plan. Leave it empty to apply to every request.

The **Error Message Customization** tab holds the messages returned when a limit is exceeded or when the target audience rejects a caller. It is available on both plan types, AI Token Limit included. When it is left at its defaults, the platform-wide messages of the [Error Messages](/en/admin/system-settings/error-messages) screen are used.

### Overlapping Plans {#overlap-rule}

An identity can have several plans, and each plan counts on its own. There is one restriction: **two plans that are counted the same way for one identity cannot limit the same API, endpoint or AI proxy**, and they cannot both set a general limit. The screens enforce this with an **Overlaps** badge, and the server rejects a conflicting plan.

- On the plan page, a limit row that would overlap another plan of an identity on this plan is blocked ("You cannot limit this here."). A limit that overlaps only in some environments or for some HTTP methods can be added for the remaining ones.
- On the **Limits** tab, a plan that overlaps a plan the identity already has is disabled in the **Add Limit Plan** list, and the tooltip names the reason.
- When the overlap depends on request conditions, the screen only warns (**Check conditions**): make sure the two conditions do not match the same request.

If you need a different limit for the same traffic, create a separate plan and add it to a different set of identities.

## Target Audience {#assignments-tab}

The **Target Audience** tab sets who the plan limits. This works the same way for both plan types, AI Token Limit included.

A caller is in the target audience if it is **a selected identity** or **matches a condition**. A caller that fits both is counted once, and a selected identity uses its own counter. An identity can also get the plan from its own **Limits** tab; it is then in the audience as well.

The tab shows a summary of the audience. A plan with an empty audience waits in the catalog; it can still be picked from an identity's **Limits** tab.

### Selected Identities

Under **Selected Identities** you add organizations, consumers, applications and API clients. The list shows the name, type and organization of each identity. For an organization, a consumer or an application, **Counted As** sets how the identity is counted — see [The Limits Tab](#assigning-a-limit-to-a-subject-the-limits-tab).

An identity added here to a plan that is not deployed is marked **Applies on deploy**.

### Callers Matching a Condition {#rule-assignments-limiting-by-identity-condition}

Under **Callers Matching a Condition** the plan also limits callers that are not selected one by one. Choose **Identify By**:

| Identify By | How the caller is recognized |
|---|---|
| **Authentication** | The username of the consumer, or the client ID of the API client, that the authentication policy resolved. |
| **Request Variable** | The value of the variable you select, read on each request. |

Then describe the callers with rows. The rows and the regular expressions are joined with OR:

- **Values** — type a value and press Enter, paste a list (`a#b#c`, `a,b` or one per line), or use **Import CSV**. A CSV file adds every cell; a first row "value" is skipped.
- **Regular expressions** — each matching identity is counted on its own. A capture group makes the identities that share it count together: with `team-blue-1` and `team-blue-2`, the group counts them under one shared counter. In **Counted as**, choose **Each identity on its own** or **Group 1 (shared)**. The expression is searched in the identity; use `^` and `$` to match the whole identity.

When **Identify By** is **Request Variable**, selected identities cannot be added next to the condition. Choose **Authentication** to select identities.

### Callers Outside the Target Audience

This setting decides what happens to callers the plan does not cover:

| Option | Meaning |
|---|---|
| **Not affected** | The default. Other callers are not limited by this plan. |
| **Rejected (403)** | Every other caller gets HTTP 403. When only identities are selected, this lets only the selected identities through. |
| **General quota** (**General limit** on an AI Token Limit plan) | Other callers share a quota or budget with its own limits. **One quota for all** (**One limit for all**) counts them together; **Separately per identity** gives each its own counter. |

The setting is evaluated together for all plans with a condition on the same API (or AI proxy, model or provider).

### Applying Changes

A change to the target audience is applied when the plan is deployed or redeployed.

## Plan Lifecycle: Deploy, Redeploy, Undeploy {#lifecycle-assign-edit-activate-end}

A plan is created, its limits are added, and it is then deployed. The plan shows one of three states:

| State | Meaning |
|---|---|
| **Undeployed** | The plan was never deployed, or was undeployed. It limits nothing. |
| **Deployed** | The gateways apply the saved version. |
| **Redeploy Required** | Changes were saved after the last deploy. The gateways keep applying the previous deployed version until you redeploy the plan. |

Click the state to open the deploy actions.

- **Deploy** and **Redeploy** open a preview drawer that lists the changes in the target audience, the limits and the settings. **Redeploy** also works with no change; it sends the version in force to the gateways again. When the plan is deployed, everyone on it gets the new values automatically.
- **Discard Changes** deletes the saved but not yet deployed changes, and the plan is the deployed version again. This cannot be undone.
- **Undeploy** stops the plan's limits on every gateway right away; requests are no longer counted or blocked by this plan. The assignments, the not-yet-deployed changes and the target audience are kept, so a new deploy brings the same limits back. **Counters are not reset**: after the next deploy, the limits continue from the current usage. You confirm by typing the plan name.

The plan page shows the version on the gateways while changes wait for redeploy, and the saved changes while you edit.

### Delete

- **Delete** — you confirm by typing the plan name. A deployed plan is undeployed first, so its limits stop on every gateway. The live assignments end, draft assignments are deleted, and the plan's information, limits, conditions, error message customizations, advanced settings and revision history are deleted. This cannot be undone.

### Revision History

The **Revision History** tab lists the deployed versions of the plan with their revision, status (**In force** or **Previous**), note, date and the user who deployed it. It reads "The plan is not deployed yet." until the first deploy.

## The Limits Tab {#assigning-a-limit-to-a-subject-the-limits-tab}

A plan reaches an identity through that identity's **Limits** tab. The tab exists on an **organization**, a **consumer**, an **application** and an **API client**. A section for each plan type (**AI Token Limit**, **API Request Count**) lists the plans that apply to the identity.

Each plan on the tab is shown as a card with the plan name (a link to the plan), the plan's state — **Deployed**, **Redeploy Required** or **Undeployed** — how it is counted, and badges such as **Deploy Required** and **Overlaps**. The card shows the plan's **definition** only. It does not show usage — see [Where to See Usage](#live-usage-on-the-limits-tab).

An identity can have **several plans of one type**, and each plan counts on its own. A different limit means a separate plan.

### Adding and Removing Plans

**Add Limit Plan** lists every plan of the type. A plan that cannot be added is disabled, and the tooltip gives the reason (for example, an overlap, or the plan is already applied). For an organization and a consumer you also choose **Counted As**. It cannot be changed afterwards; to change it, remove the plan and add it again.

**Counted As** for an **organization**:

| Option | Meaning |
|---|---|
| **Organization total** | One shared counter for everyone under the organization, including the API clients of its consumers and applications. |
| **Each API client** | Every API client under the organization that has no assignment of its own gets the plan with its own counter. |
| **Each consumer** | Every consumer and application under the organization without its own assignment gets the plan with its own counter. |
| **Each sub-organization** | Every sub-organization without its own assignment gets the plan with its own counter. |

**Counted As** for a **consumer**: **Consumer total** (one counter; its API clients are in the consumer's total and in the totals of the organizations above) or **Each API client**. An application is counted like a consumer (**Application total**).

The "Each …" options also cover identities added later.

When you add a plan from an identity's own page, it is saved as a draft and applies when the identity is deployed:

- For an organization, consumer or application, the plan applies when that identity is deployed. The card shows **Deploy Required**, and the identity shows **Redeploy Required**.
- An API client has no deploy of its own. The plan applies when the consumer or application that owns it is deployed.
- If the plan itself is not deployed, it also waits for the plan's deploy.
- A draft written elsewhere shows an **Apply** button on its row.

**Remove** stops the plan from applying to this identity immediately. The plan itself is not deleted and still applies to other identities. You can enter a reason. The **Removed Limit Plans** table lists the plan, type, start, end and reason. If you add the same plan again, it starts with a new counter.

A plan added by an administrator from the Administration menu carries the **Assigned from Administration** badge; only a system administrator can remove it.

### Inherited Limit Plans

**Inherited Limit Plans** lists plans that an organization or a consumer above the identity applies to the identities under it with an "Each …" option. The list is read-only. The identity gets the nearest one. When the identity's own assignment applies to a request, the own assignment is used for that request instead.

## Bulk Assignment {#bulk-assignment}

Adding a plan to one identity at a time does not scale once a project has thousands of them. **Bulk Assignment** adds one **deployed** plan to many identities in a single run.

Reach it from the **Bulk assignment** button in the plan list, or from a plan with the plan pre-selected. The **Back** button returns to the plan list. The screen has two tabs: **New Assignment** and **History**. A three-step flow builds a run:

1. **Limit Plan** — pick the plan. Only deployed plans are listed. Limits, targets and error settings come from the plan; they cannot be changed on this screen.
2. **Identities** — choose the identity type (**Consumers**, **API Clients**, **Applications** or **Organizations**), narrow the list with filters, and select the identities. Ticking an organization also covers its sub-organizations. Identities that already have this plan cannot be selected. **Select all … that match the filter** selects the whole filtered population in one click; identities added after the start are not included.
3. **Review and Start** — the screen shows how many identities will get the plan, and how many already have it (they are skipped). The numbers are an estimate for large selections.

Under **What happens to the other limit plans?** you choose how identities that already have another plan of the same type are handled:

| Option | Meaning | Default |
|---|---|---|
| **Keep them** | The new plan is added next to the current plans. The other plans and their counters do not change. | Yes (recommended) |
| **Replace them with the new plan** | The other plans of the same type of these identities are removed. The counters of the new plan start from zero. | — |

An optional **Validity** sets a start and an end date; by default the plan starts now and does not expire.

**Start Assignment** queues the run. It runs in the background, and you can leave the page.

### History

The **History** tab lists every run with its start time, plan, identities, result (added, removed, restored, skipped, failed), status and who started it.

| Status | Meaning |
|---|---|
| **Queued** | Accepted, not yet picked up. |
| **Running** | Actively processing. |
| **Success** | Every identity was processed with no failures. |
| **Partial** | Finished, but at least one identity failed. |
| **Failed** | The run could not complete. |
| **Cancelled** | Stopped by an operator with **Stop**. |
| **Interrupted** | The node running it stopped responding mid-run. |

Runs recorded by an older version may still show **License revoked**, a state this version no longer produces.

- **Details** lists the skipped and failed identities with the reason for each.
- **Stop** asks a running run to stop at its next step; what was already written stays.
- **Retry Failed** starts a new run over only the identities the run failed on.
- **Roll Back** removes the plan from the identities the run added it to, and brings back the old plans the run removed (their counters restart, as with any replacement). The rollback is added to History as a new record. A confirmation comes first.

An interrupted run is resumed with **Retry Failed**. If writing the new assignment fails during a **Replace** or a rollback, the engine puts the old assignment back rather than leaving the identity with no limit; if even that fails, the row says the identity has **no limit of this type now**, and **Retry Failed** is the recovery.

## Working Together With Your Existing Limits

**API Request Count**: an existing [Rate Limit Control List](/en/admin/identity-management/rate-limit-control-list) or an [API Proxy ACL](/en/admin/identity-management/api-proxy-acl)/[API Proxy Group ACL](/en/admin/identity-management/api-proxy-group-acl) quota/throttling setting is **no longer applied by the gateway** — on upgrade, every such legacy limit was converted into a limit plan and assignment, so the ceiling itself carries over; only the mechanism enforcing it changed. See [Legacy Limits Migrated at Upgrade](#legacy-limits-migrated-at-upgrade) below for exactly what moved and how.

**AI Token Limit**: the Token Quotas screen and the organization, application, project and platform budgets it saved are removed. Apinizer did not convert them. Recreate each limit as a plan, or as AI Proxy Protection on the [Token Rate Limit policy](/en/ai-gateway/token-quotas). See [Removed AI Budgets](#removed-ai-budgets) below.

## Enforcement {#enforcement-status-shadow-mode}

### API Request Count

A plan enforces for real once it is deployed. The gateway counts a request for every limit that covers it, and the first limit that fills stops the request. A plan that identifies callers by **Authentication** only applies to traffic that runs through an authentication policy, and treats an unauthenticated caller as outside its target audience. A plan that identifies callers by a **Request Variable** needs no authentication policy.

Per window:

- **Granted** — the request proceeds; the response gets the statistics headers if **Remaining Limit in Response Headers** is on.
- **Exceeded, Reject the request** — HTTP 429 with `Retry-After`; the error is a throttling error (second/minute windows) or a quota error (hour/day/month windows), customizable on the platform-wide [Error Messages](/en/admin/system-settings/error-messages) screen and on the plan's **Error Message Customization** tab. The `Retry-After` value is capped at a platform-wide ceiling (1 day by default, changeable with the `apinizer.limit.retryAfterClampSeconds` JVM system property on the Worker) rather than reporting the full window — this applies to an API Request Count and an AI Token Budget block alike.
- **Exceeded, Let it pass, only count** — the request is counted and let through; nothing is blocked.
- **Counter service unreachable** — the plan's **If the Counter Store Is Unreachable** setting: **Reject the request** or **Let the request pass**.

**Observability**: a Prometheus counter `apinizer_limit_typed_decisions_total{family, outcome}` (outcome: `granted` / `blocked` / `count_only` / `cache_error_continue` / `cache_error_fail` / `out_of_target_block`) tracks every enforcement decision.

### AI Token Limit {#ai-token-budget-still-shadow}

A deployed plan is enforced on every AI request in its target audience, with or without the [Token Rate Limit policy](/en/ai-gateway/token-quotas). The policy limits the AI proxy as a whole; plans limit the callers. Deleting or deactivating the policy does not stop plans.

- **Who is limited.** For a plan on a consumer or an API client, the gateway needs the caller's identity: an authentication policy on the proxy, or recognition by a **Request Variable**.
- **What is counted.** A call is counted in the general budget and in every target budget that covers it. The first budget that fills stops the call. Each target row has its own counter.
- **Environment values.** The value of one environment replaces the **All environments** value in that environment; they are not added.
- **Reservation.** At the start of a request, the estimated tokens are reserved. When the response ends — streamed or not — the reservation is corrected with the real usage. If every provider fails, the reserved amount is released.
- **Counters.** Counters live in the shared cache service, so every worker uses the same counter, and a worker restart does not reset them.
- **Windows** are aligned to the UTC calendar: they renew at the start of each minute, hour, day (00:00 UTC) and month.
- **USD per minute.** The cost of each call is counted in the current UTC minute. The hard cap percentage applies. When the limit is exceeded, the plan's action applies. With **Reject the request**, the response is HTTP 429 and `Retry-After` is the number of seconds left to the end of the minute. The per-model and per-provider lines inside a budget have no minute window, for tokens or for USD. Usage reports and alarms do not show minute windows. The per-minute USD counters are kept only in memory and are not saved to the database. When you upgrade, upgrade the Cache servers before the Workers.
- **When the budget is reached**, the plan's action applies: **Reject the request** (HTTP 429 with `Retry-After` — the seconds left until the window ends, capped at 86,400 by default), **Let it pass, only alert**, **Switch to a cheaper model**, or **Fail over**. If no cheaper model is defined, the provider does not allow it, or the consumer has no access to that model, a **Switch to a cheaper model** request is rejected with HTTP 429.
- **Alerts.** When an alert threshold is crossed, or a call passes under **Let it pass, only alert**, the traffic record is marked and the event shows in the **Recent Alerts** area of AI Gateway analytics. Nobody is notified automatically — see [Token Rate Limit Policy](/en/ai-gateway/token-quotas#threshold-alarms).
- **Counter store unreachable.** The plan's **If the Counter Store Is Unreachable** setting decides. See [Advanced Settings](#cache-posture-and-custom-error-message).
- **Several limits.** A request must pass every plan that covers it, and the AI Proxy Limit of the Token Rate Limit policy. The first limit to fill stops the request.

### USD Limits Need Model Prices {#usd-limits-need-model-prices}

A USD limit, including **USD/Minute**, meters only models that have an input price ("price per million input tokens") in the provider's [Models](/en/ai-gateway/llm-providers#model-prices) section. A model without a price counts as 0 in cost reports, so a USD limit does not meter it and never cuts it off. Apinizer does not refuse to save such a limit.

Set an input price for every model that the USD limit must cover, or use a token limit instead.

The same applies to AI proxies that use **Use the client's model**: the client can request any enabled model of the routed LLM provider, so a USD limit meters only those of them that have a price. See [USD limits need model prices](/en/ai-gateway/token-quotas) for details.

### The "Rate Limit" Badge on Develop

The **Rate Limit** badge shown on an API proxy's Develop screen is computed only from the plans currently covering the proxy. Clicking it opens a dialog listing every active assignment covering this proxy; each row names its subject and, when narrowed, the proxy or proxy group name.

A row whose subject no longer exists is marked **Deleted consumer** (or application, organization, API client) instead of showing a bare identifier, and that row carries its own **End** action, available to anyone who may manage limits.

:::note Assignments left over from an earlier version
On upgrade, Apinizer ends every assignment whose subject no longer exists and records the reason as *The subject no longer exists*. The same check runs again each night, so an assignment orphaned later — by an import that replaced a record, or by a manual database correction — is closed on its own rather than staying in force.
:::

### Reports and Alerts

A counter attributed to a **Consumer** (or an API Client migrated from one) is folded into that consumer's existing counters, shown under the [Quota Usage & Alerts](/en/admin/identity-management/quota-usage-and-alerts) report's existing **Plan** type, and caught by whatever Alert Definition already watches that consumer's Plan-type counters.

A counter attributed to any other subject (a project, an organization, an API proxy, the platform) keeps its own counter type instead — it is shown labeled **Other** in the report, but only once **Show other counters** is turned on (off by default). No pre-existing Alert Definition fires on it: an alert rule written before these limits existed must not silently start watching them. Alert notification text that does reference it labels it **Rate Limit**. Create a dedicated Alert Definition if you want to be notified.

## Where to See Usage {#live-usage-on-the-limits-tab}

The **Limits** tab does not show usage; it shows what each plan defines. Usage is shown here:

- **Quota Usage & Alerts** (**Identity Management → Quota Usage & Alerts**) — the usage of the counters, AI token and AI cost rows included. See [Quota Usage & Alerts](/en/admin/identity-management/quota-usage-and-alerts).
- **AI Analytics** — the cost chart. It shows the cost of the month so far and has no budget line. See [Reports and Analytics](/en/ai-gateway/reports).

A Quota Usage alert rule evaluates AI counters only if **AI Token** and/or **AI Cost** is selected in the rule's counter types. With an empty list, the rule covers the gateway request counters only.

## Error Codes

When a plan blocks or rejects a request, the caller sees one of these answers. The **How to Read** guide of the plan page lists them too.

| HTTP code | When |
|---|---|
| **429** | A limit is reached. The `Retry-After` header gives the wait time. For an AI Token Limit plan the error code is ERR-263. |
| **403** | The caller is outside the target audience of a plan, and **Callers Outside the Target Audience** is **Rejected (403)**. |
| **503** | The counter store cannot be reached and an AI Token Limit plan is set to **Reject the request**. The error code is ERR-307. |
| **400** | The variable of a condition is missing from the request, so the caller cannot be identified. |

All messages are customizable on the [Error Messages](/en/admin/system-settings/error-messages) screen and on the plan's **Error Message Customization** tab. The default body of the AI Token Limit 429 answer is shown in [Token Rate Limit Policy](/en/ai-gateway/token-quotas#what-the-caller-receives).

If a limit does not work, check in order:

1. When **Identify By** is **Authentication**: does the API proxy have an authentication policy?
2. Is the plan deployed?
3. Is the plan on the identity's **Limits** tab?
4. Does the limit point at the right API and endpoint?

## Legacy Limits Migrated at Upgrade {#legacy-limits-migrated-at-upgrade}

When you upgrade to a version where the legacy API Request Count path is retired (see [Working Together With Your Existing Limits](#working-together-with-your-existing-limits) and [Enforcement](#enforcement-status-shadow-mode) above), every legacy API Request Count limit is converted into a limit plan and assignment automatically, before the Manager accepts requests. This section describes what that conversion does.

:::warning Legacy limits migrated at upgrade
On the upgrade, every legacy Rate Limit Control List rule and every API Proxy ACL/API Proxy Group ACL throttling/quota setting is converted into a limit plan and assignment — the gateway no longer reads either legacy source at all. Afterward, expect to see `Migrated REQUEST_RATE #<checksum>` plans in your catalog and assignments with source **Migration** on your identities; like every migrated API Request Count assignment, their counters start at zero — a migrated AI Token Limit assignment is the one exception, see [AI Budgets](#ai-budgets) below.
:::

### Sources

- Every environment-scoped **throttling** and **quota** setting on an [API Proxy ACL](/en/admin/identity-management/api-proxy-acl) or [API Proxy Group ACL](/en/admin/identity-management/api-proxy-group-acl) row.
- Every [Rate Limit Control List](/en/admin/identity-management/rate-limit-control-list) record.

### Plan Creation and Deduplication

Rows that share the exact same rule body — the same windows and the same enforcement posture — are folded into a **single** plan per project, identified by a canonical checksum of that body, so thousands of legacy rows typically converge on a handful of plans:

| Field | Value |
|---|---|
| Name | `Migrated REQUEST_RATE #<checksum>` (checksum's first 8 hex characters) |
| Tags | `migrated`, `checksum:<sha>` |
| Description | "Migrated from legacy access-row / rate-limit-list limits: …" |
| Type | API Request Count |
| State | Deployed |

### Window Mapping

| Legacy field | Window |
|---|---|
| Throttling, 1 Second / 1 Minute interval | Second / Minute window |
| Quota, 1 Hour / 1 Day / 1 Month interval | Hour / Day / Month window |
| Both throttling and quota on the same row | Both windows, on the same plan |

Window Type (Fixed/Sliding) and Counting Mode are carried over unchanged for each window.

### Enforcement Posture

- **If the Counter Store Is Unreachable**: **Reject the request** if either the throttling side or the quota side of the legacy row rejected.
- **Connection Timeout**: the larger of the two legacy timeouts.
- **Remaining Limit in Response Headers**: carried over if set on the legacy row.
- A Rate Limit Control List's own custom error message, content type, and HTTP status code are carried over as the resulting plan's custom error message.

### Assignment

Every migrated row becomes one assignment with source **Migration**, active, with its own end date set to the row's expiry date, if it had one.

| Legacy row | Subject | Scope |
|---|---|---|
| API Proxy ACL / API Proxy Group ACL row | The Consumer itself — the same whether the Consumer was later migrated to an API client or stayed [**Consumer only**](/en/admin/identity-management/credentials#decision-values); when its twin belongs to a portal application, the **API client** (its client id) instead | One API Proxy + Environment / One API Proxy Group + Environment, matching the row's environment |
| Rate Limit Control List rule | Same subject rule as the row above | One API Endpoint (the rule's own endpoint) / One API Proxy (a rule written for every endpoint) / One API Proxy Group |

A Rate Limit Control List's **Target Consumers** list was, in legacy behavior, that rule's own **allow list**: an identity missing from it received the rule's out-of-target action instead of the rule's own ceiling. The migration keeps that shape: each listed Consumer still gets its own explicit assignment as in the row above, **and** one additional condition-based assignment is written for the list as a whole — an **In** condition whose value is the resolved identities (username or client id) — carrying the rule's out-of-target action and, where the rule had one, its general quota. A listed Consumer's own explicit assignment always outranks that condition-based assignment on the same target; a Consumer left off the list falls through to the rule's out-of-target action, the same as it did before the upgrade.

A Rate Limit Control List's **Target Audience** conditions and its equality-based target identity values (not already covered by the Target Consumers list) become their own condition-based assignments the same way: the identity source (auth-resolved or variable), the out-of-target action (Block, or a general quota), and the general quota itself (Total/Per identity, with its own window) all carry over. When the out-of-target action is a general quota but its quota fields were left empty, the rule's own limit is carried over as the general quota instead — the same fallback the legacy runtime applied. A rule left with nobody to migrate — no consumers, no identities, no condition — produces no assignment at all.

### AI Budgets

:::note History
This section describes the 2026.09.2 upgrade. The **AI Budget Source** setting and the remaining entity budgets were removed later, in 2026.10.0. See [Removed AI Budgets](#removed-ai-budgets).
:::

A consumer-level AI token budget is migrated the same way, from a different source and into a different plan type:

- **Source**: the environment-level **Enable AI Token Budget** setting (and its budget values) on an [API Proxy ACL](/en/admin/identity-management/api-proxy-acl)/[API Proxy Group ACL](/en/admin/identity-management/api-proxy-group-acl) row.
- **Plan**: rows sharing the exact same budget body are folded the same way API Request Count rows are — one **AI Token Limit** plan per distinct body, named `Migrated AI_TOKEN_BUDGET #<checksum>` (first 8 hex characters), tagged `migrated` and `checksum:<sha>`, deployed.
- **Assignment**: subject is the Consumer itself — the same twin the API Request Count migration above targets — or, when that Consumer's migrated API client belongs to a portal application, the **API client** instead; scope One API Proxy + Environment, matching the row's own proxy and environment; source **Migration**; end date the row's own expiry, if it had one.
- **No counter reset**: unlike every other migrated assignment, this one is counted under the same counter the legacy budget already used, so in-window consumption carries over rather than restarting at zero. A Consumer later migrated to an API client keeps sharing that same counter with its legacy record.

In 2026.09.2, the row's **AI Budget Source** field only decided whether the organization-level AI budget chain applied to that Consumer on that proxy. That field is removed. To stop the migrated assignment, remove the plan on the identity's [Limits tab](#assigning-a-limit-to-a-subject-the-limits-tab).

Not every enabled row is carried — see the AI-specific outcomes in [Not Migrated (Reported Only)](#not-migrated-reported-only) below. A row whose **AI Budget Source** was **Organization** is the notable case: its own budget was never enforced even before this migration (only the organization chain applied to it), so nothing is lost by leaving it out — add a plan directly on the Limits tab if you want that Consumer to also carry its own ceiling. A row whose Consumer no longer exists is skipped and recorded as `CREDENTIAL_MISSING`, the same as a portal-derived or expired row is skipped and counted without being listed individually.

### Not Migrated (Reported Only)

The following legacy items have no counterpart, are intentionally skipped, or are carried over with a caveat; each is recorded in the migration's audit ledger:

| Legacy item | Outcome |
|---|---|
| Quota/Throttling **Limit Change Action** (Clamp / Reset) | Dropped — no equivalent |
| A Rate Limit Control List's **condition** | Dropped; the rest of the rule is still migrated |
| A Rate Limit Control List's **Execution Order** set to "after the API method policies" (`LAST`) | Dropped; a plan always evaluates at the authentication moment |
| A **disabled** Rate Limit Control List | Not migrated |
| An expired row | Skipped |
| A row disabled for its environment | Skipped, recorded as `ENV_DISABLED_SKIPPED` |
| A row whose limit fields were left incomplete | Skipped, recorded as `LIMIT_INCOMPLETE_SKIPPED` |
| A Rate Limit Control List rule with no limit configured on it | Skipped, recorded as `RULE_WITHOUT_LIMIT` |
| A row pointing at a deleted API, group, or endpoint | Skipped, recorded as `RULE_TARGET_MISSING` |
| An API Proxy ACL/Group ACL row with a different cache-error posture for its throttling side than its quota side | Both carried onto the assignment as **Reject the request**, the stricter of the two, recorded as `CACHE_POSTURE_MERGED` |
| A rule audience whose out-of-target action is **General quota** but whose quota fields were left empty | The rule's own limit is carried over as the general quota instead, recorded as `GENERAL_QUOTA_FALLBACK` |
| A Rate Limit Control List with no consumers, no target identities, and no condition to migrate | Nothing is migrated, recorded as `EMPTY_AUDIENCE_SKIPPED` |
| A **portal-derived** (subscription/product) row | Skipped — carried instead by the Subscription Plan assignment backfill; see [Upgrading Existing Subscription Plans](#upgrading-existing-subscription-plans) |
| A row's **AI Budget Source** set to **Organization** (2026.09.2 setting) | Not carried — see [AI Budgets](#ai-budgets) above; recorded as `AI_LEAF_EXCLUDED_BY_SOURCE`, information only, not a residual failure |
| **Enable AI Token Budget** on but the budget itself disabled or naming no ceiling | Skipped, recorded as `AI_BUDGET_INCOMPLETE_SKIPPED` |
| A row with **Enable AI Token Budget** on but no API proxy named on it | Skipped, recorded as `AI_BUDGET_TARGET_MISSING` |

Re-running the migration is idempotent: an identity/scope pair that already has an active assignment from a previous run is left as-is, not written again.

## Project and Platform Limits Removed {#project-and-platform-limits-removed}

Version 2026.10.0 removed the **Project and Platform Limits** screen and the project and platform assignments. A limit plan can be assigned to a consumer, an API client, an application, an organization, an API proxy (AI Gateway) or an audience rule. This holds for both types: **API Request Count** and **AI Token Limit**. The gateways no longer enforce project or platform assignments.

On upgrade, Apinizer does the following once, when the Manager starts:

- Every project and platform assignment that was not yet ended is ended. It is ended by `system` with the reason "Project and platform limits were removed in this version". No screen shows it any more. You can read it through the Management API or APIops. The gateways stop applying it.
- Every enabled **AI Token Usage Percentage** alarm with the **Project** scope is disabled. Apinizer keeps the alarm. Change its scope to **AI Gateway** and enable it again. See [Alarm](/en/monitor/alarm).

The REST and Management API refuse a new project or platform assignment. A package import skips a project or platform assignment file, shows the notice "These limit assignments were NOT imported" and imports the rest of the package.

To limit a whole population, assign the plan to the consumers, API clients, applications or organizations, or use the **Counted As** choices of an organization.

## Removed AI Budgets {#removed-ai-budgets}

Version 2026.10.0 removed the **Token Quotas** screen and every budget it saved:

- the organization AI budget;
- the AI proxy application budget and the anonymous budget of the AI proxy routing;
- the project (tenant) budget;
- the default budget and the default anonymous budget in AI Gateway Settings;
- the **AI Budget Source** setting and the AI token budget per environment on an access row.

The upgrade removes the stored values. It does **not** convert them into plans. Recreate each limit:

| Removed limit | Where to set it now |
|---|---|
| Limit for an organization, consumer, application or API client | An **AI Token Limit** plan, added on the **Limits** tab or in the target audience. |
| Limit for a whole project or the platform | Removed. See [Project and Platform Limits Removed](#project-and-platform-limits-removed). |
| Limit for one AI proxy | **AI Proxy Protection** in the [Token Rate Limit policy](/en/ai-gateway/token-quotas#ai-proxy-protection). |

Export packages and APIops requests that still carry the old fields are accepted. Apinizer ignores the fields and keeps the rest.

## Referenced by a Portal Subscription Plan

A deployed, platform-scope plan can also be referenced from a portal API Product's **Subscription Plan** — the commercial plan a developer subscribes to — instead of, or alongside, being added by hand on the Limits tab. See [API Product → Limit Profiles](/en/api-portal/api-product#limit-profiles) and [→ Typed Limit Binding](/en/api-portal/api-product#typed-limit-binding) for how this is configured and materialized on the product side; this section covers what happens on the limit side.

A Subscription Plan may reference at most one API Request Count plan and one AI Token Limit plan, each **Off** or a specific deployed plan. The referenced plan's overflow posture must agree with the Subscription Plan's own on-exceed setting — **Block** needs a plan that blocks, **Continue & charge** needs a plan that only counts (**Let it pass, only count** for API Request Count, **Let it pass, only alert** for AI Token Limit) — a mismatch is refused when the Subscription Plan is saved.

When a subscription of that plan is **approved**, one active assignment is created automatically for the subscribing application, per referenced type — sourced from the subscription rather than entered by hand, application-wide rather than tied to one API. Both a subscription-sourced API Request Count assignment and a subscription-sourced AI Token Budget assignment enforce for real.

An application can have only one such assignment per type. If a second, different subscription of the same application also references a plan for that type, the existing assignment is **kept**, and the operator approving the second subscription is asked to keep it or switch to the new plan. When a subscription that owns the assignment ends, it is handed over to another still-approved subscription of the same application that references the same type, if one exists, so coverage and accumulated usage are not lost; otherwise the assignment ends with it.

### Upgrading Existing Subscription Plans

On upgrade, Subscription Plans that already carry quota or rate-limit numbers are converted automatically: a matching platform-scope API Request Count plan is created and the Subscription Plan is pointed at it, so nothing changes for existing subscribers. Subscriptions that were already **approved** before the upgrade do not receive their assignment automatically — a system administrator runs a one-time backfill (previewed by default, applied on request) to create it for the existing backlog. See [API Product → Version Upgrade](/en/api-portal/api-product#version-upgrade) for the portal-side summary and the [Limit Plans, Assignments & Defaults API](/api-reference/limit-plans) reference for the backfill endpoint.
