## What the Policy Does

The **Token Rate Limit** policy protects one AI proxy. It does two jobs:

- **AI Proxy Protection** limits the tokens and cost that all callers of the proxy spend together.
- **Oversized Guard** blocks a single request that is too large.

The policy does not set limits for each caller. Limits for a consumer, API client, organization, project or platform are set on [Limit Plans](/en/ai-gateway/limit-plans). The gateway applies them to every AI request, with or without this policy.

Deleting or deactivating the policy removes only the protection of the proxy. Caller limits keep working.

New AI proxies are created with this policy attached. Add the policy to the request policy list of an AI proxy if it is missing.

<Steps>
  <Step title="Add the Policy">
    Add **Token Rate Limit** to the request policy list of the AI proxy.
  </Step>

  <Step title="Turn On the AI Proxy Limit">
    In the **AI Proxy Protection** section, turn on **Active**. When it is off, the screen shows **No limit**.
  </Step>

  <Step title="Set the Limits">
    Set the token windows, the USD windows, **Hard Cap (%)**, **Alert Thresholds (%)** and **Overflow Action**.
  </Step>

  <Step title="Deploy">
    Deploy the AI proxy. Then compare the reservations with the real use in AI Reports.
  </Step>
</Steps>

## AI Proxy Protection {#ai-proxy-protection}

**AI Proxy Limit** is the total for every caller that reaches the proxy. It is a budget form with these fields:

| Field | Description |
|---|---|
| **Tokens/Minute**, **Tokens/Hour**, **Tokens/Day**, **Tokens/Month** | Token limits for each window. |
| **USD Budget / Hour**, **USD Budget / Day**, **Monthly Budget (USD)** | Cost limits for each window. |
| **Hard Cap (%)** | The percentage of a limit at which the overflow action starts. The default, 100, means when the limit is full. |
| **Alert Thresholds (%)** | Percentages at which an alert is raised. |
| **Overflow Action** | What happens when a limit is reached. See [Overflow Actions](#overflow-actions). |

Token limits and USD limits are independent. You can set only token limits, only USD limits, or both.

Windows are aligned to the **UTC calendar**. A minute, hour, day or month window renews at the start of the next minute, hour, day (00:00 UTC) or month. It does not renew a fixed time after the first request.

### Model Limits and Provider Limits

Under **Model limits** you give one model its own limit. Under **Provider limits** you give one LLM provider its own limit. A request is counted in the proxy limit and in every line that covers it. The first limit that fills stops the request.

Each line needs a model or a provider and at least one limit. The screen refuses a model or a provider that is listed twice.

### Split by Variable {#split-by-variable}

By default the proxy limit is one total for every caller. With **Split by Variable**, you select a variable, for example a tenant header. The limit is then counted separately for each value of the variable.

Under **Per-Value Limits**, click **Add Value** to give one value its own limit. Each row has these fields:

| Field | Description |
|---|---|
| **Value** | The value of the variable that the row covers. |
| **Regular Expression** | When on, the row covers every value that matches the expression. The expression needs a capture group, for example `^(team)-.*$`. The first capture group is the value the row counts under. Values that share a capture group share one counter. |
| Limit form | The row's own token, USD, hard cap, alert and overflow settings. |
| **Active** | The row must be on and must set at least one limit. The server rejects a row that does not. |

A request whose value matches a row is counted against that row. Other values are counted against the default limit, each value on its own.

Per-value rows need a variable. The screen asks you to select a variable or remove the rows. Rows work like the per-value rows of the API Throttling policy.

:::warning USD limits need model prices
A USD limit works only for models that have an input price set in the [Model Catalog](/en/ai-gateway/model-catalog). The price is "price per million input tokens" on the model, or on the supported model row of the LLM provider. Apinizer refuses a USD limit on a model without a price:

- when you save a [Limit Plan](/en/ai-gateway/limit-plans#usd-limits-need-model-prices) or this policy;
- when you deploy a plan;
- when a routing change on an AI proxy would reach a model without a price.

Fill in the missing price, or use a token limit instead.
:::

## Overflow Actions {#overflow-actions}

When a request would exceed a limit, you choose what happens next:

<CardGroup cols={2}>
  <Card title="Block" icon="ban">
    The request is rejected outright. The `429` response also carries a `Retry-After` header (in seconds) stating when the window reopens.
  </Card>
  <Card title="Failover" icon="route">
    The request is routed to the backup provider in the [failover chain](/en/ai-gateway/routing-and-failover) instead of being rejected. If the routing has no backup provider, the request is rejected with HTTP `429`. It is not sent to the over-budget primary.
  </Card>
  <Card title="Alert Only" icon="bell">
    The request goes through as usual; only a warning is raised.
  </Card>
  <Card title="Downgrade Model" icon="trending-down">
    The request is automatically redirected to the **Cheaper Model** instead of being blocked.
  </Card>
</CardGroup>

If no cheaper model is defined, the provider does not allow the switch, or the caller has no access to the cheaper model, the request is rejected with HTTP `429` instead.

:::info Retry-After is clamped
The `Retry-After` value is the time remaining until the exceeded window (minute/hour/day/month) closes, but it is capped by the `apinizer.limit.retryAfterClampSeconds` JVM system property on the worker (default `86400`, i.e. one day) — so a monthly window never reports a 30-day wait, at most one day. A client that retries earlier simply gets a new `429` with an updated `Retry-After`; counter accuracy is unaffected. The clamp applies to every window, not only monthly ones.
:::

## Per-Request Size Limit {#per-request-size-limit}

Separate from the proxy limit, you can cap the size of a **single request**. The policy checks this before the time-windowed limit, as a cheap pre-flight step. It lives in the **Oversized Guard** section:

:::tip Usable with no limit defined
This section works on its own. An installation that only wants to cap request size can add the Token Rate Limit policy and fill in these fields alone, with **no AI Proxy Limit** — the limit tier never engages and the request never reaches the cache. The *Quota Reservation & Cache Behavior* settings only matter once the AI Proxy Limit is on.
:::

| Field | Description | Default |
|---|---|---|
| **Max Tokens Per Request** | Blocks a single request whose estimated token count exceeds this value. Empty = no limit. | — |
| **Max Prompt Characters** | Blocks a single request whose prompt character count exceeds this value — only the prompt text itself is counted, not JSON envelope fields such as `model` or `stream`. Empty = no limit. | — |
| **Limit Source** | Where the effective token limit comes from: **Explicit** uses Max Tokens Per Request above; **Model Catalog** derives it from the selected model's context window instead (context window minus max output tokens minus a safety margin). If the model's context window is unknown, the limit is skipped for that request rather than blocking it. | Explicit |
| **On Overflow** | What happens when the token limit is exceeded: **Block** rejects the request; **Truncate Oldest Messages** drops the oldest conversation turns instead, until the request fits. Character-count overflow always blocks, regardless of this setting. | Block |

:::info Truncation is visible, not silent
When a request is truncated, Apinizer always preserves every `system` message and the last `user` message — if those alone still exceed the limit, it falls back to Block rather than send a partial conversation. A successful truncation is tracked in three places: the `X-Apinizer-AI-Truncated` response header (number of dropped messages), the [Guardrail Hits report](/en/ai-gateway/reports#security-and-guardrails-tab) (as `truncated`, alongside `oversized`), and — if [AI Trace](/en/ai-gateway/tracing-and-replay) is active on the proxy — that request's trace detail.
:::

This is a different concept from the **Overflow Actions** above: the proxy limit runs out over time, but the per-request size limit is about a single request that is too large for the model's context window.

## What the Caller Receives {#what-the-caller-receives}

When the overflow action is **Block**, the Token Rate Limit policy answers with HTTP `429`, error code **ERR-263**, and a `Retry-After` header. The default body is:

```json
{"error":{"code":429,"message":"AI token quota exceeded","type":"insufficient_quota"}}
```

You can change the message on the [Error Messages](/en/admin/system-settings/error-messages) screen. For a limit that comes from a Limit Plan, you can also change it on the plan's **Error Message Customization** tab.

## Threshold Alarms {#threshold-alarms}

<Card title="Usage Alerts" icon="triangle-alert">
  When usage crosses an alert threshold (**Alert Thresholds (%)**, from 1 to 99 in ascending order; Limit Plans use 50, 80 and 90 by default), the request's traffic record is marked and the event appears in the **Recent Alerts** area of AI Gateway analytics. A request that passes because its overflow action is **Alert Only** is recorded the same way.
</Card>

:::warning No notification is sent automatically
Crossing a threshold does **not** notify anyone on its own. To be notified, create an alert rule: either a rule on the [Quota Usage & Alerts](/en/admin/identity-management/quota-usage-and-alerts) screen with **AI Token** and/or **AI Cost** selected in its counter types (an empty counter-type list covers the gateway request counters only), or an alarm with the **AI Quota Soft-Cap Hit Count** or **AI Quota Alert-Only Count** trigger.
:::

## How Limit Tracking Stays Accurate

:::info
Before a request is sent to the model, Apinizer estimates its token cost and reserves that amount against every applicable limit and window. Once the response finishes — including streamed responses — the reservation is adjusted to match the actual tokens consumed. This keeps concurrent requests from over-counting or under-counting against your limits.
:::

Counters are kept in the shared cache service, so every worker uses the same counter and a worker restart does not reset them.

The **Quota Reservation & Cache Behavior** section holds the reservation settings: **Default Reservation TTL (s)**, **Cache Connection Timeout (s)** and **Fail Open on Cache Error**. They apply to the AI Proxy Limit of this policy only. A Limit Plan uses its own cache settings, or the settings of its assignment.

## When the Counter Store Is Unreachable {#when-the-counter-store-is-unreachable}

If the cache service that holds the counters cannot be reached, the **Fail Open on Cache Error** switch decides what happens to the AI Proxy Limit of this policy. A Limit Plan has its own setting, **If the Counter Store Is Unreachable**; see [Advanced Settings](/en/ai-gateway/limit-plans#cache-posture-and-custom-error-message).

- **Off** (the default, fail-closed): the request is rejected with HTTP `500` and error code ERR-234.
- **On** (fail-open): the request passes without a limit while the cache is down.

## Limit Plans and This Policy {#working-with-limit-plans}

The policy limit and the limits of [Limit Plans](/en/ai-gateway/limit-plans) are independent. A request must pass both, and the first limit to fill stops it. The policy limit is the total of the proxy. The plans limit each caller.

## Monitoring Limit Usage

View real-time consumption in [Reports and Analytics](/en/ai-gateway/reports):

- **Tokens Used** and **Tokens Remaining** for the current window
- **Cost to Date** against any configured budget
- **Alerts** raised as usage approaches a limit

The [Quota Usage & Alerts](/en/admin/identity-management/quota-usage-and-alerts) screen shows the usage of the counters, AI token and AI cost rows included. AI proxy rows on that screen come from this policy: one row for an undivided proxy limit, and one row for each per-value row that has a fixed value. A policy that is split by a variable counts each value of its default limit on its own, so the default limit has no single row.

The **Limits** tab of an identity shows only what its plans define, not usage.

### Reading the same numbers through the Management API

What has been consumed — tokens, cost in US dollars, remaining headroom, percentage and reset time, per organization, consumer, application, API client or API proxy — is read through the [Usage Reports API](/api-reference/usage-reports). It has five read-only `GET` endpoints, intended for chargeback exports and budget-alarm jobs.

Three properties of those figures are worth knowing before you build a report on them:

- **A consumer, an organization and an AI proxy are read from the hourly usage rollup** — the same table the AI reports use, so the numbers match what you see there. It is refreshed about once an hour and is kept independently of traffic-log retention, so a question about last quarter still answers correctly. Its grain is a whole UTC day, and the response says which days it actually measured.
- **An application and an API client are read from the traffic log instead**, because the rollup carries no application dimension. Their figures are therefore bounded by how long the traffic log is retained, and traffic recorded before **2026.09.2** cannot be attributed to a specific API client at all.
- **The budget block is live, not historical.** It always describes the windows that are open right now, regardless of the period you asked for, and states how fresh it is (the counters are synchronized about once a minute).

If a source cannot be read, the call still answers successfully and marks the result as partial, naming the environments it could not reach — it never reports an unread source as zero consumption.
