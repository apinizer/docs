:::info

Connectors are used in two main areas: creating workflows in **Task Flows** (API Integrator) and sending API traffic logs to different systems in **Gateway Environments**. Each connector is customized to communicate with a specific system or protocol and can be easily used with form-based configuration without the need to write code.

:::

:::tip

**Elasticsearch Connector** is particularly important. Querying and analytically visualizing API Traffic in Apinizer Management Console is only possible by adding Elasticsearch Connector to the relevant environment. Without Elasticsearch Connector, analytics screens, API Traffic tabs, and report generator menus cannot be used.

:::

:::warning

When connectors are used in Gateway Environments, the structure and privacy settings of API traffic logs are important. API Proxy Traffic Privacy Settings should be configured so that sensitive data does not appear explicitly in log records.

:::

## Log Delivery

When a Gateway Environment sends API traffic logs and other platform logs to several targets (Kafka, Elasticsearch, Webhook, RabbitMQ, ActiveMQ, database, Graylog, Syslog), each target works independently.

- **Targets do not wait for each other.** An unreachable or slow target does not delay the others, and it does not slow down the API response.
- **Failover is tried once.** If the primary target returns an error, the record is sent once to the failover target that you defined. If there is no failover target, the record is dropped and counted.
- **Own connection for logs.** Kafka, Webhook, RabbitMQ and ActiveMQ open a separate connection for log delivery. If the same connection definition is used for both logs and API calls, the Gateway worker opens one more connection. The database connection pool is shared; log delivery uses at most half of it.
- **Bounded memory.** Every log target holds a limited amount of records in memory. When the limit is full, the record goes to the failover target. If there is no failover target, the record is dropped and counted with its reason. The API response is not affected.

| Drop reason | Meaning |
|---|---|
| `CONCURRENCY_LIMIT` | The send permit, the retained bytes budget of the connection, or the log leg was not available. |
| `QUEUE_FULL` | The queue of the target is full. |
| `WRITE_FAILED` | The target returned an error and no failover target accepted the record. |
| `INGRESS_LIMIT` | The records waiting to be prepared reached the memory limit of the worker. |
| `RECORD_TOO_LARGE` | A single record is larger than the limit of the connection. |

Error lines in the Gateway log do not contain the message of the driver or the client library. They show the error class, the SQLState, the vendor code and the class of the root cause. The ActiveMQ line shows the number of brokers.

:::info Limits

- **Bytes held per connection.** The limit is the larger of 128 MiB and one sixteenth of the worker heap. Traffic logs can use 90% of it; the rest is kept for event records. The records waiting to be prepared are limited to one eighth of the heap.
- **Large bodies.** When bodies are large (for example 8 MB with a 512 MB heap), records that together exceed the limit of one connection are dropped and counted. In a test with four simultaneous 8 MB records, two were dropped. While one sixteenth of the heap does not exceed 128 MiB, the limit does not depend on the heap size. For content outside Latin-1, the real memory use can be higher than the estimate.
- **Worker shutdown.** When the worker stops with SIGTERM, the log records on their way can be lost without being counted.

:::
