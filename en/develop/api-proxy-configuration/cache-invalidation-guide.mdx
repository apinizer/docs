This guide collects cache types and invalidation paths in one place. See the source pages for full detail; only information that appears in the current documentation is summarized here.

## Cache types

- **[API Proxy — Settings (general response cache)](/en/develop/api-proxy-configuration/settings#cache-settings):** Caching successful responses from the API Proxy so client requests can be answered from cache without calling the Backend API. Only successful responses below status code `400` are cached; the general response cache does not apply to AI, MCP, and A2A type API Proxies.
- **[API Proxy — Endpoint (REST method/endpoint cache)](/en/develop/api-proxy-configuration/endpoint-configuration):** When **Cache Settings** is enabled, per-method/endpoint cache; key type, capacity, TTL, and invalidation fields are defined on the endpoint form.
- **[API Call policy cache](/en/develop/policies/api-call):** Stores the response of the external REST call made by the policy; enabled on the **CACHE** tab with **Apply By (Cache By)**, capacity, TTL, and storage type.
- **[Cache policy](/en/develop/policies/cache):** Standalone **LOOKUP**, **POPULATE**, and **INVALIDATE** in the policy chain; unlike the API Call policy’s built-in cache, you explicitly control when values are read, written, and deleted in the flow.
- **[API Proxy Group — Cache Settings](/en/concepts/core-concepts/api-proxy-group):** Group-level cache settings applied to group members. API Proxy-level settings take precedence over group-level settings.
- **[Settings — Idempotency](/en/develop/api-proxy-configuration/settings#idempotency-settings):** Records in the distributed cache using `Idempotency-Key` to return stored responses on duplicate requests — not the same mechanism as the general response cache.
- **[Deploy / Redeploy](/en/develop/deployment-and-version-management):** Not a cache entry type; reflects loaded API Proxy configuration in the environment. Changes take effect at runtime after **Redeploy**; redeploy is performed without interruption and subsequent requests are handled with the new settings.

| **Endpoint — method/endpoint cache** | Successful responses for the enabled method/endpoint (same key and invalidation field model as Settings) | **TTL (seconds)**; **Cache Key Type** (Query / Custom Key + **Variable List**); **Capacity** | Endpoint docs describe **Invalidation Requires Authn** and unauthorized handling; Cache-Control values are described the same way as on Settings | — |
| **API Proxy Group — Cache Settings** | Cache configuration defined at group level (applied to members) | No field-level detail on the concept page; member proxy endpoint/settings precedence applies | — | Group deployment is documented; clearing of group cache entries on deploy (to be verified in review) |
| **Cache policy** | **Source Variable** value (POPULATE); variable read/write in the policy chain | Key: **Key Prefix** and/or **Key Variables** (joined with `\|`); POPULATE **TTL**, **Capacity**; **Storage Type:** Local or Distributed | **INVALIDATE** operation deletes the entry for the same key | Policy deploy/usage: [Policy Management](/en/develop/api-proxy-configuration/policy-management); effect of deploy on shared cache entries (to be verified in review) |
| **API Call policy — CACHE** | Response of the REST call made by the policy | **Apply By (Cache By)** variable; **Capacity**; **TTL**; **Cache Storage Type:** DISTRIBUTED or LOCAL; optional Dynamic TTL | Documented manual clear: **INVALIDATE** via [Cache policy](/en/develop/policies/cache) (API Call FAQ). ## API Proxy — Settings response cache

**Cache Settings** on the [Settings](/en/develop/api-proxy-configuration/settings) tab manage proxy-wide response caching. Client requests can be served from cache when key match and TTL conditions are met, without reaching the Backend.

Notable rules:

- Only successful responses are cached (`4xx/5xx` with status `400` and above are not cached).
- **Cache only HTTP Get Requests** can limit caching to GET responses.
- Invalidation: **Cache-Control** on the request with `no-cache`, `no-store`, or `max-age=0`; optional authentication requirement.

On AI, MCP, and A2A proxy types the setting is ignored; for semantic caching see [Semantic Cache](/en/ai-gateway/semantic-cache).

## API Proxy Group

[API Proxy Group](/en/concepts/core-concepts/api-proxy-group) includes **Cache Settings** at group level together with CORS, Idempotency, and Maintenance Mode for shared configuration across members.

:::info

Each API Proxy in the group can also define its own settings; **API Proxy-level settings take precedence over group-level settings.**

:::

Treat the group row in the matrix as a separate management surface from proxy/endpoint cache; the concept page summarizes group cache; technical fields are assumed parallel to Settings/Endpoint.

## API Call policy

The **API Call** policy cache stores only the response of the external call that policy targets. When cache is enabled, the request goes through cache lookup first; a successful response is written to cache ([working principle](/en/develop/policies/api-call#working-principle)).

Difference from the **Cache policy**:

| | API Call — CACHE | Cache policy — INVALIDATE |
| --- | --- | --- |
| **Scope** | In-policy REST call response | Key/value you define in the policy chain |
| **Removal** | TTL; documentation recommends **Cache Policy** (INVALIDATE) for manual clear | **INVALIDATE** in the flow deletes by key |
| **Key** | **Cache By** variable | **Key Prefix** + **Key Variables** (project/environment/proxy not added automatically) |

**Settings** response cache targets the final response returned to the client; API Call cache targets the intermediate outbound call — none replaces the others.

:::warning

Invalidating the **general response cache** with **Cache-Control** on the request does not automatically clear a **Cache policy INVALIDATE** step or **API Call** policy cache. **Idempotency** records use a separate cache (`Idempotency-Key`, retention in days).

Quota, authentication token, and session data are outside the response/policy cache invalidation methods described on these pages; do not confuse them with the proxy response cache.

:::
