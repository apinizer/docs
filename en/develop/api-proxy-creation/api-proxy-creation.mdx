import {Card, CardGroup} from '@site/src/components/Card';

With Apinizer you can put an API Proxy in front of an existing API or web service used as the Backend API, or create an API Proxy without a backend and offer it as an API. An API Proxy is created with a five-step wizard:

| Step | What you do |
|------|-------------|
| [1. Proxy type](#1-proxy-type) | Pick the proxy type, or paste a specification address and let Apinizer find the type. |
| [2. Specification / Backend](#2-specification-backend) | Give the specification by URL, file or API Spec, or enter the backend address. |
| [3. General](#3-general) | Enter the name, description, version, categories, usage and sharing type. |
| [4. Client route](#4-client-route) | Set the path, method, host or header that clients use to reach the proxy. |
| [5. Review](#5-review) | Check what you entered and save. |

To open the wizard, go to **API Gateway → API Proxies** in the main menu and click **Create** at the top right.

The step bar at the top of the wizard shows where you are. Completed steps get a check mark. **Next** stays disabled until the required fields of the step are filled, and later steps cannot be opened before that. You can go back to a completed step from the step bar. From step 2 on, a panel on the right shows the selected type, the client → proxy → backend flow and a summary of the values you entered.

:::info Quick Start

To follow the same flow step by step with a sample API, see the [Quick Start](/en/develop/quick-start) page. This page describes the fields of each step in detail.

:::

## 1. Proxy type {#1-proxy-type}

<img
  src="/images/develop/api-proxy-olusturma/create-wizard-1-type.png"
  alt="Step 1 of the wizard: the specification address field and the proxy type cards"
  width="1000"
/>

At the top of the step there is a **detection field**. Paste a specification URL or a backend address and click **Parse** (or press Enter): Apinizer picks the type and takes you straight to step 2. You can also drop a specification file onto the same area, choose a file with **Upload File**, or use a stored specification with **Select API Spec**. Recognised formats: OpenAPI / Swagger, WSDL, `.proto`, `ws://` / `wss://` and an `http(s)://` backend address. Accepted files: `.json`, `.yaml`, `.wsdl`, `.xml`, `.proto` and `.zip`.

To pick the type yourself, click one of the cards below and then **Next**. Double-clicking a card also moves to the next step.

| Type | Description |
|------|-------------|
| **REST API from OpenAPI** | Creates a REST API Proxy from a Swagger 2.x or OpenAPI 3.x specification. You give the specification by URL, by uploading the file or by selecting an API Spec. Endpoints and routing addresses are read from the specification. See the [Swagger 2.0](https://swagger.io/docs/specification/2-0/what-is-swagger/) and [OpenAPI](https://swagger.io/docs/specification/about/) documentation. |
| **SOAP API from WSDL** | Creates a SOAP proxy for a target service described by a [WSDL](https://en.wikipedia.org/wiki/Web_Services_Description_Language) (SOAP 1.1 / 1.2). Operations and service addresses are read from the WSDL. Details: [SOAP API Proxy Creation](/en/develop/api-proxy-creation/soap-api-proxy-creation). |
| **REST API from WSDL** | Creates a REST proxy for a target service described by a WSDL. Clients call REST (JSON); Apinizer calls the SOAP backend. Details: [SOAP-REST API Proxy Creation](/en/develop/api-proxy-creation/soap-rest-api-proxy-creation). |
| **gRPC API** | Passes incoming gRPC requests to the backend gRPC server and returns the responses to the client. You give the proto file by URL or by uploading it. To pass gRPC traffic without a proto file, choose the **Reverse Proxy** source. Details: [gRPC API Proxy Creation](/en/develop/api-proxy-creation/grpc-api-proxy-creation). |
| **No-Spec API** | For an API without a specification file, for example one built code-first. You enter the routing addresses in the wizard and define the endpoints by hand after the proxy is created. Apinizer generates the Swagger/OpenAPI specification from these definitions. |
| **Reverse Proxy** | Creates an HTTP / HTTPS reverse proxy. It passes incoming requests to the backend whether or not a matching endpoint exists, and returns the response to the client. No specification file or endpoint definition is needed; the backend's root context is enough. |
| **WebSocket** | Creates a `ws://` / `wss://` proxy so that clients reach the backend WebSocket service through Apinizer. Details: [WebSocket API Proxy Creation](/en/develop/api-proxy-creation/websocket-api-proxy-creation). |
| **Connector** | Connects the REST API that clients call to a connector, so the HTTP request is turned into another target such as Kafka, RabbitMQ, ActiveMQ, e-mail, Elasticsearch, FTP, Graylog, Syslog, Logback or SNMP. Details: [Connector API Proxy Creation](/en/develop/api-proxy-creation/connector-api-proxy-creation). |

:::note

If your licence includes KPS, the **KPS (SOAP Proxy)** and **KPS (REST Proxy)** cards are also shown.

:::

## 2. Specification / Backend {#2-specification-backend}

<img
  src="/images/develop/api-proxy-olusturma/create-wizard-2-specification.png"
  alt="Step 2 of the wizard: specification source, URL field and routing addresses"
  width="1000"
/>

The name of this step depends on the type you picked: **Specification** for types that use a specification document, **Backend** for the others. If you pasted an address in step 1, the top of the step says what Apinizer detected, for example "Detected: OpenAPI specification".

### Specification types: choosing the source

For the OpenAPI, WSDL and gRPC types, first choose where the specification comes from:

| Source | Description |
|--------|-------------|
| **URL** | Enter the address of the specification document and click **Parse**. Examples: `https://petstore.swagger.io/v2/swagger.json`, `http://www.dneonline.com/calculator.asmx?WSDL` |
| **Upload File** | If the specification document is on your computer, upload it and click **Parse**. |
| **API Spec** | Select a specification created earlier with the [API Specification Document Editor](/en/develop/api-design/spec-designer) through **Select API Spec**. Only for the OpenAPI type. |
| **Reverse Proxy** | Only for the gRPC type. Passes gRPC traffic without a proto file. |

Reading a specification from a URL or from a file requires the **Manage** permission in the **API Management** or **AI Development** category of the project. Saving the API Proxy requires the **Manage** permission in the **API Management** category. A request without the permission is refused with HTTP 403.

When a WSDL is detected, **Create as** lets you choose **SOAP API** or **REST API**. For WSDL types the **Enable WS-A if exists in WSDL** and **Enable WS-RM if exists in WSDL** boxes are shown before parsing. These settings are read while parsing, so tick them before **Parse** if you need them.

If Apinizer cannot tell whether a pasted `http(s)://` address is a backend service or an OpenAPI specification, the **This address is** choice appears. Pick **A backend service** or **An OpenAPI specification**.

### Spec Authorization

Some specification files are open only to authenticated clients. If your specification URL is one of them, tick **Use Spec Authorization** on the URL source before **Parse**. The **Basic Authentication (Optional)** fields and the **Custom Headers & Query Parameters** table are shown. The option is not available for the Reverse Proxy and WebSocket types.

- **Basic Authentication**: If you enter a **Username** and **Password**, Apinizer builds the `Authorization: Basic ...` header itself. This is a convenient shortcut for specification URLs protected with Basic Auth.
- **Custom Headers & Query Parameters**: Enter a **Key Name**, **Value** and **Type** on each row. With **Type** `header` the value is sent as a request header; with `query` it is added to the URL as a query parameter. Other values are ignored.
- Basic Auth and the headers in the table can be used together; both are sent.
- Spec Authorization is available for the URL-based types (OpenAPI, WSDL, gRPC). For WSDL imports (such as XSD imports), sub-schema files are downloaded with the same authorization. For OpenAPI, only the table rows are sent to files referenced with `$ref`; Basic Auth is not.

### SSL / Certificate Settings

The secure connection and certificate options used when the specification is fetched from a URL are in the **SSL / Certificate Settings** panel. The panel is shown on the URL source before parsing and can be expanded or collapsed.

| Field | Description |
|-------|-------------|
| **Connection Timeout** | The longest time, in seconds, to wait for the response of the specification URL. Default 30 s, range **5–120 s**. |
| **Customize SSL/TLS Settings** | When off, the system defaults (JVM **cacerts**) are used. When on, the **Skip SSL Verification** option and the **Server Certificate Verification** section, for verifying the server certificate with a TrustStore or a PEM certificate, are shown. |
| **Skip SSL Verification** | Shown when **Customize SSL/TLS Settings** is on. When on, the server certificate is not verified and the **Server Certificate Verification** section is hidden. Useful for self-signed or private CA environments. |
| **Server Certificate Verification** | Shown when **Customize SSL/TLS Settings** is on and **Skip SSL Verification** is off. Options: **System Default (JVM)** (default), **Truststore (Key Store record)** and **Certificate (PEM)**. |

When **Truststore (Key Store record)** or **Certificate (PEM)** is selected, the **Select Existing**, **Upload TrustStore** (.jks, .p12, .pfx) with password, and **Upload PEM Certificate** (.pem, .crt, .cer) options open.

:::tip

To use an uploaded TrustStore or PEM file on other screens too, tick **Add to Keystore Pool** (for a TrustStore) or **Add to Certificate Pool** (for a PEM) and enter a name in **Pool Name**. These options are shown to users with the **Manage** permission in the Secrets category of the project.

:::

:::info

On reparse, the stored TrustStore or certificate selected at creation and the **Skip SSL Verification** choice are filled in. One-off uploaded files, the connection timeout and Spec Authorization are not kept and must be entered again.

:::

:::warning

If the selected SSL/TLS settings cannot be used (damaged file, wrong password, missing store), spec download is refused with **Customize SSL/TLS Settings** on. A stored TrustStore or certificate must belong to the current project or Administration, or have no project; a store of another project is refused like a missing store. With **Skip SSL Verification** on, an unusable store is skipped and the file is downloaded without certificate checks. If you copy or move an API Proxy to another project, reparse refuses the store of the old project (error key `specDownload.sslContextFailed`); select the SSL/TLS settings again. API clients that call `POST /api/api-proxies/create-from-url` with a stored store must send `projectId`; a System Admin who sends no `projectId` uses the Administration scope.

:::

### Routing addresses

When the specification is parsed, the **Routing Addresses** list is filled from it. These are the access addresses of the backend API. Choose the addresses to save with the **Status** box; unticked addresses are not saved. You can edit addresses in the row, add one with **+** and remove one with the trash icon. Several addresses can be used for load balancing.

For types without a specification, you enter the backend in this step:

- **No-Spec API**: Add the routing addresses by hand.
- **Reverse Proxy** and **WebSocket**: Enter the backend address.
- **Connector**: Choose and configure the connector type in the dialog opened with the **+** button.

**Next** opens once the specification is parsed (or an API Spec is selected) and at least one routing address is selected. For Reverse Proxy the backend address is enough; for Connector, the connector.

## 3. General {#3-general}

<img
  src="/images/develop/api-proxy-olusturma/create-wizard-3-general.png"
  alt="Step 3 of the wizard: name, description, version, categories, usage and sharing type"
  width="1000"
/>

| Field | Description |
|-------|-------------|
| **Name** | The name of the API Proxy, shown across the interface. Required and must be unique. The name is checked while you type, and the top right of the field shows whether it is available. If another API Proxy already uses the name, **Next** stays disabled. |
| **Description** | The description of the API Proxy. |
| **Backend API Version** | The version of the Backend API behind the API Proxy. |
| **Category List** | Categories make API Proxies easier to manage. The list sets which categories the API Proxy belongs to. |
| **Usage** | Says who owns the Backend API. Required. **Publisher**: the Backend API belongs to your own company or institution. **Consumer**: the Backend API belongs to another company or institution, and the proxy is created to reach it. **Publisher & Consumer**: a proxy created for another company's Backend API is also offered to third parties. **Unspecified**: the default. |
| **Sharing Type** | Says how the Backend API is shared. Required. Values: **External** (default), **Internal**, **External and Internal**, **Unspecified**. |

:::tip

If a specification was parsed, **Name**, **Description** and **Backend API Version** are filled in from the title, description and version of the specification. For the petstore specification, for example, the name is "Swagger Petstore" and the version "1.0.7". You can change these values.

:::

## 4. Client route {#4-client-route}

<img
  src="/images/develop/api-proxy-olusturma/create-wizard-4-client-route.png"
  alt="Step 4 of the wizard: client route with relative path, methods, hosts and headers"
  width="1000"
/>

The client route sets how clients reach this API Proxy. **Next** stays disabled until at least one relative path, method, host or header is defined.

You enter the relative paths in the **Endpoint** section. The **Endpoint per environment** list right below shows the full address clients will call: the access URL of each environment followed by your path.

| Field | Description |
|-------|-------------|
| **Relative Paths** | Part of the address of the API Proxy, used to route an incoming request to the right API Proxy. Add more paths with **Add a path**. |
| **Methods** | The HTTP methods the API Proxy accepts: GET, POST, PUT, DELETE, PATCH, HEAD, OPTIONS, QUERY. If none is selected, any method is accepted. |
| **Hosts** | The host name of the request. Add one with **Add a host**. If empty, any host is accepted. |
| **Headers** | A header name and value the request must carry. Add one with **Add a header**. If empty, there is no header condition. |

Methods, hosts and headers are in the optional **Request matching** section. The section can be expanded or collapsed, and its title line shows a summary of the current choice, for example "Any method · Any host · No header condition".

Example full access address:

| Part | Value |
|------|-------|
| Apinizer address | `https://demo.apinizer.com` |
| Environment address | `/apigateway` |
| Relative path | `/petstoreProxy` |
| Endpoint | `/findByStatus` |
| **Full access address** | `https://demo.apinizer.com/apigateway/petstoreProxy/findByStatus` |

If **Relative Path Status** is on in the project settings, the project's relative path is shown before the relative path field and is added to the path automatically on save.

Proxies that use the same relative path conflict unless they differ by host, header or method.

:::note gRPC and WebSocket

- **gRPC**: The relative path must have the form `/packagename.servicename` from the proto file. Apinizer fills it in from the proto file. For the proto below, the value is `/hello.HelloService`.

  ```proto
  syntax = "proto3";
  package hello;
  service HelloService {
  }
  ```

- **WebSocket**: For how to enter the relative path, see [WebSocket API Proxy Creation](/en/develop/api-proxy-creation/websocket-api-proxy-creation).

:::

For details, see the [API Proxy Client Route Usage Guide](/en/develop/api-proxy-creation/client-route-settings).

## 5. Review {#5-review}

<img
  src="/images/develop/api-proxy-olusturma/create-wizard-5-review.png"
  alt="Step 5 of the wizard: summary of the entered values and the Save button"
  width="1000"
/>

The last step lists everything you entered in four sections: **Proxy type**, **Specification** / **Backend**, **General** and **Client Route**. To change a section, click **Edit** next to it; the wizard goes back to that step. If everything is correct, click **Save**. The API Proxy is created and its edit page opens.
