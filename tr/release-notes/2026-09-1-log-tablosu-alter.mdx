Bu sayfa listelenmemiştir (unlisted) — sidebar'da ve arama sonuçlarında görünmez, yalnızca 2026.09.1 sürüm notlarındaki doğrudan bağlantı üzerinden erişilmek üzere tasarlanmıştır.

## Kimler ihtiyaç duyar

Bu script yalnızca API proxy trafik loglarını **SQL/JDBC trafik-log connector** üzerinden ilişkisel bir veritabanına (Oracle, MySQL, PostgreSQL veya SQL Server) yazan Apinizer kurulumlarını ilgilendirir.

**Elasticsearch veya MongoDB trafik-log connector'ı kullanıyorsanız bu sayfayı tamamen atlayın** — o hedefler yeni veriyi elle bir adım gerektirmeden taşır. Elasticsearch tarafında indeks şablonu yükseltme sırasında güncellenir ve indeks otomatik olarak rollover edilir.

## Ne değişti

Apinizer 2026.09.1, trafik loguna **politika çalışma sürelerini** ekler: bir istekte çalışan her politikanın sırası, tipi ve milisaniye cinsinden süresi. Özellik varsayılan olarak kapalıdır ve API Proxy > Log Ayarları altında log hedefi başına açılır.

İlişkisel bir hedefte liste, `policy_exec_times` adlı tek bir yeni kolona, `sıra:tip:süre` üçlülerinden oluşan karakter sınırlı bir CSV olarak yazılır:

```
1:jwt-auth:12|2:rate-limit:3|10001:content-filter:41|10002:ai-semantic-cache:8[S]
```

Kolon nullable ve seyrektir (sparse) — ayarı açana kadar her istekte, ve kapalı bıraktığınız her hedefte `NULL` kalır. Gateway yazım yolu fail-soft'tur: kolon yoksa yalnızca o alan atlanır, log yazımı başarısız olmaz; dolayısıyla script'i geç çalıştırmak veri kaybettirir ama trafiği etkilemez.

Değer yazılmadan önce 2000 karakterde sınırlanır ve kesme her zaman görünürdür (`|+N`, `N` = sığmayan kayıt adedi), sessiz değildir. Kolonun 4000 karakter genişliğinde tanımlanmasının nedeni, Oracle'da `VARCHAR2` uzunluklarının **byte** cinsinden sayılmasıdır; 2000 karakterlik bir cap en kötü durumda 4000 byte'lık alan ister.

## Ne zaman çalıştırılmalı

Bu script'i yapılandırılmış her SQL/JDBC trafik-log veritabanına karşı **bir kez** çalıştırın; 2026.09.1 yükseltmesinden önce ya da yükseltme sırasında olabilir, bakım penceresi gerektirmez. Kolon nullable olduğu için yükseltme öncesi log satırlarını yazmaya devam eden eski gateway worker'ları etkilenmez. DDL için bir değişiklik yönetimi süreciniz varsa önce production dışı bir ortamda deneyin.

## Oracle

```sql
ALTER TABLE log_ApiProxyTraffic ADD (
    policy_exec_times VARCHAR2(4000)
);
```

## PostgreSQL

```sql
ALTER TABLE log_ApiProxyTraffic
    ADD COLUMN policy_exec_times VARCHAR(4000);
```

## MySQL

```sql
ALTER TABLE log_ApiProxyTraffic
    ADD COLUMN policy_exec_times VARCHAR(4000);
```

## SQL Server

```sql
ALTER TABLE log_ApiProxyTraffic ADD
    policy_exec_times NVARCHAR(4000);
```

## Doğrulama

Script'i çalıştırdıktan sonra bir API Proxy için ilişkisel log hedefinde **Politika çalışma sürelerini** açın, o proxy'yi yeniden dağıtın ve üzerinden bir istek geçirin. Kolon o istek için bir CSV değeri taşımalıdır:

```sql
SELECT correlation_id, policy_exec_times
FROM log_ApiProxyTraffic
WHERE policy_exec_times IS NOT NULL
ORDER BY log_timestamp DESC;
```

Yeni kurulumlarda bir işlem gerekmez — [Apinizer Log Tabloları Oluşturma Komutları](/tr/operations/yonetici-kilavuzlari/apinizer-log-tablolari-olusturma-komutlari) sayfasındaki `CREATE TABLE` ifadesi kolonu zaten içerir.
