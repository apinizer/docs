**Ne İşe Yarar?**

* Gateway’deki API’leri portal vitrininde ürün olarak sunar
* Birden fazla proxy/proxy group’u tek üründe paketler
* Free / Flat rate / Metered / Tiered planlarla kota, rate limit ve onay politikası tanımlar
* Görünürlükle keşfedilebilirliği; plan onayıyla erişimi ayırır
* Abonelikleri org’a ait uygulamalar üzerinden izler

**Kimler Kullanır?**

* **Portal / Ürün Yöneticileri:** Ürün oluşturmak, paketlemek, plan tanımlamak ve yayınlamak için
* **Geliştiriciler:** Portalda ürünü keşfedip uygulama+plan ile abone olmak için
* **Destek / Operasyon:** Abonelik ve kullanım özetini doğrulamak için
      
      :::info
Paketleme envanteri (hangi proxy hangi üründe?) → [API Katalog](/tr/api-portal/api-katalog).  
Uygulama yaşam döngüsü / Unregister → [Uygulama Yönetimi](/tr/api-portal/uygulama-yonetimi).  
Test→Prod → [Uygulama Promote](/tr/api-portal/uygulama-promote).  
Canlı kota/trafik → [Trafik ve Kullanım](/tr/api-portal/trafik-ve-kullanim).
:::

## Ekrana Erişim

* Manager: **Portal → API Products**
* Developer Portal vitrin: üst menü **API’ler** (APIs)
* Yetki: Portal ürün yönetimi rollerine bağlıdır

## Model

```
API Catalog (proxy / proxy group)
        │  Select APIs from the Catalog
        ▼
API Product  (proxyRefs + OpenAPI + Plans)
        │  subscribe
        ▼
Portal App (organizasyon) + Plan  →  ApiProductAppRegister
        │
        ▼
App credential + ACL (paketlenmiş proxy’ler)
```

* **Abonelik** = (uygulama, bu ürün, seçilen plan)
* Kota **abonelik başına** uygulanır
* Aynı proxy birden fazla üründe yer alabilir

:::note
Portal ürün raporları bir isteği, gateway'in kaydettiği aboneliğin ürünü için sayar. İstekte kayıtlı abonelik ürünü yoksa istek, aynı ortamda o proxy'yi doğrudan ya da proxy grubu üzerinden kullanan başka ürün bulunmadığında bir ürün için sayılır. Aksi halde hiçbir ürün için sayılmaz.
:::

* Canlı WAITING/APPROVED abonelik varken paketten API **çıkarılamaz**; yalnızca **eklenebilir**

## Oluşturma (sihirbaz)

Yayınlanmamış ürün oluşturur. Tipik adımlar: General → APIs → API Spec → Plans → Environment → Summary.

| Konu | Kod gerçeği |
|------|-------------|
| API seçimi | Catalog’dan 1..n `proxyRefs` (proxy ve/veya group birlikte olabilir) |
| Spec | Yüklenen OpenAPI (JSON/YAML) veya ürünün API'lerinden üretilen dokümantasyon. Bkz. [Dokümantasyon kaynağı](#dokümantasyon-kaynağı) |
| Yayın | Create sonrası **Unpublished**; ayrıca publish gerekir |

### Dokümantasyon kaynağı {#dokümantasyon-kaynağı}

**API Configuration** ekranında, portaldaki API Specification içeriğinin kaynağını seçin.

| Seçenek | Davranış |
|---------|----------|
| **Yüklenen OpenAPI dokümanı** | Portal, yüklediğiniz OpenAPI dokümanını gösterir. Varsayılan budur ve mevcut tüm ürünler bunu korur. |
| **API'lerden üretilir** | Portal dokümantasyonu, ürünün API proxy'lerinden ve proxy gruplarından her okumada oluşturur. Her API için ayrı bir bölüm vardır. Proxy'ye eklenen yeni endpoint otomatik görünür. |

Üretilen dokümantasyon şunları dışarıda bırakır:

* API tanım dosyası erişimi **Erişime Kapalı** olan API.
* Ürün herkese açıksa, API tanım dosyası erişimi **Kimlik Doğrulama Gerekli** olan API.
* Pasif metotlar.

**API Configuration** ekranı, atlanan API'leri nedenleriyle listeler. Tüm API'ler atlanırsa portal henüz dokümantasyon göstermez. Bu bir hata değildir.

:::info
Portal Try It konsolunu yalnızca ürünün kendi gateway adreslerine karşı kullanın. Konsol, her API'nin erişim URL'sini veya yüklenen dokümanın servers URL'sini çağırır. Şema, host ve port eşleşmelidir. Yol, bu adresin altında olmalıdır. Portal diğer URL'leri reddeder ve yönlendirmeleri izlemez.
:::

Try It konsolu kimlik doğrulama ayarlarını ürünün ilk API'sinden alır. Üretilen dokümantasyonda, dokümantasyonun gösterdiği ilk API'yi kullanır. Portal, proxy client secret değerini tarayıcıya göndermez. Try It aktarımı bu değeri sunucu tarafında ekler. Secret gerektiren oturumsuz (anonim) bir çağrıyı 401 ile reddeder.

### Dökümantasyon yönetimi {#dökümantasyon-yönetimi}

| Sekme | Ne içerir |
|-------|-----------|
| **API Specification** | Ürün OpenAPI / endpoint görünümü |
| **Documentation** | Portal doküman sayfaları |
| **Files** | İndirilebilir dosyalar |
| **Plans** | Active/Retired planlar; Duplicate; fiyat/onay; **kota ve hız limiti doğrudan plan üzerinde sayı olarak girilir** ve sistem bu sayılardan gateway'in uyguladığı limit profilini kendisi üretir — bkz. [Abonelik Planı Limit Profilleri](#abonelik-plani-limit-profilleri) |
| **Subscriptions (N)** | Salt okunur: org → app → plan + durum + kullanım özeti |
| **Security** | Paketlenen proxy’lerde tutarlı ACL-managed auth; hazır değilse publish engeli |
| **Visibility** | Keşfedilebilirlik (erişim/onay planlarda) |
| **Danger Zone** | Unpublish / Delete |

Manuel plan onayları ürün Subscriptions özetinde yapılmaz; **API Product App Registers** / [Onay İstekleri](/tr/api-portal/onay-istekleri) tarafındadır.

:::info
Bu Subscriptions panelindeki kullanım özeti, trafiği yalnızca eski kullanıcı adı/parola credential'ı taşıyan uygulamalara değil, kimliği tipli bir API İstemcisi (client id, trafik satırının username/key alanıyla eşleşir) olan uygulamalara da atfeder.
:::

### Plan tipleri

| UI (EN) | Anlam |
|---------|--------|
| **Free** | Ücretsiz |
| **Flat rate** | Sabit ücret (eski “Subscription” adı değil) |
| **Metered** | Kullanım bazlı |
| **Tiered** | Kademeli |

Her abonelikte tüketici **tek plan** seçer. Onay: plan seviyesinde **Auto approval** / **Approval Required**. Ürün seviyesinde auto-approve alanı deprecated’tir; dokümanda öğretilmez.

Plan editöründe aşım davranışı için **Engelle (429)** ve **Devam et ve ücretlendir** seçenekleri sunulur. **Metered (Kullanım başına)** ve **Tiered (Kademeli)** fiyatlama tiplerinde her çağrı zaten faturalandığı için **Engelle** seçeneği ekranda pasiftir ve seçilemez — bu fiyatlama tiplerinde aşımda istek reddedilmez, yalnızca sayılır. Planın fiyatlama tipini Metered veya Tiered'a değiştirdiğinizde, önceden **Engelle** seçili olsa bile aşım seçimi otomatik olarak **Devam et ve ücretlendir**'e döner.

### Plan limitlerinin uygulanabilmesi için gereken kimlik doğrulama {#plan-limiti-kimlik-dogrulama}

Plan limitleri **isteği yapan tüketiciye** göre sayılır. Bu nedenle ürüne bağlı her proxy'nin, isteğin kimin adına geldiğini belirleyebilmesi gerekir. Proxy tüketiciyi tanıyamazsa istek anonim kabul edilir, planın kotası ve rate limiti **hiç uygulanmaz** ve aşımda 429 dönmez.

Bir proxy şu durumda tüketiciyi tanır:

| Proxy'deki durum | Plan limiti uygulanır mı |
|------------------|--------------------------|
| **Aktif** Basic / Base64 / Digest / mTLS kimlik doğrulama politikası | Evet |
| **Aktif** JWT veya OAuth2 politikası, token'ı üçüncü taraf üretiyor | Evet |
| **Aktif** JWT veya OAuth2 politikası, token'ı Apinizer üretiyor, grant type **password** ve sağlayıcı **Secret Manager (ACL)** | Evet |
| **Aktif** JWT veya OAuth2 politikası, token'ı Apinizer üretiyor, grant type **password** ama sağlayıcı LDAP / Veritabanı / API | Hayır — yalnızca imza doğrulanır, tüketici çözülmez |
| **Aktif** JWT veya OAuth2 politikası, token'ı Apinizer üretiyor ve grant type **client_credentials** | Hayır — yalnızca imza doğrulanır, tüketici çözülmez |
| **Aktif** JWT veya OAuth2 politikası, kimlik kaynağı bir **OIDC kimlik sağlayıcısı** ve token isteğin anında bu sağlayıcıya doğrulatılıyor (onay türü **password** dışında) | Sağlayıcıda [**Eşleşen Consumer Zorunlu Olsun**](/tr/develop/politikalar/jwt) açıksa Evet, kapalıysa Hayır — token doğrulanır ama isteğe bir Consumer bağlanmaz |
| Kimlik doğrulama politikası var ama **pasif** | Hayır |
| Hiç kimlik doğrulama politikası yok | Hayır |
| Yalnızca OIDC oturum doğrulaması | Hayır |
| Yalnızca **JOSE Uygulama** politikası | Hayır — JOSE Uygulama imzalar/şifreler, kimlik doğrulamaz; kimlik doğrulama politikası yokmuş gibi değerlendirilir |

Kimlik doğrulama politikası doğrudan proxy'de değil, **aktif** bir Politika Grubu'nun içinde de olabilir; bu durumda politika grubun içinden de sayılır. Politika grubunun kendisi **pasifse** içindeki hiçbir politika çalışmaz — grup içindeki kimlik doğrulama politikası aktif olsa bile tüketici tanınmaz. Bu kural hem yukarıdaki tabloya hem Security sekmesindeki tüketici kimliği kolonuna aynı şekilde uygulanır (Apinizer 2026.09.4).

Politikayı etkinleştirmek tek başına yeterli değildir: değişiklik **proxy yeniden yüklenene (redeploy)** kadar ağ geçidine ulaşmaz.

Bu durum artık üç yerde uyarı olarak gösterilir:

* **Manager > API Product > Planlar** ve **Abonelikler** sekmelerinin üstünde sarı uyarı. Metin, tüketiciyi **tanımayan** proxy'lerin nedenine göre değişir: tanımayan proxy'lerin **tümünde** tek sebep pasif bir kimlik doğrulama politikasıysa politikayı etkinleştirip yeniden yüklemeniz istenir; tanımayan proxy'lerin **tümünde** sebep token'ın yalnızca imzayla doğrulanması ya da kimlik doğrulama şemasının tüketiciyi hiç tanımlamamasıysa onay türünü ya da kimlik sağlayıcıyı değiştirmeniz istenir; sebepler karışıksa ya da tanımayan proxy'lerden birinde hiç kimlik doğrulama politikası yoksa nedeni Security sekmesinden görmenizi isteyen genel bir uyarı gösterilir. Bağlı proxy'lerin **hepsi** tüketiciyi tanıyor ama en az biri henüz yeniden yüklenmediyse, bunun yerine yalnızca yeniden yükleme gerektiğini belirten ayrı bir uyarı görünür (Apinizer 2026.09.4).
* **Manager > API Product > Security** sekmesindeki proxy tablosunda **Tüketici kimliği** kolonu: her proxy için "Tanınıyor" / "Tanınmıyor" ve tanınmama nedeni.
* **Developer Portal ürün sayfası > API Specification**: kimlik doğrulama tipi pasif bir politikadan geliyorsa tipin yanında **(pasif)** etiketi ve altında tüketiciye yönelik uyarı.

Uyarı proxy'nin tüketiciyi tanımadığını söylüyorsa, bu trafiğin portalın **Pano** ve **Trafik** sayfalarında da görünmeyeceğini belirtir.

JWT politikası **ACL'den Yönet** modundaysa portal ürün sayfası token adresini `/auth/jwt` yerine `/credential/jwt` ile gösterir ve proxy anahtarlarını göstermez. Portal test ekranı ve portal MCP token aracı aynı adresi ve tüketicinin credential'ını kullanır.

JWT veya OAuth2 token politikası **Politikadan Yönet** modundaysa token adresi JWT için `/auth/jwt`, OAuth2 için `/auth/token` olur. Test ekranı seçilen uygulamanın credential'ına ihtiyaç duyar. Bu yüzden bu politikaları şöyle işler:

* **OAuth2 politikası:** Token yalnızca API'nin kendi istemcisine verilir, uygulama credential'ına verilmez. Test ekranı **Authorize** düğmesini devre dışı bırakır ve bir ipucu gösterir.
* **Anahtarları portalda yayımlanmayan JWT politikası:** Portal, üst düzey bir politikanın anahtarlarını yayımlar. Politika grubunun içindeki bir politikanın anahtarlarını yayımlamaz. Test ekranı **Authorize** düğmesini devre dışı bırakır ve bir ipucu gösterir. Bu kural yalnızca API'nin kimlik doğrulama tipi JWT ise geçerlidir.
* **Anahtarları portalda yayımlanan JWT politikası:** **client_credentials** grant tipinde test ekranı token'ı API'nin kendi anahtarlarıyla alır. Token API'ye aittir. Bu yüzden çağrılar uygulamanızın Pano sayfasında görünmez.

İlk iki durumda portal sunucusu token isteğine `400` ile yanıt verir ve ağ geçidine hiçbir şey göndermez. API spesifikasyonundaki boş client ID, eksik anahtar sayılır.

MCP araçları `get_token` ve `get_api_auth_info` aynı kuralları uygular. Bkz. [MCP Genel Bakış](/tr/api-portal/mcp-kullanimi/mcp-genel-bakis#token-ve-kimlik-doğrulama).

### Abonelik Planı Limit Profilleri {#abonelik-plani-limit-profilleri}

Plan ekranında girdiğiniz **hız limiti** ve **kota** değerleri, gateway'in fiilen uyguladığı limitlerdir. Kaydettiğinizde sistem bu sayılardan plana ait bir **İstek Hızı limit profili** üretir, yürürlüğe koyar ve planın onaylı tüm aboneliklerini bu profile bağlar. Sayıları değiştirdiğinizde profil yeni değerlerle güncellenir; sayıları tamamen kaldırdığınızda profil bu abonelik planından ayrılır: ona zaten bağlı aboneliklere uygulanmaya devam eder, yeni aboneliklere limit uygulanmaz ve profil katalogda düzenlenebilen sıradan bir plana dönüşür.

Bu profil kataloğa da yazılır ama **düzenlemeye kapalıdır** ve varsayılan olarak listede görünmez — tek düzenleme noktası plan ekranıdır. Ayrıntı: [Limit Planları](/tr/ai-gateway/limit-planlari).

Hız limiti ve kota **en az 1 çağrıya** izin vermelidir. `0` (ya da negatif bir sayı) girilerek kaydedilen bir plan, kaydedilmeden önce reddedilir ve hangi kutunun düzeltilmesi gerektiğini söyleyen bir uyarı gösterilir — sıfır limit hiçbir trafiğe izin vermez ve gateway'in uygulayabileceği bir profile dönüştürülemez. Bir planı hız limitsiz ya da kotasız bırakmak için sıfır yazmak yerine ilgili kutucuğun işaretini kaldırın.

İşaretli bir kutucuğun yanındaki sayıyı **boş bırakmak** da "limit yok" anlamına gelmez: Hız Limiti ya da Kota kutucuğu işaretliyken sayı zorunludur, kutunun altında bir uyarı çıkar ve sayı girilene kadar Kaydet düğmesi pasif kalır. O limiti kapatmak için kutucuğun işaretini kaldırın.

Dışa/içe aktarma ile — ya da bir portal kopyalamasıyla — gelen bir plan, limit profilini içe aktarmanın bir parçası olarak alır ve sayılarını hemen uygular; ayrıntı: [Dışa/İçe Aktarma](/tr/admin/secrets-management/export-import#api-urunu-abonelik-planlari).

Eski bir sürümde oluşturulmuş bir planda, hiçbir profilin karşılamadığı bir hız limiti ya da kota görünüyorsa plan ekranı **bu limitlerin gateway'de uygulanmadığını** bildiren bir uyarı gösterir. Değerleri kontrol edip planı kaydedin; profil kaydetme sırasında oluşturulur ve uyarı kaybolur.

Plan ekranında katalogdan profil seçilmez. Gateway her zaman planın kendi sayılarından üretilen profili uygular. Önceki bir sürümden kalan katalog İstek Hızı profilini kullanan plan, bir sonraki kayıtta kendi profilini alır.

Bir plan, ekranın önceki bir sürümünde seçilen bir AI token bütçesi limit planını hâlâ kullanabilir. Plan ekranı bu bütçeyi **AI token bütçesi** bölümünde gösterir. **Kaldır**, bütçeyi kaydettiğinizde plandan kaldırır. Bütçe kaldığı sürece ekran yalnız bütçeyle uyumlu aşım seçeneğini sunar.

#### Değişiklik Etki Önizlemesi

Kayıtlı bir planda bazı değişiklikler kaydetmeden önce bir onay penceresi açar: aşım davranışının değişmesi, AI token bütçesinin kaldırılması ya da katalog İstek Hızı profilinin yerini kendi profilinin alması. Pencere, değişiklikten etkilenecek abonelik ve uygulama sayısını gösterir. Pencere yalnız planın onaylı aboneliği varsa açılır. Onaylamadan devam edilirse değişiklik kaydedilmez.

### Tipli Limit Bağlama {#tipli-limit-baglama}

Bir abonelik onaylandığında, seçilen plandaki Limit Profili referansları o abonelik sahibi uygulama için **uygulama seviyesinde** bir bağlama (binding) doğurur; bu bağlama uygulamanın tüm trafiğine uygulanır.

- **Plan değişikliği** aynı bağlamayı yeni plana taşır, sayaç sıfırlanmaz.
- **Abonelik sona erdiğinde** bağlama, aynı uygulamanın başka bir aktif aboneliğine devredilir (varsa); yoksa bağlama da sona erer.
- Aynı uygulama ve aynı plan ailesi için her zaman **tek** bir bağlama bulunur. İki farklı abonelik aynı aile için farklı bir profil istiyorsa, mevcut bağlama **korunur**; onay ekranında bu durum bir uyarıyla bildirilir ve profili değiştirmek isteyen operatör **Profili Değiştir** eylemiyle bilinçli bir geçiş yapar (bkz. [Onay İstekleri](/tr/api-portal/onay-istekleri)).
- Birden çok projede kullanılan portal uygulamalarının bağlaması **admin** projesi altında tutulur.

### Sürüm Yükseltmesi {#surum-yukseltmesi}

Sürüm yükseltmesi **elle bir işlem gerektirmez**. Yükseltmede, kota/hız limiti değeri girilmiş her ürün planı için otomatik bir **İstek Hızı** limit profili oluşturulur (önceki sürümde oluşturulmuş otomatik profiller varsa yenisi açılmaz, mevcut olan devralınır), plan bu profile bağlanır ve **onaylanmış** aboneliklerin uygulama seviyesindeki bağlamaları da aynı adımda kurulur. Limit taşımayan planlar **Kapalı** kalır.

Aynı adımlar her gece yeniden çalışır; bir plan herhangi bir nedenle profilsiz kalırsa (içe aktarma, ortam terfisi, elle veri düzeltmesi) en geç ertesi gün kendiliğinden düzelir. Bağlama var olduğunda ne yaptığı için Limit Planları sayfasındaki [Limitlerin Uygulanması](/tr/ai-gateway/limit-planlari#gölge-modu) bölümüne bakın.

### Görünürlük {#visibility-görünürlük}

| Tip | Anlam |
|-----|--------|
| **Public** | Herkese keşfedilebilir |
| **Only logged in Organizations** | Oturum açmış kurumlara |
| **Authorized Organizations** | Yetkili kurum listesine |

Görünürlük = keşif. Abone olma onayı plan ayarındadır.

* **Delete:** Aktif abonelik varken engellenir
