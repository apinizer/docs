---
title: "API Call ile Backend Uygulamasından JWT Token Alıp Cache Uygulanması"
description: "Backend uygulamasının token uç noktasından API Call politikası ile JWT alınması, dönen token'ın Authorization header'ına eklenmesi ve Dynamic TTL ile cache'lenmesi. Adım adım API Proxy yapılandırması ve test."
---

Bu senaryoda **Swagger PetStore** isimli **REST** mimaride oluşturulmuş bir **API Proxy** üzerinden, backend uygulamasının beklediği **JWT token**'ın **API Call** politikası ile token uç noktasından alınması ve **cache** mekanizması ile yeniden kullanılacak şekilde yapılandırılması anlatılacaktır.

**Örnek Senaryo:**

- Backend API, her istekte `Authorization: Bearer <jwt>` header'ı beklemektedir.
- Token, backend uygulamasına ait bir **token (authentication) uç noktasından** alınır.
- Her istemci isteğinde token servisine gidilmesi hem gecikme hem de token servisi üzerindeki yük açısından istenmez.
- Bu nedenle token, **API Call** politikası ile alınır; alınan yanıt **cache**'lenir ve token süresi dolana kadar aynı token yeniden kullanılır.

**Çözüm:**

Apinizer'da request hattına eklenen **API Call** politikası ile token uç noktasına senkron çağrı yapılır. Yanıttaki `access_token` değeri, backend'e gidecek isteğin **Authorization** header'ına eklenir. Cache sekmesinde **Dynamic TTL** açılarak TTL, JWT içindeki `exp` claim'inden (veya yanıttaki `expires_in` alanından) hesaplanır; böylece süresi dolmuş token cache'te tutulmaz.

Bahsi geçen senaryonun uygulanma adımları **şu şekildedir;**

- **API Client**, **Apinizer'a** istekte bulunur.
- **Apinizer**, cache'te geçerli bir token var mı diye bakar.
  - **Cache miss:** **API Call** ile backend token uç noktasına istek atılır, dönen JWT cache'e yazılır.
  - **Cache hit:** Token servisine gidilmez; cache'teki JWT kullanılır.
- Alınan JWT, backend'e gidecek isteğin **Authorization** header'ına eklenir.
- **Apinizer, Backend API'ye** istekte bulunur.
- **Backend API, Apinizer'a** yanıt verir.
- **Apinizer, API Client'a** yanıt verir.

:::info

Bu senaryoda token uç noktası örneği olarak `https://auth.ornek.com/oauth/token` adresi kullanılacaktır. Kendi ortamınızda backend uygulamanızın gerçek token URL'sini, client kimlik bilgilerini ve grant tipini kullanmanız gerekir. API Call politikasının alan detayları için [API Çağrısı](/tr/develop/politikalar/api-cagrisi) sayfasına bakabilirsiniz.

:::

## 1) API Proxy'nin Oluşturulması

Bu senaryoda [Swagger Petstore](https://petstore.swagger.io) OpenAPI spesifikasyonu kullanılır. Adımlar:

1. **Development → API Proxies** sayfasına gidin.
2. Sağ üstten **+ Add API Proxy** ile yeni proxy oluşturmayı başlatın.
3. **Swagger 2.x/OpenAPI** şablonunu seçin.
4. **Enter URL** ile spec adresinin girileceği ekrana geçin.

<img src="/images/tutorials/api-proxy-senaryolari/apicall-ile-backend-uygulamasindan-jwt-token-alip-cache-uygulanmasi/choose-api-spec-type.png" alt="Swagger OpenAPI seçimi" width="1000" />

5. **URL** alanına `https://petstore.swagger.io/v2/swagger.json` yazıp **Parse** ile spec'i yükleyin.
6. **Name**, **Description**, **Routing Addresses**, **Client Route** (ör. `/documentation/petstoreproxy`) ve diğer alanları ihtiyacınıza göre doldurup **Save** ile kaydedin.

<img src="/images/tutorials/api-proxy-senaryolari/apicall-ile-backend-uygulamasindan-jwt-token-alip-cache-uygulanmasi/swagger-parse.png" alt="Parse ve proxy ayarları" width="1000" />

Ayrıntılar için [API Proxy Oluşturma](/tr/develop/api-proxy-olusturma).

7. Kayıttan sonra proxy detayında **Develop** sekmesine geçin; sol tarafta endpoint listesi, ortada request/response akış diyagramı görünür. Endpoint listesinin üstündeki **ALL** satırı, eklenecek politikaların **tüm uç noktalara** uygulanması içindir.

<img src="/images/tutorials/api-proxy-senaryolari/apicall-ile-backend-uygulamasindan-jwt-token-alip-cache-uygulanmasi/api-proxy-main-page.png" alt="Develop sekmesi" width="1000" />

:::info

Bu senaryoda **API Call** politikası **ALL** üzerinden **Request** hattına eklenir.

:::

8. İlk kurulumdan sonra (ve ileride politika kaydettikten sonra) değişikliklerin ortama yansıması için sağ üstten **Deploy** / **Redeploy** yapın.

## 2) Token Değerini Taşıyacak Değişkenlerin Oluşturulması

Token yanıtından `access_token` okumak ve backend **Authorization** header'ına yazmak için değişken tanımları gerekir.

1. **Development → Variables** sayfasına gidin.
2. Her değişken için sağ üstten **Create** (veya eşdeğer **+ New**) ile yeni kayıt açın; **Name**, **Type** ve ilgili alanları doldurup kaydedin.

Bu senaryoda aşağıdaki değişkenler oluşturulacaktır:

| Değişken Adı | Tip | Kullanım |
| --- | --- | --- |
| **jwtAccessToken** | Body | Token yanıt gövdesinden `$.access_token` değerini okur |
| **jwtExpiresIn** | Body | (Opsiyonel) Token yanıt gövdesinden `$.expires_in` değerini okur |
| **backendAuthToken** | Custom Variable | Token değerinin politika zincirinde taşınması için kullanılır |

**jwtAccessToken** değişkeni için **Tip** olarak **Body** seçilir ve **JSON Path** alanına şu değer yazılır:

```text
$.access_token
```

**jwtExpiresIn** değişkeni için yine **Body** tipi seçilir ve **JSON Path** alanına şu değer yazılır:

```text
$.expires_in
```

**backendAuthToken** için **Custom Variable** tipi seçilir. Bu değişken, API Call yanıtından okunan token'ın After Call aşamasında Authorization header'ına yazılmasında kullanılır.


İlgili değişken tanımlamaları gerçekleştirildikten sonra variables listesi aşağıdaki şekilde gözükecektir.

<img src="/images/tutorials/api-proxy-senaryolari/apicall-ile-backend-uygulamasindan-jwt-token-alip-cache-uygulanmasi/created-variables.png" alt="Variables Menüsü" width="1000"/>

:::info

Değişken kavramı ve tipleri hakkında ayrıntılı bilgi için [Değişkenler (Variables)](/tr/concepts/temel-kavramlar/variable) sayfasına bakabilirsiniz.

:::

## 3) API Call Politikasının Eklenmesi

1. **Development → API Proxies** listesinden bu senaryoda oluşturduğunuz **Swagger Petstore** proxy'sini açın.
2. **Develop** sekmesine geçin.
3. Request hattında **ALL** satırını (veya politikayı yalnızca belirli bir uç noktaya uygulayacaksanız ilgili method/path satırını) seçin.
4. **Actions** satırındaki üç nokta menüsünden **Add Policy** seçin.

<img src="/images/tutorials/api-proxy-senaryolari/apicall-ile-backend-uygulamasindan-jwt-token-alip-cache-uygulanmasi/open-policy-selection-popup.png" alt="Add Policy" width="1000"/>

5. Açılan **Policies** penceresinde **Conversion & Processing** bölümünden **API Call** politikasını seçin.

<img src="/images/tutorials/api-proxy-senaryolari/apicall-ile-backend-uygulamasindan-jwt-token-alip-cache-uygulanmasi/select-api-call-policy.png" alt="API Call seçimi" width="1000" />

### 3.1) Temel Çağrı Ayarları

Bu ekran üzerinde yer alan ifadeler tek tek incelenecek olursa:

- **Call Type** alanı **Two-Way-Call (Process Response)** seçilir. İstek atıldıktan sonra istek sonucunda response olarak dönecek olan token'ın alınıp işlenmesi söz konusu olduğu için sadece isteğin gidişi değil dönecek olan response da önemlidir.
- **Method** alanı **POST** seçilir.
- **URL** alanına token uç noktasının adresi yazılır. Bu senaryoda örnek adres:

```text
https://auth.ornek.com/oauth/token
```

<img src="/images/tutorials/api-proxy-senaryolari/apicall-ile-backend-uygulamasindan-jwt-token-alip-cache-uygulanmasi/api-call-settings-1.png" alt="API Call Temel Ayarlar" width="1000" />

### 3.2) Request — Token İsteğinin Hazırlanması

Token uç noktasına gidecek istek, istemciden gelen orijinal body'nin iletilerek gerçekleştirilebileceği gibi istemciden gelecek olan istek body'si silinerek API CALL Politikası içerisinde API CALL için bir istek body'si de yaratılabilir.

- **Clear Copied Body Content** ve **Use Message Template** açık olsun.
- **Message Template Content Type** olarak **x-www-form-urlencoded** seçin (token servisi form body bekliyorsa).
- Body şablonuna token almak için gerekli alanları yazın.

| Key | Value |
| --- | --- |
| `grant_type` | `client_credentials` |
| `client_id` | `<CLIENT_ID>` |
| `client_secret` | `<CLIENT_SECRET>` |
| `scope` | `api.read` |

<img src="/images/tutorials/api-proxy-senaryolari/apicall-ile-backend-uygulamasindan-jwt-token-alip-cache-uygulanmasi/api-call-settings-2.png" alt="API Call Temel Ayarlar" width="1000" />

:::warning

`client_id` ve `client_secret` gibi hassas bilgileri politika içinde düz metin olarak tutmak yerine **Variable** / ortam değişkeni kullanmanız önerilir. Production ortamlarında credential'ların vault veya şifreli değişken üzerinden çözülmesi tercih edilmelidir.

:::

:::info
  Ayrıca yazılacak farklı bir script ile, token alımı esnasında kullanılan parametreler kullanıcının gönderdiği değerlere göre dinamik hale getirilebilir. 
  Böylece token alma işlemi kullanıcı bazlı özelleştirilerek, her kullanıcının kendine ait ve kendi verileriyle örtüşen bir token almasını sağlanabilir.
:::

**HEADER sekmesi:**

- Token servisi `Content-Type` bekliyorsa ilgili header eklenir.
- Gerekmiyorsa istemciden gelen gereksiz header'ların token servisine gitmemesi için **Remove All Headers Before Call** aktif edilebilir; ardından yalnızca gerekli header'lar **New Headers** ile eklenir.

Örnek yeni header:

| Name | Value |
| --- | --- |
| `Content-Type` | `application/x-www-form-urlencoded` |
| `Accept` | `application/json` |

### 3.3) Cache — JWT'nin Önbelleğe Alınması

Her istekte token servisine gitmemek için **CACHE** sekmesi yapılandırılır.

Bu senaryoda kullanılacak ayarlar:

| Alan | Değer | Açıklama |
| --- | --- | --- |
| **Enable Cache** | Açık | Token yanıtı cache'lensin |
| **Apply By (Cache By)** | Sabit bir değişken veya sabit anahtar | `client_credentials` senaryosunda gateway'in kullandığı tek token için sabit key yeterlidir. Örnek: `backend-jwt-token` |
| **Capacity (count)** | `10000` | Cache'te tutulacak kayıt sayısı |
| **Storage Type** | **Distributed** (veya **Local**) | Ortamınıza göre |
| **TTL (seconds)** | `3600` | Sabit TTL örneği (Dynamic TTL için aşağıya bakın) |
| **Cache Null Responses** | İsteğe bağlı | Boş yanıtları cache'lemek için işaretlenebilir |

:::info
`Apply By` özelliği ile seçilen variable'ın değerine göre ayrı cache'leme yapılabilir. 
Bu sayede, gelen isteklerde ilgili variable'ın değeri farklılaştığında sistem cache'deki veriyi değil, doğrudan backend'den dönen güncel veriyi kullanarak yeni bir cache kaydı oluşturur. 
Böylece her istek, ait olduğu değere göre unique şekilde cache'lenir ve istekler birbirinden ayırt edilebilir.
:::

:::info
  Eğer token bazında bir ayrım yapılmasına gerek yoksa Apinizer ilgili backend'in tek yetkili kullanıcısı konumundaysa, cache sayısının 1 olarak ayarlanması önerilir.
:::

<img src="/images/tutorials/api-proxy-senaryolari/apicall-ile-backend-uygulamasindan-jwt-token-alip-cache-uygulanmasi/default-cache-settings.png" alt="API Call Cache Temel Ayarlar" width="1000" />

Yukarıdaki ekran görüntüsünde **Cache** sekmesinde sabit **TTL (seconds)** ile basit cache örneği verilmiştir. Token'ın gerçek ömrüne göre tutmak için **Enable Dynamic TTL** seçeneğini açın.

### Dynamic TTL ile JWT süresine göre cache

<img src="/images/tutorials/api-proxy-senaryolari/apicall-ile-backend-uygulamasindan-jwt-token-alip-cache-uygulanmasi/api-call-cache-settings-1.png" alt="Dynamic TTL — JWT exp" width="1000" />

:::info
  Sabit TTL yerine token'ın gerçek geçerlilik süresine göre cache tutulması önerilir.
:::

**Dinamik TTL yapılandıması için iki yaygın yöntem vardır:**

**Yöntem A — JWT `exp` claim'i (önerilen):**

1. **Enable Dynamic TTL** açık.
2. **TTL Source Variable** olarak `jwtAccessToken` seçilir.
3. **Value is inside a JWT Token** açık; **JWT Claim Name:** `exp`.
4. **Value Format:** **Unix Epoch (saniye)** veya arayüzde gösterilen **ISO 8601 DateTime** (token yapınıza göre).
5. **Offset (seconds):** ör. `-60` (süre dolmadan cache yenilensin).
6. **Fallback TTL (seconds):** ör. `300`.

**Yöntem B — `expires_in` alanı:**

Token yanıtı aşağıdaki gibiyse:

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 3600
}
```

1. **Dinamik TTL Etkinleştir** açılır.
2. **TTL Kaynak Değişkeni** olarak `jwtExpiresIn` (`$.expires_in`) seçilir.
3. **Değer Formatı** olarak **Expires In (saniye)** seçilir.
4. **Offset** yine `30` saniye verilir.

:::info

Dynamic TTL alanlarının ayrıntılı açıklaması için [API Çağrısı — Dinamik TTL](/tr/develop/politikalar/api-cagrisi#dinamik-ttl-dynamic-ttl) bölümüne bakabilirsiniz.

:::

### 3.4) Response — Token'ın Authorization Header'ına Eklenmesi

Token alındıktan (veya cache'ten okunduktan) sonra, backend'e gidecek **orijinal istek** üzerine JWT yazılmalıdır.

**BODY sekmesi:**

- **Message Template Operation Type** olarak **NOT_CHANGE_BODY** seçilir. Böylece token servisinden dönen gövde, istemciden gelen orijinal request body'nin üzerine yazılmaz.

**Original Message Data Manipulation / HEADER sekmesi:**

:::info
  Authorization header'ına, Original Data Manipulation yöntemiyle API çağrısından dönen JWT'yi ekleyebiliriz. Ancak ele aldığımız senaryoda backend servisimiz JWT token'ı "Bearer" prefix'i ile beklemektedir.
  prefix (ön ek)'in Apinizer üzerine eklenebilme özelliğini kullanabilmek için JWT'yi Body sekmesinden değil, Header sekmesinden set etmemiz gerekir.
:::

- Backend'e gidecek isteğe yeni bir header eklenir:

| Name | Kaynak | Prefix | Açıklama |
| --- | --- | --- | --- |
| `Authorization` | `jwtAccessToken` değişkeni | **BEARER** | `Bearer <access_token>` formatında header eklenir |

**Response → Header** sekmesinde backend'e gidecek orijinal isteğe header ekleyin:

1. **Header** sekmesine geçin.
2. **New Header** ile yeni header tanımını açın.
3. **Name** alanına `Authorization` yazın.
4. **Value Source** olarak **Use a Variable** seçin.
5. **Prefix** alanına `Bearer` yazın (veya listeden seçin).
6. **Value** alanında `jwtAccessToken` değişkenini seçin.
7. Modal pencerede **Save** ile header tanımını tamamlayın.

<img src="/images/tutorials/api-proxy-senaryolari/apicall-ile-backend-uygulamasindan-jwt-token-alip-cache-uygulanmasi/api-call-add-jwt-settings-2.png" alt="Authorization header — jwtAccessToken" width="1000" />

:::warning

İstemciden gelen istekte zaten bir `Authorization` header'ı varsa ve backend'e yalnızca gateway'in aldığı JWT gitmeliyse, After Call öncesinde eski Authorization header'ını silin veya **Clear Authentication Information** benzeri bir yaklaşımla istemci kimlik bilgisinin backend'e sızmasını engelleyin.

:::

Token alma, cache ve header adımları bittikten sonra API Call politika ekranının sağ üstündeki **Save** ile politikayı kaydedin. Proxy listesine veya proxy **Develop** görünümüne dönüp sağ üstten **Deploy** / **Redeploy** yapın.

### 3.5) Hata Mesajı Özelleştirme (İsteğe Bağlı)

Token servisi erişilemezse veya timeout olursa istemciye anlamlı bir hata dönülmesi için **Error Message Customization** sekmesi kullanılabilir.

Örnek:

```json
{
  "statusCode": 502,
  "errorCode": "BACKEND_TOKEN_UNAVAILABLE",
  "message": "Backend token servisi yanıt vermiyor. Lütfen daha sonra tekrar deneyin."
}
```

## 4) API Proxy'nin Test Edilmesi

**Swagger Petstore** isimli proxy seçilir.

**Develop** sekmesi altında yer alan bir endpoint seçilir. Bu senaryoda **`/user/login`** endpointi kullanılacaktır.

**Test Endpoint** ifadesine tıklanarak bu endpoint test edilir.

**Send** butonuna basılarak direkt istek gönderilir.

### 4.1) İlk istek (Cache miss)

İlk istekte cache boş olduğu için akış şu şekilde ilerler:

1. API Call, token uç noktasına POST atar.
2. Dönen JWT cache'e yazılır (Dynamic TTL ile).
3. JWT, Authorization header'ına eklenir.
4. Backend API çağrılır.

Başarılı yanıt alınır.

<img src="/images/tutorials/api-proxy-senaryolari/apicall-ile-backend-uygulamasindan-jwt-token-alip-cache-uygulanmasi/first-succeeded-request.png" alt="First Succeeded Request" width="1000" />

:::info

İlk istekte token servisi çağrıldığı için gecikme, sonraki isteklere göre daha yüksek olabilir. Trace / adım adım izleme açıksa API Call adımının süresi görülebilir.

:::

### 4.2) Sonraki istekler (Cache hit)

Aynı proxy'ye kısa süre içinde yeniden istek atıldığında:

1. Cache'te geçerli JWT bulunur.
2. Token uç noktasına **gidilmez**.
3. Cache'teki JWT Authorization header'ına yazılır.
4. Backend API çağrılır.

:::info
  Senaryonun konusu olan JWT'nin API Call ile alınarak cache'lenmesini adım adım daha iyi görebilmek adına cache'den dönmesini beklediğimiz isteği trace ile inceleyeceğiz.
:::

**İsteğin Trace üzerinden izlenebilmesi için**;

- **Trace** sekmesinde ortamı seçip **Start** ile izlemeyi başlatın.

<img src="/images/tutorials/api-proxy-senaryolari/apicall-ile-backend-uygulamasindan-jwt-token-alip-cache-uygulanmasi/open-tracing.png" alt="Tracing Start" width="1000" />

- **Develop** sekmesinde **`GET /user/login`** (veya test ettiğiniz uç nokta) seçin; alttaki **Test Endpoint** ile **Send** gönderin.

<img src="/images/tutorials/api-proxy-senaryolari/apicall-ile-backend-uygulamasindan-jwt-token-alip-cache-uygulanmasi/test-endpoint.png" alt="Test Endpoint" width="1000" />

- **Trace** sekmesine dönüp gönderdiğiniz isteğin satırına tıklayın.

- Açılan ekranda API Call politikası seçilir.

### 4.3) Token süresi dolduğunda

Dynamic TTL + offset sayesinde cache kaydı, JWT `exp` değerinden **offset** kadar önce geçersiz olur. Sonraki istekte tekrar cache miss oluşur; yeni token alınır ve cache yenilenir. Böylece süresi dolmuş token ile backend'e istek gitmesi engellenmiş olur.

:::tip

Aynı token'ı birden fazla API Proxy'de kullanmanız gerekiyorsa, API Call politikasını **Global Policy** olarak tanımlayıp ilgili proxy'lere bağlayabilirsiniz. Politika alanlarının tamamı için [API Çağrısı](/tr/develop/politikalar/api-cagrisi) dokümanını inceleyin.

:::
