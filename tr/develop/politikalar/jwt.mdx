## Genel Bakış

### Amacı Nedir?

- **Merkezi JWT üretimini standardize etmek**: Farklı istemci tipleri için güvenilir JWT oluşturma akışını Apinizer üzerinde toplar.
- **Kimlik doğrulama kaynaklarını yönetmek**: Secret Manager, LDAP, Database, API veya OIDC tabanlı kimlik doğrulama servislerini seçilebilir hale getirir.
- **Yetkilendirme entegrasyonunu kolaylaştırmak**: Rol ve yöntem bazlı yetkilendirmeyi JWT üretimi ile aynı politika üzerinde koordine eder.
- **Operasyonel denetimi sağlamak**: Token süreleri, yenileme hakları ve header aktarımlarını merkezi olarak kontrol ederek audit ve izlenebilirlik sunar.

### Çalışma Prensibi

1. **İstek Gelişi**: API Gateway'e gelen her HTTP/HTTPS isteği için, istemin kaynak IP adresi tespit edilir.
2. **Politika Kontrolü**: JWT Kimlik Doğrulama politikası aktif ise, sistem aşağıdaki sırayla kontrol yapar:
   - Condition (koşul) tanımlı mı? Varsa koşul sağlanıyor mu?
   - Politika aktif mi (active=true)?
   - Variable kullanılıyor mu yoksa Apinizer default mı?
3. **JWT Üretim ve Doğrulama Süreci**: Seçilen grant type'a göre kimlik doğrulama kaynağı tetiklenir, imzalama algoritması uygulanır, token ömrü ve refresh hakları hesaplanır.
4. **Karar Verme**:
   - **Eşleşme Var**: Token oluşturulur veya doğrulanır, gerekirse kullanıcı/rol header'ları eklenerek hedef servise yönlendirilir.
   - **Eşleşme Yok**: Varsayılan veya özelleştirilmiş hata mesajı ile istek reddedilir; yenileme tokenı üretimi/iptali yapılmaz.
5. **Hata İşleme**: Politika kuralına uymayan istekler için özelleştirilebilir HTTP durum kodu ve hata mesajı döndürülür.

## Özellikler ve Yetenekler

### Temel Özellikler

- **Grant Type Yönetimi**: Client Credentials ve Password grant tipleri arasında hızlı geçiş, her tip için gerekli kimlik doğrulama bileşenlerinin otomatik denetlenmesi.
- **Kimlik Kaynağı Seçimi**: Secret Manager, LDAP, Database, harici API veya [OIDC Kimlik Sağlayıcı](/tr/admin/identity-management/identity-providers/oidc-provider) kaynaklarını JWT üretim sürecine entegre eder.
- **Token Yaşam Döngüsü Kontrolü**: Token ömrü, yenileme hak sayısı ve süreleri için ayrıntılı yapılandırma ve varsayılan değer atamaları.
- **Aktif/Pasif Durum Kontrolü**: Politikanın aktif veya pasif durumunu kolayca değiştirme (active/passive toggle). Pasif durumda politika uygulanmaz ancak yapılandırması saklanır.
- **Koşul Bazlı Uygulama**: Query Builder ile karmaşık koşullar oluşturarak politikanın ne zaman uygulanacağını belirleme (örn: sadece belirli endpoint'lere veya header değerlerine göre).

### İleri Düzey Özellikler

- **JWT İmza Algoritmaları**: RS256, RS384, RS512 seçenekleri ile hedef sistem gereksinimlerine uygun imzalama sağlar.
- **Header Enjeksiyonu**: Kullanıcı kimliği ve rol bilgilerini istenilen header isimleriyle hedefe taşır; role-based yetkilendirme ile entegre çalışır.
- **Refresh Token Politikaları**: Yenileme token'ı üretimi, kullanım limiti ve süreleri üzerinden güvenlik/konfor dengesi kurar.
- **Export/Import Özelliği**: Politika yapılandırmasını ZIP dosyası olarak export etme. Farklı ortamlara (Geliştirme, Test, Production) import etme. Versiyon kontrolü ve yedekleme imkanı.
- **Policy Group ve Proxy Group Desteği**: Birden fazla politikayı Policy Group içinde yönetme. Proxy Group'lara toplu politika atama. Merkezi güncelleme ve deploy işlemleri.
- **Deploy ve Versiyonlama**: Politika değişikliklerini canlı ortama deploy etme. Hangi API Proxy'lerde kullanıldığını görme (Policy Usage). Proxy Group ve Policy Group kullanım raporları.

## Client Id / Client Secret Yönetimi

**Managed From This Policy** seçeneği açık olduğunda, token isteklerinde doğrulanacak Client Id ve Client Secret değerleri; bu politikanın bağlı olduğu **API Proxy**, **API Proxy Group** veya **Politika Grubu (Policy Group)**'nun kendi anahtarlarıdır. Politika formunda yer alan **API Anahtarını Göster (Show API Key)** seçeneğiyle açılan pencerede mevcut Client Id ve Client Secret görüntülenebilir, kopyalanabilir ve gerektiğinde değiştirilebilir. Her iki alan salt okunurdur; değeri göstermek için göz butonu, değiştirmek için kalem butonu (**Client Id Düzenle** / **Client Secret Düzenle**) kullanılır.

### Anahtar Üretim Tipi (Key Generation Type)

Client Id veya Client Secret düzenlenirken ilgili kaydın adı yazılır ve bir anahtar üretim tipi seçilir:

- **Otomatik (Automatic):** Yeni rastgele değeri sistem üretir.
- **Manuel (Manual):** Değeri siz yazarsınız. Anahtar değerini elle girmenin tek yolu budur; yalnızca boşluklardan oluşan değer kabul edilmez.

  alt="Client Id veya Secret Key Düzenle onay diyaloğu"
  width="1000"
  height="486"
/>

:::warning

Anahtarı değiştirmek kritik bir işlemdir: Client ID değiştirilir ve mevcut değeri kullanan entegrasyonlar çalışmaz. Devam edebilmek için ilgili kaydın adını yazmanız, **Düzenle** butonuna tıklamanız ve son soruyu ("Key'i değiştirmek istediğinizden emin misiniz?") onaylamanız istenir. Yeni anahtar taslak olarak tutulur; kaydedilmeden geçerli olmaz (**Save** ve key dialogunda onay; **Cancel** taslağı iptal eder); kayıttan sonra yeni anahtarların etkin olabilmesi için ilgili API Proxy, API Proxy Group veya Politika Grubu'nun yeniden yüklenmesi (redeploy) gerekir. Bu politikayı kullanan mevcut istemcilerin de yeni Client Id/Client Secret değerleriyle yeniden yapılandırılması gerekir.

:::

### Ekranlar Arası Tutarlılık

Bu Client Id / Client Secret görüntüleme, kopyalama ve düzenleme deneyimi (Otomatik/Manuel seçimi, isim yazarak onaylama, son onay adımı dahil); **API Proxy**, **Politika Grubu (Policy Group)** ve **API Proxy Group** ekranlarındaki kendi anahtar yönetimi bölümleriyle birebir aynıdır. Bu JWT Kimlik Doğrulama Politikası bir API Proxy'nin, bir API Proxy Group'un veya bir Politika Grubu'nun politika listesine bağlandığında — global (paylaşılan) bir politika olarak seçilmiş olsun ya da o API/Grup'a özel yerel bir politika olarak oluşturulmuş olsun — politika formunda görünen **API Anahtarını Göster** seçeneği aynı deneyimi sunar.

## Client Authentication — Authorization Basic Header Desteği (RFC 6749 §2.3.1)

**Örnek**:

<Tabs>
<TabItem value="basic-authorization-header-yeni-2026-04-4" label="Basic Authorization Header (Yeni — 2026.04.4)">

```bash
curl -u "my-client-id:my-secret" \
  -d "grant_type=client_credentials" \
  https://gateway.example.com/credential/token
```

</TabItem>
<TabItem value="body-parametreleri-geriye-donuk-uyumlu" label="Body Parametreleri (Geriye Dönük Uyumlu)">

```bash
curl -d "grant_type=client_credentials&client_id=my-client-id&client_secret=my-secret" \
  https://gateway.example.com/credential/token
```

</TabItem>
</Tabs>

**Önemli Kurallar**:
- **Çift gönderim yasağı**: Aynı istekte hem Authorization Basic header'ı hem body'de `client_id`/`client_secret` parametreleri gönderirseniz, sunucu HTTP 400 (`invalid_request`) ile reddeder (RFC 6749 §2.3.1 "MUST NOT" kuralı).
- **Bozuk header işlemesi**: Base64-decode edilemeyen veya eksik Basic header'lar HTTP 401 (`invalid_client`) ile reddedilir.
- **Diğer Authorization scheme'leri**: Basic dışındaki yetkilendirme türleri (örn. `Bearer`, `Digest`) görmezden gelinir; bu durumda body parametreleri kullanılır.
- **Şifre ve kullanıcı adı**: PASSWORD grant akışında `username` ve `password` her zaman request body'de gönderilir; Authorization header sadece `client_id`/`client_secret` için kullanılır.

**Koşullar** ve **Hata Mesajı Özelleştirme** panellerinin açıklaması için [Politika Nedir?](/tr/concepts/temel-kavramlar/politika-nedir) sayfasındaki [Koşullar](/tr/concepts/temel-kavramlar/politika-nedir#koşullar) ve [Hata Mesajı Özelleştirme (Error Message Customization)](/tr/concepts/temel-kavramlar/politika-nedir#hata-mesajı-özelleştirme-error-message-customization) bölümlerini inceleyebilirsiniz.

Hata mesajı yapılandırmasının tüm katmanları, öncelik sırası ve senaryo örnekleri için [Hata Mesajı Yapılandırma Rehberi](/tr/concepts/temel-kavramlar/hata-mesaji-yapilandirma) sayfasına bakın.

## Tarayıcı ile Giriş (authorization_code) {#tarayici-ile-giris}

**Bu Poliçe'den Yönet** modunda politikaya **Tarayıcı ile giriş (authorization_code)** anahtarını açabilirsiniz. Anahtar açıkken standart bir OAuth2 istemcisi (örneğin Claude Code veya MCP Inspector) Apinizer'ı yetkilendirme sunucusu olarak kullanır. Kullanıcı gateway'in `/auth` giriş sayfasında oturum açar ve uygulama onun adına token alır. Seçili eski grant (client credentials veya password) çalışmaya devam eder.

- Kullanıcılar politikanın kimlik kaynağından gelir: Secret Manager, LDAP, veritabanı veya API. Kimlik kaynağı OIDC ise anahtar kapalıdır.
- Politikada **Token Never Expires** kapalı olmalı ve access token süresi sonlu olmalıdır. Refresh token'a izin veriyorsanız refresh süresi de sonlu olmalıdır. Tarayıcı girişi süresiz token vermez.
- İstemci, uygulamaya ait bir API istemcisidir. `client_id` değeri bu istemcinin client kimliğidir. Uygulamanın proxy için ACL satırı da gerekir.
- Anahtar yalnız API Proxy'nin kendi token politikasında kullanılabilir. Proxy grubu politikasında ve bir metodun politikasında kullanılamaz.
- Anahtarı açtıktan ya da kapattıktan sonra politikayı kaydedin ve proxy'yi yeniden deploy edin. Anahtarı kapatırsanız tarayıcı girişiyle verilmiş token'lar hemen geçersiz olur.
- Tüm worker'lar yükseltilmeden anahtarı açmayın.
- **ACL'den Yönet** modunda anahtar görünmez. Bu modda tarayıcı girişi, uygulamaya ait API istemcisinde açılır.

Politika kaydedilirken şu hata mesajları görünebilir:

| Mesaj | Anlamı |
|---|---|
| Token politikasının grant listesi geçerli değil. Liste, seçili grant tipiyle aynı olan tek bir eski grant (client credentials veya password) içermelidir. Tarayıcı girişi (authorization_code) eklenebilir. | Grant listesi geçersiz. |
| Bu politikada tarayıcı girişi (authorization_code) için access token süresi sonlu olmalıdır. Refresh açıksa refresh token süresi de sonlu olmalıdır. | Süresiz token ayarı var. |
| Kimlik kaynağı OIDC ise tarayıcı girişi (authorization_code) kullanılamaz. OIDC sağlayıcısının kendi girişini kullanın. | Kimlik kaynağı OIDC. |
| Tarayıcı girişi (authorization_code) API proxy'nin kendi token politikasının ayarıdır. Proxy grubu politikasında kullanılamaz. | Politika bir proxy grubuna bağlı. |
| Tarayıcı girişi (authorization_code) API proxy'nin kendi token politikasının ayarıdır. Bir metodun politikasında kullanılamaz. | Politika bir metoda bağlı. |

Adım adım kurulum için [MCP Gateway'e Keycloak Olmadan Tarayıcı ile Giriş](/tr/tutorials/ai-proxy-senaryolari/mcp-gateway-tarayici-girisi) senaryosuna bakın. Uç noktalar için [Token Servisi](/tr/develop/politikalar/token-service/genel-bakis) sayfasına bakın.

## Yetki Devri Token'larını Kabul Etme (Token Exchange) {#yetki-devri-tokenlari}

**Yetki devri token'larını kabul et (token exchange)** anahtarı, bir ajanın bu API proxy'yi bir kullanıcı adına çağırmasını sağlar. Ajan, token exchange ile aldığı token'ı kullanır. Anahtar varsayılan olarak kapalıdır. Anahtar kapalıyken politika yetki devri token'ını eskisi gibi reddeder. Doğrudan istemciler etkilenmez.

- Anahtar hem **ACL'den Yönet** hem de **Bu Poliçe'den Yönet** modunda görünür. Kimlik kaynağı OIDC ise görünmez.
- Anahtarı açtığınızda iki alan daha görünür.
- **İzin verilen ajanlar**: Ajanların API istemcilerinin client ID değerlerini girin. Eski tüketici için kullanıcı adını girin. Değeri yazın ve Enter tuşuna basın. Liste boşsa hiçbir ajan kabul edilmez.
- **Yetki devri zinciri derinliği**: **Bir ajan** veya **En çok iki ajan** seçeneğini seçin. Varsayılan değer **En çok iki ajan** seçeneğidir.
- Gateway bu ayarı yalnız API proxy'nin kendi istek politikası listesindeki aktif JWT ve OAuth2 politikalarından okur. Metot, proxy grubu veya politika grubu içindeki politikaları okumaz.

Gateway, yetki devri token'ı için şunları denetler:

- Token yalnız bu API proxy içindir. Audience değeri bu proxy'nin kanonik adresidir.
- Zincirdeki her ajan **İzin verilen ajanlar** listesindedir. Zincir, seçilen derinlikten uzun değildir.
- Her ajan hâlâ aktiftir ve token'ları iptal edilmemiştir.
- Kullanıcı, istek kimliği olarak bu proxy'nin erişim denetimlerinden geçer. ACL denetimi açıksa kullanıcının ACL satırı gerekir.
- İstek, kullanıcının **güncel** rolleriyle çalışır. Token'ın scope'u rolleri yalnız daraltabilir. OAuth scope adı olmayan rol taşınmaz.

Reddedilen token için gateway normal "token geçerli değil" yanıtını verir.

JWT politikası yetki devri JWT'lerini doğrular. OAuth2 politikası saklanan (opaque) yetki devri token'larını doğrular. Token exchange, hedef politikanın doğruladığı biçimde token verir. Ajan biçimi seçemez.

Daha fazla bilgi için [Token Exchange (RFC 8693)](/tr/develop/politikalar/token-service/genel-bakis#token-exchange-rfc-8693) bölümüne bakın.

## Yalnızca Kimlik Modu (ACL Kapalı)

**İstemci için ACL Kontrol Et** kapalıyken politika yalnızca kimlik modunda çalışır. Kimliği yine çözümler ve doğrular; ancak tüketicinin bu API Proxy veya Proxy Group için erişim listesini (ACL) kontrol etmez.

| ACL kapalıyken yine uygulananlar | ACL kapalıyken atlananlar |
|----------------------------------|---------------------------|
| Tüketici mevcuttur ve etkindir.<br />Tüketicinin organizasyonu ve üst organizasyonları aktiftir.<br />Tüketicinin geçerlilik süresi (expire date) dolmamıştır.<br />Tüketicinin sözleşmeleri bitiş tarihini geçmemiştir.<br />İstemci IP'si tüketicinin IP listesindedir (**Validate Client Address** açıksa).<br />API Client sahibi aktiftir.<br />Rol yetkilendirmesi (etkinse) ve Limit Plan kuralları uygulanır.<br />İstek doğrulanmış olarak işaretlenir ve çözümlenen kimlik trafik loguna yazılır. | Tüketicinin bu API Proxy veya Proxy Group için erişim satırı (süresi, ortam etkinleştirme anahtarı, izin verilmeyen method ve proxy'ler).<br />API Client aboneliği ve erişim izinleri (portal abonelikleri).<br />Bu bilgi erişim satırından geldiği için trafik logunda bu istekler için abonelik ürünü ve planı görünmez. |

:::warning

ACL kapalıyken, kimlik kurallarını geçen ortamdaki her aktif tüketici API'yi çağırabilir. Proje sınırı yoktur.

Seçenek token uçlarına da uygulanır: PASSWORD grant için token üretimi aynı anahtarı izler.

:::

:::info

LDAP, Database, API ve OIDC kimlik kaynakları ACL'yi hiçbir zaman sorgulamaz. Bu kaynaklarda seçeneğin etkisi yoktur.

:::

Bir API Product'ın güvenlik sekmesinde, ACL'si kapalı politika mevcut "Politikadan yönetiliyor" durumuyla raporlanır: kimlik doğrulama consumer store (ACL) yerine politikadan yönetilir, bu nedenle uygulama credential'ları orada yetkilenmez.

## İleri Düzey Özellikler

| Özellik | Açıklama ve Adımlar |
|---------|---------------------|
| **Role Bazlı Header Enjeksiyonu** | - Authorization sekmesinden `addRolesToHeader` seçeneğini açın.<br />- Header adını belirleyin (örn. `X-Authenticated-UserRoles`).<br />- Roller JWT claim'lerinden hedef servise taşınır. |
| **JWT Regenerator Service Entegrasyonu** | - Kimlik kaynağı olarak API seçildiğinde ikinci servis modalını açın.<br />- JWT yenileyici servisi seçin ve kaydedin.<br />- Password grant akışında refresh token kullanımıyla entegre çalışır. |
| **Method Bazlı Yetkilendirme** | - Authorization sekmesinde Method Access özelliğini aktif edin.<br />- API method listelerini seçip rol eşleştirmesi yapın.<br />- İstekler yöntem bazında 403 ile reddedilebilir. |

## Best Practices

### Yapılması Gerekenler ve En İyi Uygulamalar

| Kategori | Açıklama / Öneriler |
|----------|---------------------|
| **Token Ömrü Yönetimi** | **Kötü:** Varsayılan süreleri her ortamda kullanmak.<br />**İyi:** Canlı Ortam için 15 dk, Geliştirme için 60 dk belirlemek.<br />**En İyi:** Kullanım metriklerine göre token süresini düzenli gözden geçirmek. |
| **Refresh Token Stratejisi** | **Kötü:** Sınırsız yenileme hakkı tanımak.<br />**İyi:** 3 yenileme hakkı ve 24 saatlik süre kullanmak.<br />**En İyi:** MFA zorunlu oturumlarda refresh'i kapatmak. |
| **Header Kullanımı** | **Kötü:** Varsayılan header isimlerini değiştirmeden bırakmak.<br />**İyi:** Hedef servisin beklediği header adlarını tanımlamak.<br />**En İyi:** Güvenlik taramasından geçen özel header adları kullanmak. |
| **Grant Type Seçimi** | **Kötü:** Tüm istemcilerde PASSWORD grant kullanmak.<br />**İyi:** Makine-makine iletişimde CLIENT_CREDENTIALS tercih etmek.<br />**En İyi:** Minimum yetki prensibiyle grant seçimini per istemci analizine dayandırmak. |
| **Kimlik Kaynağı Yönetimi** | **Kötü:** Aynı anda birden fazla kimlik kaynağı tanımlamak.<br />**İyi:** Her grant tipinde tek kaynak seçmek.<br />**En İyi:** Secret Manager sürümleriyle uyumlu merkezi kimlik yönetimi kurmak. |

### Güvenlik En İyi Uygulamaları

| Güvenlik Alanı | Açıklama / Uyarılar |
|----------------|---------------------|
| **Token Saklama** | Token'ları tarayıcı localStorage yerine Secure Cookie'de saklayın; `HttpOnly` ve `Secure` bayraklarını zorunlu tutun. |
| **İmza Algoritması** | RS256 dışına geçerken IM sertifika yönetiminin hazır olduğundan emin olun; anahtar rotasyonunu planlayın. |
| **Refresh Token Koruması** | Yenileme uç noktalarını IP ve cihaz doğrulamasıyla sınırlayın; başarısız girişimleri loglayın. |
| **Header Hijacking Önlemleri** | `ClearAuth` özelliğini legacy token geçişlerinde aktif edin; karışık kimlik doğrulama zincirleri oluşturmayın. |
| **Audit ve İzleme** | Politika loglarını SIEM'e aktarın; grant tipine göre başarısız girişleri ayrı dashboard'larda izleyin. |

### Kaçınılması Gerekenler

| Kategori | Açıklama / Uyarılar |
|----------|---------------------|
| **Sınırsız Token Ömrü** | **Neden kaçınılmalı:** Güvenlik ihlallerinde kalıcı yetki sağlar.<br />**Alternatif:** Token sürelerini ortam bazlı kısaltın. |
| **URL Parametresiyle Token Taşıma** | **Neden kaçınılmalı:** Loglarda token sızıntısına yol açar.<br />**Alternatif:** Header veya Authorization Bearer kullanın. |
| **Ortak Kimlik Kaynağı** | **Neden kaçınılmalı:** Üretim ve test kimlikleri karışabilir.<br />**Alternatif:** Her ortam için ayrı Secret Manager domaini kullanın. |
| **Yetkisiz Refresh Servisi** | **Neden kaçınılmalı:** Yenileme endpoint'i ele geçirilebilir.<br />**Alternatif:** JWT Regenerator servisini sadece güvenli ağ segmentlerinden erişilebilir kılın. |

### Performans İpuçları

| Kriter | Öneri / Etki |
|--------|--------------|
| **Token Hesaplama Süresi** | **Öneri:** RS256 tercih edip anahtar boyutunu gereksiz büyütmeyin.<br />**Etki:** JWT üretimi milisaniyeler seviyesinde kalır. |
| **Refresh Çağrıları** | **Öneri:** Yenileme sayısını sınırlayın, gereksiz round-trip'i azaltın.<br />**Etki:** Gateway throughput'u artar. |
| **Kimlik Kaynağı Yanıt Süresi** | **Öneri:** LDAP/API kaynaklarını Cache ile destekleyin.<br />**Etki:** Throttling tetiklenmeden yüksek TPS yönetilir. |
| **Header Boyutu** | **Öneri:** Rol listelerini minimal tutun, gereksiz claim aktarmayın.<br />**Etki:** Upstream servilerine giden header yükü azalır. |
| **Koşul Değerlendirmesi** | **Öneri:** Query Builder kurallarını optimize edin; gereksiz regex kullanmayın.<br />**Etki:** Politika değerlendirme süresi düşer. |

## Sık Sorulan Sorular (SSS)

| Kategori | Soru | Cevap |
|----------|-----------|-----------|
| **Genel** | Password grant kullanan politikada kimlik kaynağı olmadan kayıt yapabilir miyim? | Hayır. PASSWORD seçiliyken bir Identity Role Group veya Secret Manager bağlantısı zorunludur; aksi halde politika Validation hatası verir. |
| **Genel** | Token Never Expires seçeneği ne zaman kullanılır? | Sadece makine-makine iletişiminde ve güvenliği başka katmanların sağladığı durumlarda önerilir; kullanıcı tabanlı erişimlerde risklidir. |
| **Teknik** | JWT Regenerator Service API zorunlu mudur? | Sadece kimlik kaynağı API seçildiğinde ve refresh token senaryosunda gereklidir; diğer kaynaklarda otomatik olarak pasif kalır. |
| **Teknik** | Header'a eklenen rol listesi nasıl belirlenir? | Authorization Configuration alanında seçilen rol/claim eşleştirmeleri doğrultusunda `addRolesToHeader` aktifken otomatik yazılır. |
| **Kullanım** | Global politikayı local kopyaya dönüştürmek için ne yapmalıyım? | Detay sayfasından **[Localize]** butonunu kullanın; politika yeni bir local sürüme kopyalanır ve düzenlenebilir hale gelir. |
| **Kullanım** | Politika ismi çakışırsa nasıl ilerlerim? | Sistem name-exist kontrolüyle uyarır; ismi değiştirin veya global politikayı localize ederek benzersiz ad verin. |
