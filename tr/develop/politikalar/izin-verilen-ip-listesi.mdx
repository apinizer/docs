## Genel Bakış

### Amacı Nedir?

- **Erişim Güvenliğini Artırmak**: API Gateway (API Vekil Sunucusu) üzerinden sunulan servislere yalnızca güvenilir IP adreslerinden erişim sağlanmasını garanti eder.
- **Yetkisiz Erişimi Engellemek**: Beyaz listede yer almayan kaynaklardan gelen istekleri otomatik olarak reddederek güvenlik açıklarını minimize eder.
- **Coğrafi Kısıtlama Uygulamak**: Belirli ülke ve şehirlerden gelen istekleri kabul ederek veya engelleyerek coğrafi bazlı güvenlik politikaları oluşturur.
- **Merkezi IP Yönetimi**: IP grupları kullanarak aynı IP setlerini farklı politikalarda tekrar kullanılabilir hale getirir.
- **Variable Desteği**: Kontrol edilecek istemci IP adresi, bağlantı adresi yerine bir variable'dan okunabilir.

### Çalışma Prensibi

1. **İstek Gelişi**: API Gateway'e gelen her HTTP/HTTPS isteği için, istemcinin kaynak IP adresi tespit edilir.
2. **Politika Kontrolü**: IP Beyaz Listesi politikası aktif ise, sistem aşağıdaki sırayla kontrol yapar:
   - Condition (koşul) tanımlı mı? Varsa koşul sağlanıyor mu?
   - Politika aktif mi (active=true)?
   - İstemci IP adresi bağlantıdan mı yoksa bir variable'dan mı alınıyor?
3. **IP Doğrulama**: İki kontrol yapılır ve isteğin ikisini de geçmesi gerekir:
   - **IP kontrolü**: İstemci IP adresi, manuel tanımlanan IP listesindeki veya seçili IP Gruplarındaki bir kayıtla eşleşir.
   - **Geolocation kontrolü**: Geolocation etkinse ve ülke/şehir kuralları tanımlıysa, istemcinin konumu bu kurallardan biriyle eşleşir.
4. **Karar Verme**:
   - **İki kontrolü de geçer**: İstek bir sonraki politika adımına veya backend servisine yönlendirilir.
   - **Bir kontrolü geçemez**: İstek reddedilir ve özelleştirilmiş hata mesajı döndürülür (default: 403 Forbidden).
   - **Boş IP Listesi**: Politikada ve IP gruplarında hiç IP adresi yoksa IP kontrolü her adrese izin verir. Tanımlıysa Geolocation kuralları yine kontrol edilir.
5. **Hata İşleme**: Politika kuralına uymayan isteklere özelleştirilebilir HTTP durum kodu ve hata mesajı döndürülür.

## Özellikler ve Yetenekler

### Temel Özellikler

- **Manuel IP Listesi Yönetimi**: IPv4 adreslerini, `*` joker karakterlerini (örn: 192.168.1.*) ve `-` aralıklarını (örn: 192.168.1.4-18) tanımlama. Her IP adresi virgül ile ayrılarak eklenebilir.
- **IP Grubu Entegrasyonu**: Önceden tanımlanmış IP gruplarını politikaya ekleme. Birden fazla IP grubunu aynı anda seçme ve yönetme imkanı. IP grupları merkezi olarak güncellenir, politikada otomatik yansır.
- **Global ve Local Politika Desteği**: Global olarak tanımlanıp birden fazla API Proxy'de kullanılabilir veya spesifik bir API Proxy için local politika olarak yapılandırılabilir.
- **Aktif/Pasif Durum Kontrolü**: Politikanın aktif veya pasif durumunu kolayca değiştirme (active/passive toggle). Pasif durumda politika uygulanmaz ancak yapılandırma saklanır.
- **Koşul Bazlı Uygulama**: Query Builder ile karmaşık koşullar oluşturarak politikanın ne zaman uygulanacağını belirleme (örn: sadece belirli endpoint'lere veya header değerlerine göre).

### İleri Düzey Özellikler

- **Geolocation (Coğrafi Konum) Desteği**: Geolocation servis entegrasyonu ile ülke ve şehir bazında IP kontrolü. Tüm ülke veya spesifik şehirlerden gelen istekleri kabul etme/engelleme. Birden fazla ülke ve şehir kombinasyonu tanımlama imkanı.
- **Variable (Değişken) Mekanizması**: **İstemci IP'sini Kullan** seçeneğini kapatıp bir variable seçin. Politika bağlantı adresi yerine variable'ın tuttuğu adresi kontrol eder.
- **Hata Mesajı Özelleştirme**: HTTP durum kodu özelleştirme (default: 403). Custom JSON veya XML hata mesajı tanımlama. Farklı hata senaryoları için farklı mesajlar yapılandırma.
- **Export/Import Özelliği**: Politika yapılandırmasını ZIP dosyası olarak export etme. Farklı ortamlara (Development, Test, Production) import etme. Versiyon kontrolü ve yedekleme imkanı.
- **Policy Group ve Proxy Group Desteği**: Birden fazla politikayı Policy Group içinde yönetme. Proxy Group'lara toplu politika atama. Merkezi güncelleme ve deploy işlemleri.
- **Deploy ve Versiyonlama**: Politika değişikliklerini canlı ortama deploy etme. Hangi API Proxy'lerde kullanıldığını görme (Policy Usage). Proxy Group ve Policy Group kullanım raporları.

## Politika Parametrelerini Yapılandırma

Bu adımda, kullanıcı **yeni bir politika oluşturabilir** ya da **mevcut politika parametrelerini yapılandırarak** erişim kurallarını belirleyebilir. Tanımlanan parametreler, politikanın çalışma şeklini (örneğin hangi IP'lerin izinli olacağı, coğrafi kısıtlamalar, koşullu aktivasyonlar vb.) doğrudan etkiler. Bu sayede politika hem kuruma özel gereksinimlere göre özelleştirilebilir hem de merkezi olarak yönetilebilir.

### Yeni Allowed IP List Politikası Oluşturma

<img src="/images/develop/politikalar/allowed_new.png" alt="İzin Verilen IP Listesi Politikası Yapılandırma" width="1000" />

#### Yapılandırma Adımları

| Adım | Açıklama / İşlem |
|------|------------------|
| **Adım 1: Oluşturma Sayfasına Gitme** | - Sol menüden **Development → Global Settings → Global Policies → Allowed IP List** bölümüne gidin.<br />- Sağ üstteki **[+ Create]** butonuna tıklayın. |
| **Adım 2: Temel Bilgileri Girme** | **Policy Status (Politika Durumu):** Aktif/Pasif durumu gösterir. Yeni politikalar varsayılan olarak aktiftir.<br /><br />**Name (İsim) Zorunlu:**<br />Örnek: `Production_IP_Whitelist`<br />- Benzersiz isim girin, boşlukla başlamaz.<br />- Sistem otomatik kontrol eder: Yeşil tik: kullanılabilir Kırmızı çarpı: mevcut isim.<br /><br />**Description (Açıklama):**<br />Örnek: "Prod ortamı için yalnızca kurum içi ve partner sistemlerinden gelen isteklere izin verir."<br />- Maks. 1000 karakter.<br />- Politikanın amacını açıklayın. |
| **Adım 3: Variable Kullanımı** | - Sayfanın üst kısmındaki işlem butonları alanında, **[&lt;&gt; Variable]** butonunu kullanarak dinamik değer seçebilirsiniz.<br />- Context/global variable ifadeleri sayesinde politika parametrelerini sabit değer yerine değişken tabanlı yönetebilirsiniz.<br />- Bu kullanım, değişen değerlerde manuel güncelleme ihtiyacını azaltır ve operasyonel kolaylık sağlar.<br />- Detaylı bilgi için [Dinamik Değişkenler](/tr/concepts/temel-kavramlar/dinamik-degiskenler) sayfasını inceleyebilirsiniz. |
| **Adım 4: IP Listesi Yapılandırması** | **İstemci IP'sini Kullan:** Açıkken politika, gateway'in belirlediği istemci IP adresini kontrol eder. Kapalıyken **İstemci IP için Değişken** alanında bir variable seçin; politika variable'ın tuttuğu adresi kontrol eder.<br /><br />**IP Ekleme:**<br />- Tekil IP: `192.168.1.100` → Enter veya ✓ ile eklenir.<br /><br />**IP Silme:** IP etiketine veya ✕ ikonuna tıklayın.<br /><br />IP aralığı belirtmek için (`*` ve `-`) karakterleri kullanılabilir.<br /><br />**Örnekler:**<br />- `10.0.0.1` → Tekil IP<br />- `10.3.10.*` değeri `10.3.10.0` ile `10.3.10.255` arasındaki IP'leri belirtir.<br />- `10.3.10.4-18` değeri `10.3.10.4` ile `10.3.10.18` arasındaki IP'leri ifade eder (4 ve 18 dahil).<br />- `10.*.*.*` → 10 ile başlayan tüm IP'ler<br /><br />IP ekledikten sonra Enter tuşuna basılmalıdır.<br /><br />Yalnızca IPv4 adresleri eşleşir. CIDR notasyonu (örn: `192.168.1.0/24`) hiçbir adresle eşleşmez; bunun yerine `*` ve `-` kullanın. |
| **Adım 5: IP Grupları Kullanımı (İsteğe Bağlı)** | - "Click to add IP Groups" butonuna tıklayın.<br />- Sol tarafta mevcut IP grupları, sağda seçilenler görünür.<br /><br />**Ekleme:**<br />- Sol listeden grup seçin → [Select].<br />- Sağ tarafa taşınır.<br />- Bir grup birden fazla politikada kullanılabilir.<br /><br />**Kaldırma:**<br />- Sağ listede 🗑️ simgesine tıklayın → sol listeye döner.<br /><br />**Avantaj:**<br />- IP listelerini merkezi yönetin.<br />- Tek güncelleme tüm politikalara yansır.<br />- Partner erişimi için idealdir. |
| **Adım 6: Coğrafi Konum Filtresi (İsteğe Bağlı)** | - **Country (Ülke)** dropdown'ından ülke seçin (örnek: Turkey).<br />- **City (Şehir)** dropdown'ı ülke seçilince aktif olur (örnek: Istanbul, Ankara, Izmir).<br />- **[+ Add]** ile tabloya eklenir.<br />- Satırlar 🗑️ ile tekil, üstteki 🗑️ ile toplu silinebilir.<br /><br />**Örnek Senaryolar:**<br />- *Yalnızca Türkiye:* Country: Turkey, City: —<br />- *Türkiye büyük şehirler:* Istanbul, Ankara, Izmir, Bursa<br />- *Birden fazla ülke:* Turkey (tümü), Germany (Berlin, Munich), USA (tümü) |
| **Adım 7: Koşul Tanımlama (İsteğe Bağlı)** | - **Condition** sekmesine geçin.<br />- Koşullar, politikanın hangi durumda aktif olacağını belirler.<br /><br />**Örnekler:**<br />• Ortam bazlı: Header = X-Environment, Operator = Equals, Value = production<br />• API Key bazlı: Header = X-API-Key, Starts With = PROD-<br />• Endpoint bazlı: Path = /api/admin/*<br /><br />Koşul tanımlanmazsa politika her zaman aktiftir.<br /><br /> |
| **Adım 8: Hata Mesajı Özelleştirme (İsteğe Bağlı)** | - **Error Message Customization** sekmesine gidin<br />- Erişim reddedildiğinde dönecek mesajı özelleştirin.<br /><br />**Varsayılan:**<br />`{ "statusCode": 403, "message": "Access denied: IP not whitelisted" }`<br /><br />**Özel:**<br />`{ "statusCode": 403, "errorCode": "ACCESS_DENIED", "message": "You do not have permission to access this API.", "details": "Your IP address is not on the allowed list. Please contact support@sirket.com for access." }` |
| **Adım 9: Kaydetme** | - Sağ üstteki **[Save]** butonuna tıklayın.<br /><br />**Kontrol Listesi:**<br />- Benzersiz isim<br />- Zorunlu alanlar dolu<br />- En az bir IP veya IP grubu tanımlı (hiç IP adresi olmayan bir politika her adrese izin verir)<br /><br />**Sonuç:**<br />- Politika listeye eklenir.<br />- API'lere bağlanabilir.<br />- Global politikaysa otomatik uygulanır. |

:::warning

Hiç IP adresi kalmayan bir İzin Verilen IP Listesi **her adrese** izin verir. Bu durum, politikanın kendi IP adresi yoksa ve IP grupları boş, silinmiş veya devre dışı bırakılmışsa oluşur: gateway eksik veya devre dışı bir grubu atlar ve bu yüzden istekleri reddetmez. Bir IP grubunu silerken veya devre dışı bırakırken önce hangi politikaların kullandığını kontrol edin; IP Grubu penceresi bunları listeler. Bkz. [IP Grupları](/tr/admin/identity-management/ip-guruplari).

:::

**Koşullar** ve **Hata Mesajı Özelleştirme** panellerinin açıklaması için [Politika Nedir?](/tr/concepts/temel-kavramlar/politika-nedir) sayfasındaki [Koşullar](/tr/concepts/temel-kavramlar/politika-nedir#koşullar) ve [Hata Mesajı Özelleştirme (Error Message Customization)](/tr/concepts/temel-kavramlar/politika-nedir#hata-mesajı-özelleştirme-error-message-customization) bölümlerini inceleyebilirsiniz.

Hata mesajı yapılandırmasının tüm katmanları, öncelik sırası ve senaryo örnekleri için [Hata Mesajı Yapılandırma Rehberi](/tr/concepts/temel-kavramlar/hata-mesaji-yapilandirma) sayfasına bakın.

## İleri Düzey Özellikler

| Özellik | Açıklama ve Adımlar |
|---------|---------------------|
| **Variable ile İstemci IP'si** | - Öncelikle istemci IP adresini tutan bir Variable oluşturun (Variables menüsünden), örneğin bir header'dan okunan değer.<br />- Politika oluşturma/düzenleme sayfasında **İstemci IP'sini Kullan** toggle'ını kapatın.<br />- **İstemci IP için Değişken** alanında variable'ı seçin.<br />- Kaydedin. Politika artık her istekte variable'daki adresi kontrol eder.<br />- Variable'ın değeri yoksa politika isteği reddetmez. |
| **IP Grubu ile Merkezi Yönetim** | - IP Group menüsünden yeni bir IP Grubu oluşturun (örn: "Partner IPs").<br />- IP grubuna IP'leri ekleyin (politikadaki biçimle aynı).<br />- Farklı IP Beyaz Listesi politikalarında bu grubu kullanın.<br />- IP Grubunu güncelleyin (yeni IP ekle/çıkar).<br />- Değişiklik otomatik olarak bu grubu kullanan tüm politikalara yansır.<br /><br />**Avantaj:** Bir IP setini birden fazla politikada kullanma, tek noktadan güncelleme. |
| **Geolocation ile Ülke Bazlı Engelleme** | **Ön Gereksinim:** Geolocation Settings'den Geolocation servisinin aktif edilmiş olması.<br />- Politika sayfasında **"Geolocation"** bölümünde ülke dropdown'ını açın.<br />- İstenen ülkeyi seçin (örn: Germany).<br />- Şehir seçmeden **[ Add ]** butonuna tıklayın (tüm ülke için geçerli olur).<br />- Birden fazla ülke ekleyebilirsiniz.<br /><br />**Avantaj:** IP bilgisine gerek kalmadan coğrafi lokasyon bazlı erişim kontrolü |
| **Geolocation ile Şehir Bazlı Engelleme** | - Ülke seçtikten sonra **"City"** dropdown'ı aktif olur.<br />- Bir veya birden fazla şehir seçin (multi-select destekler).<br />- **[ Add ]** butonuna tıklayın.<br />- Eklenen şehirler tablo formatında görünür.<br /><br />**Örnek:** "Türkiye - İstanbul" ve "Türkiye - Ankara" seçilirse sadece bu iki şehirden istekler kabul edilir.<br /><br />**Dikkat:** Şehir verisinin doğruluğu Geolocation sağlayıcısına bağlıdır. |
| **Condition ile Koşullu IP Kontrolü** | - Politika düzenleme sayfasında **"Condition"** sekmesine geçin.<br />- Query Builder'da koşul oluşturun (örn: `path='/admin' OR header.X-Admin-Request='true'`).<br />- Koşul sağlandığında IP kontrolü yapılır, sağlanmazsa politika atlanır.<br />- Kaydedin.<br />- Admin endpoint'lere özel IP kısıtlaması, public API'lere IP kontrolü yok.<br /><br />**Avantaj:** Aynı API Proxy'de farklı endpoint'ler için farklı politika davranışları. |
| **Hata Mesajı Özelleştirme** | - **"Error Message Customization"** sekmesine geçin.<br />- Hata tipi seçin (örn: "IP Not Whitelisted").<br />- HTTP Status Code değiştirin (örn: 403 yerine 401).<br />- Custom JSON mesajı girin:<br />`{ "error": "Erişim Reddedildi", "message": "IP adresiniz beyaz listede değil", "code": "IP_NOT_ALLOWED" }`<br />- Dil bazlı mesajlar ekleyin (TR, EN).<br />- Kaydedin.<br /><br />**Avantaj:** Kullanıcıya daha anlamlı hata mesajları, custom error tracking. |
| **Export/Import ile Politika Taşıma** | **Export:**<br />- Politika listesinde "..." menüsünden **[ Export ]** seçin.<br />- ZIP dosyası indirilir (format: `DD-MMM-YYYY-policy-[name]-export.zip`).<br /><br />**Import:**<br />- Liste sayfasında **[ Import ]** butonuna tıklayın.<br />- Export edilmiş ZIP dosyasını seçin.<br />- Import ayarlarını yapın (override, yeni ad vb.).<br />- Import işlemini tamamlayın.<br /><br />**Avantaj:** Geliştirme → Test → Canlı ortam arasında politika taşıma, yedekleme. |
| **Policy Group ile Toplu Yönetim** | - **"Policy Group"** menüsünden yeni bir grup oluşturun.<br />- IP Beyaz Listesi politikası dahil birden fazla politikayı gruba ekleyin.<br />- Policy Group'u bir veya birden fazla API Proxy'ye atayın.<br />- Grup içindeki tüm politikalar toplu olarak uygulanır.<br /><br />**Avantaj:** Birden fazla politikayı paket olarak yönetme, toplu deploy. |

### Yapılması Gerekenler ve En İyi Uygulamalar

| **Global vs Local Politika Seçimi** | **Kötü:** Her API Proxy için ayrı local IP Beyaz Listesi politikası oluşturmak<br />**İyi:** Ortak güvenlik politikası olarak global politika kullanmak<br />**En İyi:** Genel kurallar için global, özel durumlar için local politika kullanmak |
| **Geolocation Kullanımı** | **Kötü:** Tüm ülke IP bloklarını manuel eklemek<br />**İyi:** Geolocation servisini aktif etmek<br />**En İyi:** Ülke ve şehir kombinasyonlarını kullanarak hassas kontrol sağlamak |
| **Hata Mesajı Özelleştirme** | **Kötü:** Default 403 hatası kullanmak<br />**İyi:** Custom JSON mesajı ile detaylı açıklama yapmak<br />**En İyi:** Farklı hata senaryoları için farklı mesajlar, log ID eklemek |
| **Politika Adlandırma** | **Kötü:** `policy1`, `ipwhite` gibi belirsiz isimler<br />**İyi:** `IP_White_List_Production` gibi açıklayıcı isimler<br />**En İyi:** `[ENV]_[Purpose]_IP_White` formatı (örn: `PROD_Partner_API_IP_White`) |
| **Condition Kullanımı** | **Kötü:** Tüm endpoint'lere aynı IP kısıtlaması uygulamak<br />**İyi:** Public ve private endpoint'leri ayırmak<br />**En İyi:** Condition ile `/admin/*` path'lerine özel IP kontrolü, `/public/*` path'lerine IP kontrolü yapmamak |

### Güvenlik En İyi Uygulamaları

| Güvenlik Alanı | Açıklama / Uyarılar |
|----------------|---------------------|
| **En Az Yetki Prensibi (Least Privilege)** | **Kritik:** IP Beyaz Listesine sadece gerçekten gerekli IP'leri ekleyin. Geniş joker karakterleri (örn: `*.*.*.*`) kullanmaktan **kesinlikle** kaçının.<br />**Öneri:** Tek IP veya en fazla son oktet aralığı (örn: `192.168.1.*`) kullanın. |
| **IP Spoofing ve Proxy Güvenliği** | **Uyarı:** Eğer API Gateway önünde bir Load Balancer veya Reverse Proxy varsa, gerçek istemci IP'sini almak için `X-Forwarded-For` veya `X-Real-IP` header'larını doğru yapılandırın.<br />**Risk:** IP spoofing ile beyaz listeyi bypass etme riski. |
| **Geolocation Güvenilirliği** | **Not:** Geolocation servisleri %100 doğru değildir. VPN ve Proxy kullanımı ile atlatılabilir.<br />**Öneri:** Geolocation'ı tek başına değil, diğer güvenlik katmanları (JWT, API Key vb.) ile birlikte kullanın. |
| **Variable Güvenliği** | **Güvenlik Riski:** İstemci IP'si, istemcinin değerini belirleyebildiği bir variable'dan (örneğin bir istek header'ı) okunuyorsa, istemci kontrol edilecek adresi kendisi seçebilir.<br />**Öneri:** Yalnızca kendi altyapınızın belirlediği bir variable kullanın; örneğin güvenilir bir load balancer'ın eklediği header. |
| **Hata Mesajı Bilgi Sızıntısı** | **Dikkat:** Hata mesajlarında sistem mimarisi veya internal IP'ler hakkında bilgi vermeyin.<br />**Kötü:** "Your IP 203.0.113.5 is not in whitelist. Allowed range: 192.168.1.*"<br />**İyi:** "Access denied. Your IP address is not authorized." |
| **Düzenli Güncelleme ve Gözden Geçirme** | **Best Practice:** IP Beyaz Listesini düzenli olarak gözden geçirin (örn: aylık).<br />**Aksiyon:** Kullanılmayan, eski partner IP'lerini kaldırın. Değişen IP'leri güncelleyin. Audit log'larını kontrol edin. |
| **Multi-Factor Security** | **Öneri:** IP Beyaz Listesini tek güvenlik katmanı olarak kullanmayın.<br />**Best Practice:** IP kontrolü + API Key/JWT + Rate Limiting kombinasyonu kullanın. |
| **Production Ortam İzolasyonu** | **Kritik:** Production ortamı için ayrı global politika oluşturun. Test/Development ortamlarının IP'lerini production politikasına **asla** eklemeyin.<br />**Öneri:** Ortam bazlı Policy Group kullanın. |

### Kaçınılması Gerekenler

| Kategori | Açıklama / Uyarılar |
|----------|---------------------|
| **Geniş Aralıklar Kullanma** | **Neden kaçınılmalı:** `10.*.*.*` gibi geniş aralıklar milyonlarca IP'yi kapsayabilir ve güvenlik riskini artırır.<br />**Alternatif:** Spesifik aralıklar kullanın (örn: `10.10.50.*`). İhtiyaç duyulan IP'leri tek tek veya küçük aralıklarla ekleyin. |
| **İstemci IP'sini Güvenilmez Bir Variable'dan Okumak** | **Neden kaçınılmalı:** Variable'ın değeri yoksa politika isteği reddetmez.<br />**Alternatif:** Her zaman değeri olan bir variable kullanın veya **İstemci IP'sini Kullan** seçeneğini açık tutun. |
| **Politikayı Pasif Durumda Bırakma** | **Neden kaçınılmalı:** Pasif politika trafiğe uygulanmaz, unutulması durumunda güvenlik açığı oluşabilir.<br />**Alternatif:** Geçici olarak test etmek için kısa süreliğine pasif yapın. Test tamamlandıktan sonra aktif edin veya silin. |
| **Hata Mesajında IP Bilgisi Vermek** | **Neden kaçınılmalı:** Hata mesajında istemcinin veya izin verilen IP'lerin gösterilmesi saldırganlara bilgi verir.<br />**Alternatif:** Genel hata mesajları kullanın: "Access denied" veya "Unauthorized". Detaylı logları sadece sunucu tarafında tutun. |
| **Local Politika ile Yönetimi Karmaşıklaştırma** | **Neden kaçınılmalı:** Her API Proxy için ayrı local IP Beyaz Listesi politikası oluşturmak, yönetimi zorlaştırır ve IP güncellemelerinde tutarsızlık yaratır.<br />**Alternatif:** Global politika kullanın. Sadece gerçekten farklı IP gereksinimlerine sahip API Proxy'ler için local politika oluşturun. |
| **Geolocation'a Aşırı Güvenmek** | **Neden kaçınılmalı:** VPN, Tor, Proxy kullanımı ile coğrafi konum atlatılabilir. Hassas işlemler için yeterli değildir.<br />**Alternatif:** Geolocation'ı ek güvenlik katmanı olarak kullanın. Kritik işlemler için IP + Authentication + MFA kombinasyonu uygulayın. |
| **Politika Güncellemelerini Deploy Etmemek** | **Neden kaçınılmalı:** Global politikada yapılan değişiklikler deploy edilmeden canlı ortama yansımaz.<br />**Alternatif:** Politika güncellendikten sonra Deploy butonunu kullanın. Deploy işlemini CI/CD pipeline'a entegre edin. |
| **Test Etmeden Production'a Geçiş** | **Neden kaçınılmalı:** Yanlış IP yapılandırması tüm kullanıcıların engellenmesine neden olabilir.<br />**Alternatif:** Test ortamında politikayı doğrulayın. Önce passive modda deploy edin, logları kontrol edin. Sonra aktif edin. Rollback planı hazırlayın. |

### Performans İpuçları

| Kriter | Öneri / Etki |
|--------|--------------|
| **IP Grubu Boyutu** | **Öneri:** IP gruplarını maksimum 100-200 IP ile sınırlayın. Daha fazla IP gerekiyorsa birden fazla grup oluşturun.<br />**Etki:** Her istekte tüm IP listesi kontrol edilir. Çok büyük listeler performansı düşürür (her IP için O(n) karşılaştırma). |
| **Aralıkları Tercih Etme** | **Öneri:** IP aralıkları için mümkün olduğunca `*` ve `-` aralıklarını kullanın.<br />**Etki:** 254 ayrı kayıt yerine `192.168.1.*` (1 kayıt) kullanmak listeyi kısa tutar ve kontrolü hızlandırır. |
| **Geolocation Performansı** | **Not:** Geolocation lookup her istekte gerçekleşir ve ek gecikme yaratır (ortalama 1-5ms).<br />**Öneri:** Yüksek trafikli API'lerde geolocation yerine sabit IP listesi kullanmayı tercih edin. Geolocation sonuçlarını cache'leyin (IP → Country/City mapping). |
| **Condition Karmaşıklığı** | **Öneri:** Basit ve optimize edilmiş koşullar yazın. Gereksiz karmaşık regex veya nested condition'lardan kaçının.<br />**Etki:** Basit koşul (`path='/' AND method='GET'`) < 0.1ms. Karmaşık regex koşul > 1-2ms. |
| **Politika Sıralaması** | **Best Practice:** Policy Group içinde IP Beyaz Listesi politikasını önce çalıştırın.<br />**Mantık:** Yetkisiz IP'lerden gelen istekler erken aşamada engellenirse, diğer politikalar (Rate Limiting, JWT vb.) gereksiz yere çalışmaz. |
| **Log Seviyesi Ayarı** | **Production:** Log seviyesini ERROR veya WARN'da tutun.<br />**Development:** DEBUG veya TRACE kullanabilirsiniz.<br />**Etki:** Aşırı logging (her istekte IP kontrolü loglanması) disk I/O ve performans sorununa yol açabilir. |
| **Aktif Olmayan Politikaları Silme** | **Öneri:** Kullanılmayan veya pasif durumdaki politikaları düzenli olarak silin.<br />**Etki:** Veritabanı ve in-memory policy registry'nin küçük kalması, politika lookup süresini azaltır. |

## Sık Sorulan Sorular (SSS)

| Kategori | Soru | Cevap |
|----------|-----------|-----------|
| **Genel** | IP Beyaz Listesi politikası kaç tane IP destekler? | Teknik olarak sınır yoktur ancak performans için 500-1000 IP önerilir. Daha fazla IP için IP grupları ve `*` veya `-` aralıkları kullanın. |
| **Genel** | IPv6 adresleri destekleniyor mu? | Hayır. Yalnızca IPv4 adresleri eşleşir. |
| **Genel** | Politikayı pasif yapsam bile API Proxy deploy edilmeli mi? | Evet. Global politikalarda yapılan her değişiklik (aktif/pasif dahil) deploy edilmelidir. Local politikalarda API Proxy'nin kendisi deploy edilmelidir. |
| **Teknik** | `X-Forwarded-For` header'ından IP nasıl alınır? | API Gateway otomatik olarak `X-Forwarded-For`, `X-Real-IP` header'larını kontrol eder. Gateway ayarlarından "Use Forwarded IP" seçeneğini aktif etmelisiniz. Header yoksa direkt socket IP'si kullanılır. |
| **Teknik** | İstemci IP için Değişken nasıl formatlanmalı? | Variable tek bir istemci IP adresine çözülmelidir, örneğin `203.0.113.10`. |
| **Teknik** | CIDR notasyonu destekleniyor mu? | Hayır. Gateway tam IPv4 adreslerini, `*` joker karakterlerini ve her oktetteki `-` aralıklarını eşleştirir. `192.168.1.0/24` gibi bir kayıt hiçbir adresle eşleşmez. Bunun yerine `192.168.1.*` kullanın. |
| **Teknik** | Politika uygulandığında hangi HTTP header'lar eklenir? | Politika başarılı olduğunda herhangi bir header eklenmez. Başarısız olduğunda (IP reddedildi) custom hata mesajı döner. Debugging için `X-Apinizer-Policy-Status: REJECTED` gibi custom header'lar ekleyebilirsiniz. |
| **Kullanım** | Hem IP listesi hem de Geolocation kullanırsam mantık AND mi OR mu? | **AND** mantığı çalışır. İsteğin iki kontrolü de geçmesi gerekir:<br />- **IP kontrolü:** İstemci IP'si manuel IP listesindeki veya IP Gruplarındaki herhangi bir kayıtla eşleşir. İkisi de boşsa her adres geçer.<br />- **Geolocation kontrolü:** Geolocation etkinse ve ülke/şehir kuralları tanımlıysa, istemcinin konumu bu kurallardan biriyle eşleşir.<br />Bir kontrolü geçemeyen istek reddedilir. |
| **Kullanım** | Global politikayı güncelledim ama API'de yansımadı, neden? | Global politika değişiklikleri deploy edilmelidir.<br /><br />İşlem adımları:<br />- Politikayı kaydedin.<br />- Politika detay sayfasındaki "Deploy" butonuna tıklayın.<br />- Deploy edilecek ortamları (DEV, TEST, PROD) seçin.<br />- Deploy işlemini onaylayın.<br />- Deploy sonrası 1-2 dakika içinde değişiklikler canlıya yansır. |
| **Kullanım** | IP Grubunu silersem veya devre dışı bırakırsam politika ne olur? | **Uyarı:** Politika daha sıkı hale gelmez. Gateway silinen veya devre dışı bırakılan grubu atlar, bu yüzden grubun adreslerine artık izin verilmez. Politikada başka IP adresi veya grup yoksa IP listesi boşalır ve boş liste **her adrese** izin verir.<br />Politika grubu seçiminde tutar ve hata göstermez. Bir grubu silmeden veya devre dışı bırakmadan önce hangi politikaların kullandığını kontrol edin; IP Grubu penceresi bunları listeler ve her politikadaki etkiyi gösterir. |
| **Kullanım** | Geolocation servisi nasıl aktifleştirilir? | - Admin menüsünden "Geolocation Settings" sayfasına gidin.<br />- Geolocation sağlayıcısını seçin (örn: MaxMind GeoIP2).<br />- API Key veya lisans bilgilerini girin.<br />- "Test Connection" ile bağlantıyı test edin.<br />- "Enable Geolocation" toggle'ını açın ve kaydedin.<br />- Geolocation database'i düzenli güncellenmelidir (aylık). |
| **Kullanım** | Bir API Proxy'de hem global hem local IP Beyaz Listesi politikası kullanabilir miyim? | Teknik olarak evet, ancak **önerilmez**. İki politika da aktif ise **AND** mantığı çalışır (her iki listeye de uyması gerekir). Karmaşık yönetim ve beklenmeyen bloklamalara yol açabilir.<br />**Best Practice:** Global politika kullanın. Spesifik durum varsa global politikayı localize edin ve özelleştirin. |
| **Hata Giderme** | IP kaydım kabul edildi ama hiç eşleşmiyor, neden? | Ekran kaydın biçimini kontrol etmez. Tam IPv4 adresi (`192.168.1.100`), joker karakter (`192.168.1.*`) veya aralık (`192.168.1.4-18`) kullanın. CIDR (`192.168.1.0/24`), IPv6 veya eksik adres gibi diğer biçimlerdeki kayıtlar hiçbir adresle eşleşmez. |
| **Hata Giderme** | Whitelist'e eklediğim IP hala 403 alıyor, ne yapmalıyım? | Troubleshooting adımları:<br />- Politika **aktif** mi kontrol edin (active=true).<br />- Global politika ise **deploy edilmiş** mi kontrol edin.<br />- API Gateway loglarında istemcinin gerçek IP'sini görün (Load Balancer arkasındaysa X-Forwarded-For).<br />- Condition tanımlı mı? Koşul sağlanıyor mu kontrol edin.<br />- IP kaydı desteklenen biçimde mi (CIDR değil)?<br />- İstemci IP'si için variable kullanılıyorsa variable değerini kontrol edin.<br />- Cache temizliği yapın (politika cache'i reload).<br />Hala sorun varsa destek ekibine log dosyalarını iletin. |
| **Hata Giderme** | Geolocation kontrolü çalışmıyor, ne yapmalıyım? | Kontrol listesi:<br />- Geolocation Settings'de servis aktif mi?<br />- Geolocation database güncel mi? (Son güncelleme tarihini kontrol edin)<br />- İstemci IP'si public IP mi? (Private IP'ler için geolocation çalışmaz: 192.168.x.x, 10.x.x.x)<br />- VPN veya Proxy kullanılıyor olabilir (gerçek lokasyonu gizler).<br />- API Gateway loglarında geolocation lookup sonucunu kontrol edin (hangi ülke/şehir tespit edilmiş).<br />- Geolocation sağlayıcısının API limit'ine ulaşılmış olabilir. |
