## Log Kayıt Bölgeleri

Apinizer üzerinde tanımlanan API Proxy'e gelen ve giden mesaj bilgileri mesaj ögelerine (başlık, parametre, gövde) göre Elasticsearch veri tabanında loglanmaktadır.

Bu log kaydı tutulan bölgeler:

<CardGroup cols={2}>
  <Card title="Request from Client" icon="arrow-right">
    İstemciden API Proxy'e gelen istek bilgileri
  </Card>
  <Card title="Request to Target" icon="arrow-right">
    API Proxy'den Backend API'ye iletilen istek bilgileri
  </Card>
  <Card title="Response from Target" icon="arrow-left">
    Backend API'den API Proxy'e verilen yanıt bilgileri
  </Card>
  <Card title="Response to Client" icon="arrow-left">
    API Proxy'den istemciye gönderilen yanıt bilgileri
  </Card>
</CardGroup>

Varsayılan olarak, projenin tüm mesaj bölgelerindeki alanların loglanması aktiftir. Loglanan alanlar ihtiyaca göre veya log sunucusunun kaynak tüketimi baz alınarak kısıtlanabilir.

Bu ekran üzerinden proje ve ortam (environment) bazlı log ayarı yönetilmektedir.

:::info

Üretim ortamı için aşağıdaki ortamlara ait ögeleri loglama işleminin devre dışı bırakılması tavsiye edilmektedir.

- API Proxy'den Backend API'ye (Request to Target)
- Backend API'den API Proxy'e (Response from Target)

Eğer bir API Proxy üretim ortamında çalışıyorsa, API Proxy'deki tüm poliçelerin ayarları ve testleri tamamlandığı ve artık geliştirme yapılmayacağı anlamına gelmektedir.

Bu yüzden veri tabanında verilerinin aşırı büyümemesi bu iki bölgedeki başlık, parametre ve gövde verilerinin yazılmaması tavsiye edilir.

:::

:::warning

Tüm loglama alanları kapalı olsa dahi istekte de bir hata oluştuysa log alanlarının tümü hatanın tespit edilebilmesi için kayıt edilir. Bu özellik genel ayarlarda açılıp, kapatılabilir.

:::

:::warning

Formdata istekleri değişken veri büyüklükleri ve veri formatları nedeniyle dosya kısımları hiçbir şekilde loglanmamaktadır. Sadece diğer metadata alanları loglanmaktadır.

:::

:::warning

Websocket ve gRPC istekleri Apinizer'a gelen ve Apinizer'dan çıkan veriler şeklinde tutulmakta olduğundan bu tip API Proxylerde sadece 2 bölge vardır.

:::

Bu ekranda [API Proxy](/tr/concepts/temel-kavramlar/api-proxy-nedir) bazlı trafik log ayarlarını yönetebilirsiniz. [Ortam](/tr/concepts/temel-kavramlar/ortam-nedir) üzerinde tanımlı [konnektör](/tr/concepts/temel-kavramlar/konnektor) entegrasyonları varsa, her proxy için trafik kayıtlarının bu hedeflere gönderilip gönderilmeyeceğini buradan ayarlarsınız.

### Listede neler görünür

Her satır, bir ortamdaki bir API Proxy'nin bir konnektörünü gösterir. Liste yalnız kaydettiğiniz değerleri değil, geçerli olan değerleri gösterir.

| Sütun | Açıklama |
|------|----------|
| API Proxy | API Proxy adı. |
| Ortam | Ortam adı. Altındaki satır API Proxy'nin o ortamdaki deploy durumunu gösterir: **Deploy edildi**, **Yeniden deploy gerekli** veya **Deploy edilmedi**. |
| Konnektör | Konnektörün adı ve tipi. Konnektör açık değilse altındaki satır nedenini gösterir: **Kapalı**, **Ortamda devre dışı** veya **Kapalı · yapılandırılmamış**. |
| İstemciden API Proxy'e Gelen İstek, API Proxy'den Backend API'ye İletilen İstek, Backend API'den API Proxy'e Verilen Yanıt, API Proxy'den İstemciye Gönderilen Yanıt | Her mesaj bölgesi için nelerin yazıldığı: Parametre, Header, Body veya hiçbir şey yazılmıyorsa tire. Ortam kısıtı ve saklama profili uygulanmış hâldedir. Ortam değeri daraltmışsa ipucu bunu söyler. Saklama profili **Kalıcı yok** ise hücrede **Saklanmaz (saklama profili)** yazar. |
| Kapalı alanlar | Kapalı olan log içeriği grupları: **İstek ayrıntıları**, **İstemci adresi**, **Metrikler**, **Yanıt durumu**. İpucu, bu alanları hangi ekranların okuduğunu gösterir. Metot bazlı geçersiz kılmalar burada sayılmaz. |
| Metot Bazlı Geçersiz Kılma | Metot bazlı geçersiz kılma sayısı. |
| Proje | API Proxy'nin projesi. Yalnız yönetim projesinde görünür. |

Kaydedilen log ayarları gateway'e hemen gönderilir. Yeniden deploy gerekmez; bu yüzden deploy durumunun bu ekranda bir işlemi yoktur.

Listeyi daraltmak için listenin üstündeki filtre çubuğunu kullanın. **API Proxy**, **Ortam**, **Proxy deploy durumu** ve **Kapalı alanlar** her zaman görünür (yönetim projesinde **Proje** de). **Diğer filtreler** ile **Bağlayıcı durumu**, **Body loglanıyor**, **Metot Bazlı Geçersiz Kılma**, **Ortam kısıtlarını ez**, **Saklama profili** ve API Proxy özellikleri gibi daha fazla filtre ekleyebilirsiniz. **Excel** filtrelenen listeyi indirir: her API Proxy, ortam ve konnektör için bir satır; deploy durumu, konnektör durumu, dört mesaj bölgesi, kapalı alanlar, saklama profili ve metot geçersiz kılma sayısı ile. Liste dışa aktarma sınırından uzunsa dosya kesildiğini belirtir.

### Birçok API Proxy'ye uygulama

Birçok API Proxy'nin log ayarlarını tek adımda değiştirebilirsiniz. Log ayarlarını değiştirme yetkisi olan kullanıcılar onay kutularını ve düğmeleri görür.

1. Filtre çubuğunda tek bir ortam seçin. Yönetim projesinde tek bir proje de seçin. Log ayarları bir seferde tek ortama ve tek projeye uygulanır. Bunlar seçilene kadar düğmeler pasif kalır ve ipucu neyi seçeceğinizi söyler.
2. İstediğiniz satırları işaretleyin. Sütun başlığındaki onay kutusu (**Bu sayfadakilerin tümünü seç**) sayfadaki tüm satırları işaretler. Listenin üstündeki çubuk seçili satır sayısını ve **Seçimi temizle** düğmesini gösterir.
3. **Seçililere uygula** düğmesini seçin. Filtrelerin listelediği tüm API Proxy'lere, tüm sayfalarda, uygulamak için **Filtrelenen sonuçlara uygula** düğmesini seçin. Bu düğme hiçbir satır işaretli değilken de görünür.
4. **Log ayarlarını uygula** penceresinde konnektörü seçin. Değiştirmek istediğiniz her alan için **Değiştir** kutusunu işaretleyin ve **Yeni değer** belirleyin. Alanlar şu gruplardadır: **Bağlayıcı** (açık veya kapalı), **İçerik** (her mesaj bölgesinin Parametre, Header ve Body ayarları), **Body boyut sınırı** ve **Alan grupları** (HTTP İstek Ayrıntıları, İstemci Adresi, Performans Metrikleri, Yanıt Durum Bilgileri, Routing Adresi, Politika Çalışma Süreleri).
5. **Önizleme** bölümünü kontrol edin ve **Uygula** düğmesini seçin.

Yalnız işaretlediğiniz alanlar değişir. Diğer alanlar, metot bazlı geçersiz kılmalar ve boş (varsayılan) değerler olduğu gibi kalır. **Ortam kısıtlarını ez**, **Gizlilik**, **Metot override'ları** ve saklama profili burada değişmez. Bunları her API Proxy için ayrı düzenleyin.

Ayarlar 50'şer API Proxy'lik gruplar hâlinde gönderilir. Pencere ilerlemeyi gösterir; **İptal** henüz gönderilmemiş grupları durdurur. İşlem bitince pencere her API Proxy için sonucu listeler:

| Sonuç | Anlamı |
|------|----------|
| Kaydedildi ve gönderildi | Ayarlar kaydedildi ve gateway'ler ayarları aldı. |
| Kaydedildi; gateway güncellemesi eksik | Ayarlar kaydedildi, ancak tüm gateway'ler güncellenmedi. Güncellenmeyen gateway'ler sonucun yanında gösterilir. |
| Kaydedildi, gateway'e ulaşılamadı | Ayarlar kaydedildi, ancak gateway'e ulaşılamadı. |
| Kaydedilmedi: neden | Ayarlar kaydedilmedi. Neden şunlardan biridir: API Proxy bulunamadı veya log ayarlarını değiştirme yetkiniz yok; ortam bu API Proxy'nin projesine açık değil; proxy düzeyinde log ayarı olmadan metot override'ları var (bu API Proxy'yi tek başına düzenleyin); ayarlar kaydedilemedi. |

Ortamda deploy edilmemiş bir API Proxy de kaydedilir. Ayarlar proxy'yi deploy ettiğinizde geçerli olur.

### Düzenleme penceresi (Edit API Traffic Proxy Log Settings)

Satırda **Düzenle** ile açılan pencerede solda **CONNECTORS** menüsünde Logback, Webhook, Kafka, RabbitMQ, veritabanı, Syslog, Elasticsearch gibi log hedefleri listelenir; bir öğeye tıkladığınızda sağda yalnızca o hedefe özel form görüntülenir. Üstte ortam seçimi ve **Save and Deploy** bulunur; her konnektör kartında **Active for this environment** anahtarı ile seçili ortamda gönderimin açılıp kapatılmasını yönetirsiniz. Menüdeki renkli durum göstergesi, ilgili konnektör için yapılandırmanın özet durumunu yansıtır. **Method Overrides** ile metot bazlı ek yapılandırmaya geçebilirsiniz.

**Method Overrides** bölümünde metotlar, yolun önünde HTTP metodu ile listelenir (örneğin `GET /pet/{petId}`); böylece aynı yolu paylaşan ancak metodu farklı olan uç noktalar birbirinden ayırt edilebilir. SOAP operasyonları gibi HTTP metodu bulunmayan kayıtlar yalnızca adıyla listelenir.

Seçtiğiniz konnektör için **Log içeriği** bölümünde HTTP istek ayrıntıları, istemci adresi, performans metrikleri ve yanıt durumu gibi üst düzey grupları ayrı ayrı işaretleyebilirsiniz; bu gruplar birbirinden bağımsızdır. Dört mesaj bölgesi bir isteğin akışını izler ve bu sırayla numaralanır: **1** Request from Client, **2** Request to Target, **3** Response from Target, **4** Response to Client. Her bölgede Parametre, Başlık ve Gövde (ve varsa **Partial Size** / kısmi boyut) ayarlarını düzenlersiniz. **Routing Adresi** 2. bölgededir, çünkü gateway bu bilgiyi isteği backend'e gönderirken yazar. Altta **Privacy** ile gizlilik işleme seçeneğini açıp kapatabilirsiniz.

Veritabanı konnektörü log hedefi olarak seçildiğinde, log tablolarının şema ön eki veya özel tablo adı **bağlantı (Connection) tanımında** ayarlanır. Detay için [Veritabanı Bağlantısı](/tr/integrations/baglanti-yonetimi/database) sayfasına bakın.

## Sonradan Eklenen Konnektörler {#sonradan-eklenen-konnektorler}

API Proxy'nin log ayarlarında kaydı olmayan konnektör trafik logu almaz. Trafik Log Ayarları listesinde durumu **Yapılandırılmamış** olur. Proxy'nin log ayarlarını kaydettikten sonra ortama eklediğiniz konnektör buna örnektir.

Yeni bir konnektöre loglamayı başlatmak için API Proxy'nin log ayarlarını açın, konnektörü seçin, **Bu ortam için aktif** anahtarını açın ve **Save and Deploy** seçeneğini seçin.

- **Yükseltme:** Yükseltmede Apinizer, log ayarı olan her API Proxy için ortamda zaten var olan her konnektöre açık bir kayıt ekler. Bu konnektörler eskisi gibi loglamaya devam eder. Konnektör kaydı olmayan bir API Proxy yükseltmeden önce hiçbir şey loglamıyordu ve sonra da loglamaz.
- **Yükseltme sırası:** Önce Manager'ı yükseltin. Manager logunda `Migration 202610-007030: completed` satırını görene kadar bekleyin. Ardından Gateway Engine örneklerini yeniden başlatın. Geçiş bitmeden başlayan Gateway Engine, kaydı olmayan konnektörleri kapalı sayar.
- **Okunamayan konnektör:** Yükseltme bir konnektörü veya ortamı okuyamazsa Manager loguna bir WARN satırı yazar ve onu atlar. Tamamlanma satırı da WARN'dır ve atlanan öğe sayısını gösterir. Atlanan konnektöre loglamak için o konnektörde **Bu ortam için aktif** anahtarını açın.

:::warning

APIops ile log ayarlarını güncellerseniz gönderdiğiniz konnektör ayarları kayıtlı konnektör ayarlarının yerine geçer. Kısmi güncellemede listelemediğiniz konnektörün sonrasında kaydı olmaz, bu yüzden loglamayı durdurur. Loglamaya devam etmesini istediğiniz her konnektörü gönderin. Aynısı metod geçersiz kılmaları için de geçerlidir.

:::

## Log Ayarları Alanları

Log ayarları için kullanılan başlıca alanlar aşağıdaki tabloda özetlenmektedir.

| Alan | Açıklama |
|------|----------|
| Active for this environment | Seçili ortamda bu log hedefine trafik kaydı gönderilip gönderilmeyeceğini açar veya kapatır. |
| HTTP istek ayrıntıları | HTTP metodu, URI, port, çağıran kimliği gibi istek üst bilgilerinin loga dahil edilmesini yönetir. Kapalıyken istemci adresi alanları da çıkarılır. |
| İstemci adresi | İstemci IP'sini, forwarded-for adresini, uzak host ve portu ve IP'den türetilen konumu yönetir. HTTP istek ayrıntılarını yalnız daraltır: bu seçenek kapalı, HTTP istek ayrıntıları açıkken HTTP metodu, URI ve çağıran kimliği yine yazılır. Açık bir değeri olmayan kayıt HTTP istek ayrıntılarını izler. Açıkça kapatılırsa adres, başarısız veya engellenen isteklerde de yazılmaz. |
| Performans metrikleri | Süre, iletişim boyutu, önbellek ile ilişkili metriklerin loga yazılıp yazılmayacağını yönetir. |
| Yanıt durumu bilgisi | HTTP durum kodu ve hata tipi gibi alanların loga dahil edilmesini yönetir. |
| Yönlendirme adresi | Yönlendirme veya hedef adres bilgisinin loga yazılıp yazılmayacağını yönetir. |
| Başlık (Header) | İlgili mesaj bölgesinde başlık bilgilerinin loglanıp loglanmadığını yönetir. |
| Gövde (Body) | İlgili mesaj bölgesinde gövde bilgilerinin loglanıp loglanmadığını yönetir. |
| Parametre (Parameter) | İlgili mesaj bölgesinde parametre bilgilerinin loglanıp loglanmadığını yönetir. |
| Kısmi boyut (Partial size) | Uzun metin alanlarında kayıt boyutunun sınırlandırılıp sınırlandırılmayacağını ilgili mesaj bölgesi için yönetir. |
| Politika çalışma süreleri | İstekte çalışan her politikanın sırasını, tipini ve milisaniye cinsinden süresini loga ekler. Varsayılan olarak kapalıdır; bkz. aşağıdaki bölüm. |
| Gizlilik (Privacy) | Ortamda tanımlı gizlilik kurallarının bu konnektör çıkışındaki log akışına uygulanıp uygulanmayacağını yönetir. |

**HTTP istek ayrıntıları** kapalıyken çağıranın kullanıcı adı ve çağıranın atıf bilgisi o konnektörün trafik logundan çıkarılır: tipli istemci atıf kimlikleri (`ack`, `cot`, `coi`, `coo`) ve abonelik kimlikleri (`subi`, `subp`, `subpl`, `subo`). AI kiracı kimlik bilgisi (`aivk`) yazılmaya devam eder. Bu kimliklere göre sayan kullanım raporları ve AI alarmları o konnektörün trafiğini görmez; kota ve limit uygulaması etkilenmez.

## Politika Çalışma Süreleri

Bir istek beklenenden yavaş olduğunda sıradaki soru genellikle *hangi politikanın süreyi yediğidir*.
Bugüne kadar bu sorunun cevabı için API Proxy üzerinde **Trace** açmak gerekiyordu; Trace her
politikanın gövdesini, başlıklarını ve parametrelerini öncesi/sonrasıyla kaydettiği için production
ortamında sürekli açık tutulamaz.

**Politika çalışma süreleri** aynı soruyu hiçbir içerik yakalamadan cevaplar. Ayar açıldığında her
trafik log kaydı, o istekte çalışan politikaların kısa bir listesini taşır:

| Değer | Anlamı |
|------|----------|
| Sıra | Çalışma sırası. Değer aynı zamanda hattı da taşır: `0-9999` istek, `10000-19999` yanıt, `20000` ve üzeri hata. API Trafiği detay ekranı hem hattı hem hat içindeki sırayı gösterir. |
| Politika tipi | Politikanın tipi; örneğin `jwt-auth` veya `content-filter`. Politika *adı* bilinçli olarak tutulmaz — genellikle otomatik üretilmiş bir tanımlayıcıdır ve ekranda bir anlam taşımaz. |
| Süre | Politikanın çalışma süresi (milisaniye). |

Akış (streaming) yanıtının sonunda çalışan kayıtlar, koşulu karşılanmadığı için atlanan politikalar ve
alışılmadık sayıda politika çalıştığında eklenen kesme işareti, politika tipinin yanında küçük bir
rozetle gösterilir.

Ölçümün kendisi yeni bir iş değildir: gateway her politikanın süresini zaten her istekte hesaplıyor ve
Trace kapalıyken bu değeri atıyordu. Bu ayar yalnızca değerin saklanmasını sağlar.

### Ayarın açılması

Ayar diğer log içerik seçenekleriyle birlikte durur ve **log hedefi başına** verilir; böylece süreleri
Elasticsearch'e yazarken ilişkisel veritabanı hedefinin dışında bırakabilirsiniz. Metot bazlı
geçersiz kılmalar da geçerlidir.

**Değişiklikten sonra API Proxy'yi yeniden dağıtın** — trafik log ayarları gateway'e proxy dağıtımıyla
birlikte ulaşır.

### Verinin yazıldığı yer

| Hedef | Temsil |
|------|----------|
| Elasticsearch | `pxt` alanı, `nested` obje dizisi olarak. `nested`, tip ile süreyi ilişkili tuttuğu için "X politikasının süresi 100 ms'den büyük olan istekler" gibi bir sorgu doğru satırları döndürür. |
| MongoDB | Alt doküman dizisi. |
| İlişkisel veritabanı (SQL/JDBC) | `policy_exec_times` kolonu; karakter sınırlı tek bir CSV: `sıra:tip:süre`, dikey çizgiyle ayrılmış. |
| Graylog | İlişkisel hedefle aynı CSV. |

:::note
Ayar varsayılan olarak kapalıdır. Elasticsearch tarafında `nested` alan, listedeki her öğeyi ayrı bir
iç doküman olarak indeksler; dolayısıyla 10-20 politikalı bir kayıt o indeksin doküman sayısını buna
göre artırır. Yalnızca veriye gerçekten ihtiyaç duyduğunuz hedeflerde açın.
:::

:::info Mevcut Elasticsearch indeksleri
Yeni alan yükseltme sırasında indeks şablonuna eklenir ve indeks otomatik olarak rollover edilir.
Trafik logları bir data stream'e yazıldığı için alan yalnızca rollover sonrası oluşan backing
indekslerde bulunur; eski kayıtlar olduğu gibi kalır.
:::

:::info SQL/JDBC log hedefi
Trafik loglarını ilişkisel bir veritabanına yazıyorsanız `policy_exec_times` kolonunun her ortam
veritabanına bir kez eklenmesi gerekir. ALTER betiği için [2026.09.1 — Log Tablosu ALTER Scriptleri](/tr/release-notes/2026-09-1-log-tablosu-alter)
sayfasına bakın; yeni kurulumlarda kolon
[Apinizer Logları için Tablo Oluşturma Komutları](/tr/operations/yonetici-kilavuzlari/apinizer-log-tablolari-olusturma-komutlari)
scriptiyle zaten oluşur.
:::
